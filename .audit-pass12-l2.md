### Fix 1 — K2-1: Lua extend in `enqueueDeduped` — ⚠️ PARTIALLY FIXED (correct code, overstated commit, one sub-path untouched)
`backend/src/queues.ts:241-252`. The extend is now a single Lua script: `if redis.call('exists',KEYS[1])==1 then return redis.call('expire',KEYS[1],ARGV[1]) else return 0 end`, with `.catch(() => 0)` → warn log on `extended !== 1`.

**Adversarial Q (the brief's explicit ask) — is compare-and-exists actually correct under all interleavings?** Yes, for what it does — but it is **exists-extend, not compare-extend**, and the distinction matters:
- The claim value is the constant `'1'` (`limiterRedis().set(mapKey, '1', 'EX', 60, 'NX')`, `:232`). A true value-compare (like `leaderElection.ts`'s token compare-and-pexpire) is *impossible* without changing the claim protocol to per-claimer random tokens. The commit message ("Lua compare-extend") overstates what was built.
- Interleaving trace — key is ours → extended, correct. Key lapsed and re-taken by a second claimant → we extend *their* claim: benign (the re-taker owns the window; their own extend/release governs; the throw-path release is an unconditional `DEL`, so no clobber). Key lapsed and released → Lua returns 0, no resurrect. In fact, across every interleaving I constructed, the Lua has **identical observable behavior to a plain `EXPIRE`** — `EXPIRE` on a deleted key is already a no-op. The Lua's material contribution is observability (return 0 → warn), not atomicity.
- `.catch(() => 0)` maps a Redis *error* to the "lapsed" warn — the message is then inaccurate (key may still hold our 60s claim), but harmless.

**Residual — K2-1 path (b) is UNFIXED:** if `Queue.add` hangs >60s on the retry-forever BullMQ connection (`maxRetriesPerRequest: null`, `getConnection().duplicate()`), the short claim still lapses mid-enqueue and a concurrent caller still double-enqueues; the fix's own comment acknowledges this ("If the key is gone, our claim lapsed mid-enqueue … log it"). K2's suggested mitigations (refresh the claim while enqueue is in flight; size the short TTL to cover enqueue latency) were **not** implemented. Paths (a) swallowed-extend-failure → now logged (still collapses to 60s on eval failure, but visible) and (c) crash-between-add-and-extend → unchanged 60s phantom (inherent to the short-claim design) are accepted. So: the fix is correct code that closes the *silence*, not the *lapse*. Same LOW severity, same narrow trigger (>60s Redis stall coinciding with a manual enqueue), consequence bounded (one duplicate LLM report; DB-layer idempotency still prevents double-notify/double-write). Recorded here as a **residual of K2-1, not a new finding** (re-filing the identical sub-path would double-count).

No regression test covers the Lua extend (the 4 pass#11 tests are K5-LOW-1, K1-LOW-1, K2-3, K5-LOW-3).

### Fix 2 — K2-2: scheduler per-site try/catch — ✅ VERIFIED for the helper; ❌ INCOMPLETE (one loop missed — NEW LOW L2-2 below)
`backend/src/scheduler.ts:68-82` — each `enqueue` in `enqueueForVerifiedSites` is now wrapped; failures log per site and the tick continues.

**Adversarial Q — does it preserve the tick's idempotency?** Yes. Idempotency keys are computed once per tick (C2-L6) *before/outside* the loop and are untouched by the catch; the catch neither re-enqueues nor mutates keys. A failed site simply misses this tick and is picked up next cycle under a fresh key. No double-enqueue path: BullMQ `add` is atomic accept-or-reject, so a throw means nothing was queued. There is no tick watermark, so "tick completed with per-site errors logged" has identical downstream semantics to the old "tick aborted, wrapper logged". `extra(s.id, s.tenant_id)` is evaluated *inside* the try (argument expression), so a throwing `extra` is isolated too. **The helper is fixed.**

**But** the `rank-checks` schedule (`scheduler.ts:128-139`) runs its own inline loop with a **bare `await enqueue`** — the pass#11 fix only wrapped the helper. Same abort-mid-tick shape K2-2 filed, still live on the daily rank-check tick. Filed as NEW LOW L2-2 (§2).
