## 2. NEW findings (4 LOW)

### NEW LOW-1 — checkout-claim 10-min steal applies to `'open'` claims: abandoned-then-restarted checkout can yield two live Stripe subscriptions
**Files:** `backend/src/routes/billing.ts:348-366`; `backend/migrations/050_wave4_pass9_checkout_claim.sql`
**What's wrong:** the comments (`billing.ts:331-332`, migration 050) say *"a stale 'creating' claim (>10 min — the creator crashed mid-flight) is stolen."* The code steals **any** claim older than 10 min by `created_at` regardless of status — including `'open'`, whose Stripe session URL stays valid for 24h (and the `'open'` UPDATE never refreshes `created_at`, so the window is measured from session *creation*, not last activity). Trigger: user starts checkout (claim `'open'`), abandons it for 11 minutes, starts a new checkout → old claim silently deleted, second live Stripe session created → user completes **both** sessions (old tab + new tab) → two live subscriptions, two charges; the second sub's events hit the E4-H-2 warn-and-ignore → billed twice, entitled once. This is the I1-L-3 double-session shape the claim was built to kill, reopened through abandonment instead of concurrency. (Fellow pass#10 auditor J4 filed the *docs* facet of this same code fact — comments misstating steal semantics — as a docs LOW; this filing is the *behavioral* residual: the steal predicate itself.)
**Impact:** LOW — requires the user to complete two payments (self-inflicted, card-statement-visible); same severity as the original I1-L-3.
**Fix:** steal only `status='creating'` claims; for stale `'open'` claims keep the 409/URL-reuse (the session is valid until `checkout.session.expired` releases it) — or refresh `created_at` on the `'open'` transition so the window measures inactivity.
**Duplicate check:** grepped `.audit-pass{1..9}-*.md` for steal/claim phrasing — only J4 (pass#10, out of scope for the duplicate rule) and unrelated hits. I1-L-3 (pass#9) covered the pre-fix concurrent race, not the post-fix steal. **NEW.**

### NEW LOW-2 — `invoice.payment_failed` no-row path duns without minting; the later `subscription.updated` for the same failure mints AND duns → two dunning emails, one episode
**Files:** `backend/src/providers/stripe.ts:1116-1128` (payment_failed `won` fallback), `:904-917` (updated `justMinted`)
**What's wrong:** when no subscription row exists, the atomic UPDATE matches 0 rows and `won` falls back to `rows.length === 0 → true` — "keep the old emit behavior" — so payment_failed **sends the dunning email without minting any grace**. When the same failure's `customer.subscription.updated(past_due)` is processed later (it upserts/INSERTs the row), `justMinted` is true and it duns **without consulting `episodeDunningSent`** — the first email is invisible to it. Net: 2 identical dunning emails for one failure. Worse, *every* Smart Retry arriving while the row is still missing re-duns (the no-row `won=true` fallback fires per retry). Reachable via out-of-order delivery: payment_failed (newer `created`) processed before `customer.subscription.created`/`checkout.session.completed` arrive — the C-01 stale guard then *drops* the older `created`, so the row genuinely doesn't exist until the later `updated` INSERTs it.
**Impact:** LOW — email-only duplication in a narrow ordering window; no money/data/privilege impact.
**Fix:** gate the `justMinted` emit on `!(await episodeDunningSent(q, tenantId, graceUntil))` as well — the prior send is recorded in `notification_log`, so the later minter would stay silent; the genuine first-failure path (no prior send) is unaffected.
**Duplicate check:** H1-L-2 covered sequential cross-event duns *with a row*; I1-L-1 covered the atomic mint *with a row*. The no-row emit-then-mint interleaving is unreported in passes 1–9. **NEW.**

### NEW LOW-3 — `justMinted`'s exact-millisecond comparison double-duns on a same-ms `graceDeadline()` collision
**Files:** `backend/src/providers/stripe.ts:904-915`
**What's wrong:** the race-safety argument ("the stored value equals THIS event's computed graceUntil only if this event minted") assumes distinct `graceDeadline()` values. Two *distinct* `customer.subscription.updated(past_due)` events (different event ids — e.g. a metadata change and a plan change both landing past_due) processed concurrently can both compute `graceDeadline()` within the same millisecond → both upserts store the identical timestamp → both compute `justMinted=true` → both emit. (Same-`event_id` duplicates are saved by the H2-L-1 claim dedupe; this needs distinct events.)
**Impact:** LOW — email-only; needs concurrent distinct past_due updates *and* a 1-ms computation collision.
**Fix:** replace the ms-equality with a small tolerance window, or derive the emit decision from an atomic conditional write instead of comparing timestamps.
**Duplicate check:** no pass discusses `justMinted`/ms-equality. **NEW.**

### NEW LOW-4 — `episodeDunningSent` re-duns multiply under concurrent retries
**Files:** `backend/src/providers/stripe.ts:439-460`, `:918`, `:1140`; `backend/src/services/billing.ts:93-121`
**What's wrong:** the I1-L-2 re-dun path is check-then-act across two concurrent deliveries: two Smart-Retry `invoice.payment_failed` events (grace active, minting send transiently failed) both evaluate `episodeDunningSent → false` before either sends. The H2-L-1 claim-first dedupe that would save a same-event redelivery is keyed on `(event_id, notification_type)` — distinct retries carry distinct event ids, so both win their own claim and both send.
**Impact:** LOW — email-only; needs a transient send failure at mint time *plus* concurrent retry processing.
**Fix:** make the re-dun claim episode-scoped (e.g. claim key includes tenant + episode anchor) instead of event-scoped.
**Duplicate check:** unreported in passes 1–9. **NEW.**
