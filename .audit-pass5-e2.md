## NEW findings

### M-1 — MEDIUM — `reserveGlobalProviderBudget`'s FOR UPDATE serialization is broken; concurrent reserves overshoot the cap (D5-L-3 fix does not fix)

**File:** `backend/src/services/providerGuard.ts:95-96` (the false claim), `:108-155` (the statement)

**What's wrong:** The comment claims the single-statement `INSERT … SELECT … WHERE … AND EXISTS (SELECT 1 FROM global_provider_guard … FOR UPDATE)` serializes concurrent reserves because "READ COMMITTED then re-evaluates the daily totals against the committed rows." That is false. The `today` CTE is evaluated once with the **statement-start snapshot**; when a second reserve blocks on the guard-row lock and the first commits, EvalPlanQual only re-checks the **guard row's own quals** (`day = today`, which never changes — reservers never modify the guard row, they only `INSERT … ON CONFLICT DO NOTHING` it and insert into `provider_spend`). The CTE is never recomputed, so the second reserve inserts against a stale total. The FOR UPDATE serializes *statement execution order* but not the *check*.

**Concrete trigger (reproduced on PG 16):** cap = 100¢, existing daily spend = 40¢. Session A holds the guard-row lock (simulating its reserve statement in flight); session B starts the exact reserve statement (50¢) and blocks on the lock (confirmed via `pg_stat_activity wait_event_type='Lock'`); A commits its own 50¢ reservation; B unblocks and **inserts** — final total **140¢ > 100¢ cap**. Correct serialized behavior would reject B (40+50=90, 90+50=140 ≥ 100 → 0 rows). B returned a reservation id.

**Why MEDIUM not HIGH:** both caps default to 0 (disabled) via `globalCapsFromEnv()`, so the bug is latent in default deployments; overshoot is bounded by (concurrent in-flight reserves × per-reservation cost), and per-call costs are cents. But it is a money-control whose central documented guarantee ("atomic check-AND-reserve") is empirically false, and the test suite actively encodes the false belief (`tests/wave4/w4-fix4-cleanup.test.ts:57` — "global reserve enforces the cap atomically" — only ever runs **sequential** reserves, so it cannot catch this).

**Fix suggestion:** keep the running totals **on the guard row itself** and make the guard row the UPDATE target, so EPQ re-evaluation applies to the checked values:
```sql
UPDATE global_provider_guard
SET cost_cents = cost_cents + $5, units = units + $4
WHERE day = today AND NOT ((capCents > 0 AND cost_cents + $5 >= capCents) OR …)
RETURNING day;
```
then insert the `provider_spend` evidence row separately. I validated this pattern empirically on the same scratch DB: the second concurrent attempt correctly got `UPDATE 0` (rejected) and the total stayed at 90 ≤ 100. Alternative: explicit transaction with `pg_advisory_xact_lock` around check+insert, exactly as `metering.ts:reserveUsage` already does correctly.

### L-1 — LOW — 045 breaks `scripts/seed.ts`'s site upsert (`ON CONFLICT` without the partial-index predicate)

**File:** `scripts/seed.ts:55`; broken by `backend/migrations/045_wave4_fix4_cleanup.sql:10-18`

**What's wrong:** 045 drops the full `UNIQUE (tenant_id, domain)` constraint and replaces it with the partial index `… WHERE deleted_at IS NULL`. `ON CONFLICT (tenant_id, domain)` without the matching predicate no longer resolves to any unique index. Reproduced on PG 16: `ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification`. `src/routes/sites.ts:144` was updated to the predicate form; `seed.ts` was missed, so seeding a fresh DB now crashes at the demo-site upsert.

**Fix:** `ON CONFLICT (tenant_id, domain) WHERE deleted_at IS NULL DO UPDATE …` (mirroring `routes/sites.ts:144`).

### L-2 — LOW — 044's "seed/demo rows are backfilled far-future" invariant fails for post-migration seeds; column default hardcodes 14d vs env-overridable trial length

**Files:** `backend/migrations/044_trial_ends_at.sql`; `scripts/seed.ts:38`; `backend/src/services/billing.ts:108-116`

**What's wrong:** (a) The migration comment promises seed/demo rows are grandfathered, but the backfill only covers rows existing *at migration time*. On a fresh DB (migrations → seed), `seed.ts` inserts the demo tenant without `trial_ends_at`, so the column default (`now() + 14 days`) applies — 14 days later the demo tenant hits `requireActiveSubscriptionOrTrial`, gets 402 `SUBSCRIPTION_REQUIRED`, and is flipped `read_only`. (b) Related: `signupTrialDays()` is env-overridable (`SIGNUP_TRIAL_DAYS`), but the column default hardcodes `interval '14 days'` — any insert path that doesn't set the column explicitly (bench/load scripts, future code, manual SQL) silently gets a different trial length than the "authoritative" one.

**Fix:** `seed.ts` should set `trial_ends_at` far-future explicitly for the demo tenant; consider deriving the column default from the same source of truth or documenting the divergence.

### L-3 — LOW — mock vs real `pauseSubscription`/`resumeSubscription` diverge; real pause is non-atomic

**Files:** `backend/src/providers/stripe.ts:252-278` (real), `:344-370` (mock); `backend/src/routes/admin.ts:131-176`

**What's wrong:**
1. The mock's `mockPausedStatus` map is **write-only** — `pauseSubscription` records every pre-pause status as hardcoded `'active'` (not the row's actual status), and `resumeSubscription` ignores the map entirely, restoring `'active'` unconditionally. A `trialing`/`past_due` subscription paused+resumed under mock becomes `'active'`; real Stripe preserves the underlying status (pause is orthogonal via `pause_collection`). Tests asserting suspend/unsuspend round-trips against mock therefore prove less than they appear to.
2. Real `pauseSubscription` updates subscriptions **sequentially with no rollback** — if update #2 of 3 throws, sub #1 stays paused while the admin flow logs "best effort" and continues; the tenant is suspended while partially billed. (Self-heals on unsuspend since `resumeSubscription` clears *all* `pause_collection`s — including ones set outside this flow, e.g. manually in the Stripe dashboard, which unsuspend would then wrongly resume.)
3. Both list with `status: 'all', limit: 100` — a customer with >100 subscriptions silently truncates.

**Fix:** mock should persist the actual pre-pause status (in the DB row or read the map on resume); consider a reconciliation pass or at least surfacing the partial-pause list to the admin caller instead of only `console.error`.

### L-4 — LOW — orphan global reservations inflate the daily total until UTC midnight; no reaper

**File:** `backend/src/services/providerGuard.ts:108-175`; call sites in `keywordCache.ts`, `keywordService.ts`, `serpSnapshots.ts`

**What's wrong:** The reserve → provider-call → commit/release protocol has no timeout or reaper. A process crash between `reserveGlobalProviderBudget` and settle leaves the provisional row in `provider_spend` permanently inflating today's total (self-heals at UTC midnight when the day window rolls). Verified all four call sites single-settle correctly (catch → release + throw; success → commit XOR release on `isMock`), so double-settle (release-after-commit deleting real spend evidence) is not reachable today — but nothing in `commit`/`release` themselves prevents it if a future caller misuses them.

**Fix:** a periodic reaper deleting `provider_spend` rows older than N minutes with no matching cache/commit evidence — or at minimum a `reserved_at`/`settled` flag distinguishing provisional rows from committed spend.

### L-5 — LOW — TTL `NaN` passes the clamp; `make_interval(mins => $6)` then fails at PG type-parse

**File:** `backend/src/metering.ts:293`

**What's wrong:** `Math.max(1, Math.min(1440, Math.round(opts.ttlMinutes ?? 15)))` — if a caller passes `NaN` explicitly, the result stays `NaN` (`Math.min/max` propagate NaN). node-pg sends `"NaN"`, and `make_interval(mins => $6)` needs an integer → `invalid input syntax for type integer: "NaN"` → 500. No current caller can produce this (the sole `ttlMinutes` caller, `crawlJobs.ts:381`, computes `15 + Math.ceil(plan.crawl_pages / 50)`, always finite) — purely a robustness gap for future callers.

**Fix:** `const ttlMins = Number.isFinite(raw) ? Math.max(1, Math.min(1440, Math.round(raw))) : 15;`
