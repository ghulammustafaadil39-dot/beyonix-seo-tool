# Observability (Wave 3, Q-03)

## Logging audit

- **API**: Fastify's built-in **pino** logger (`logger: config.nodeEnv !== 'test'`
  in `backend/src/index.ts`) emits **structured JSON lines** (no pino-pretty
  in the dependency tree — raw JSON). Every request carries a request id:
  generated by `genReqId()` (`randomUUID()`), echoed on every response as
  `x-request-id`, included in every error body as `error.requestId`
  (`errorEnvelope`), and attached to pino log records as `requestId`
  (`requestIdLogLabel`). Verified by test: `tests/wave3/q03-observability.test.ts`
  ("request id … honoured, echoed, present in error bodies").
- **Worker**: still uses `console.log`/`console.error` (unstructured) with the
  `[worker]` prefix. Job ids are included in the message text, but there is
  no JSON logger, no request/tenant propagation into the worker logs, and no
  log correlation id on job payloads. This is an **honest gap**: Wave 3 did
  not retrofit pino into the worker (product-code churn outside the QA slice);
  recommended as a Backend follow-up.
- **Secrets**: never logged (S-07 contract); webhook/API-key material is
  hashed before any logging surface.

## Metrics — GET /metrics

Prometheus text exposition (no new dependency; `backend/src/services/metrics.ts`):

- `bseo_http_requests_total{method,route,status}` — counter (route = matched
  route pattern, so cardinality stays bounded)
- `bseo_http_request_duration_ms` — histogram (buckets 5ms→5s) + `_sum`/`_count`
- `bseo_job_outcomes_total{queue,outcome}` — worker completed/failed
  (wired in `worker.ts` event handlers)
- `bseo_queue_jobs{queue,state}` — live BullMQ counts (waiting/active/delayed/failed)
- `bseo_provider_spend_cents_30d{provider}` — from the `provider_spend` table
- `bseo_dead_letters_pending` — dead-letter backlog gauge
- `bseo_uptime_seconds`

Queue depth and spend are read **live** from BullMQ/Postgres at scrape time,
never cached, so the series can't drift from reality. `/metrics` carries no
tenant ids, emails or payload data.

## Status — GET /status (+ /status page)

JSON: `{ ok, time, services: {db, redis}, queues, deadLettersPending,
providerSpendCents30d, hooks }`. A basic server-rendered `/status` page
(`frontend/app/status/page.tsx`) shows the same data as an accessible
table. Frontend Lead owns UI polish.

## Sentry / OpenTelemetry hooks (env-gated, no hard dependency)

- `SENTRY_DSN`: when set, the operator initializes Sentry around the process
  (e.g. `node -r ./sentry-init.js dist/index.js`). The app does not import
  Sentry — no dependency, no behavior change when unset.
- `OTEL_EXPORTER_OTLP_ENDPOINT`: when set, attach an OTel collector exporter
  (auto-instrumentation of Fastify/pg/ioredis is the recommended route).
- `/status.hooks` reports `{ sentry: bool, otel: bool }` so dashboards can
  show whether the hooks are configured.

## Example alert rules (Prometheus)

```yaml
groups:
  - name: bseo
    rules:
      - alert: BseoApiDown
        expr: up{job="bseo-api"} == 0
        for: 2m
      - alert: BseoQueueBacklog
        expr: sum(bseo_queue_jobs{state="waiting"}) > 500
        for: 10m
        annotations:
          summary: "BullMQ waiting backlog above 500"
      - alert: BseoDeadLettersGrowing
        expr: increase(bseo_dead_letters_pending[30m]) > 10
        annotations:
          summary: "Dead-letter queue growing"
      - alert: BseoProviderSpendSpike
        expr: increase(bseo_provider_spend_cents_30d[1d]) > 5000
        annotations:
          summary: "Provider spend spike > $50/day equivalent"
      - alert: BseoErrorRate
        expr: |
          sum(rate(bseo_http_requests_total{status=~"5.."}[5m]))
          / sum(rate(bseo_http_requests_total[5m])) > 0.01
        for: 5m
        annotations:
          summary: "5xx error rate above 1%"
```

`bseo_uptime_seconds` can back a restart-flap alert if the process manager
exposes restarts.
