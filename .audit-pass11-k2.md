## 2. NEW findings (3 LOW)

### NEW LOW K2-1 — J2-LOW-3 residual: the 60s short-claim can lapse or fail to extend, collapsing the dedupe window and allowing duplicate (LLM-spending) job execution
**Files:** `backend/src/queues.ts:231-248`; `backend/src/services/reportJobs.ts:58-62`.

**What's wrong:** Three paths leave the dedupe window at 60s after a *successful* enqueue:
1. **Swallowed extend failure** (`:244`): `limiterRedis().expire(mapKey, ttlSec).catch(() => {})` — a Redis blip on the extend leaves the claim at 60s. After 60s the same key re-claims and enqueues a duplicate. For `reports/generate` the protection collapses 7 days → 60s.
2. **Claim lapse mid-enqueue** (the sharp one): `Queue.add` (`:243` → `enqueue()` → `getQueue().add`) runs on the BullMQ connection with `maxRetriesPerRequest: null` — it retries *forever* during a Redis stall (the D2-M-1 comment says so explicitly). If the add hangs >60s, the short claim **expires while the enqueue is still in flight**; a concurrent caller claims and also enqueues. The two jobs carry random jobIds (`:242`), so BullMQ's jobId dedupe doesn't see them as duplicates. The pre-fix code (TTL = full window) made this practically impossible; the fix introduced a realistic trigger (any >60s Redis stall during a manual enqueue).
3. **Crash between add and extend**: 60s phantom guarding a live job; after 60s a duplicate enqueue lands while the first job may still be queued/running.

**Impact — worse than "wasted slot":** processors are *correctness*-idempotent at the DB layer (reports: `(site_id, period_start)` ON CONFLICT + winner-only notify; ranks: DB-backed `checkedToday`, `rankJobs.ts:76-84`; backlinks: `ON CONFLICT (site_id, source_url, target_url)`; content: draft-status skip), but the duplicate **does the expensive work first**: `reportProcessor` runs LLM `generateReport` (`reportJobs.ts:58`) *before* the INSERT race (`:60-68`) — the loser pays for a full metered report generation and then skips. So the consequence is real provider spend (one extra LLM report per duplicate), not just a wasted worker slot. Rank-check duplicates are spend-free (all keywords already in `checkedToday` → skipped before any provider call).

**Trigger:** Redis stall >60s coinciding with a manual refresh click (path 2), or a blip on the extend (path 1), or a ms-window crash (path 3). Narrow, hence LOW.

**Fix direction:** make the extend conditional-and-atomic (Lua: extend only if the value is still ours), and/or refresh the short claim while `enqueue` is in flight, or size the short TTL to cover enqueue latency (e.g. 5 min) as a compromise between phantom-duration and lapse risk.

**Duplicate check:** grepped all `.audit-pass{1..10}-*.md` — J2-LOW-3 filed the *phantom-claim-on-crash* (the defect this fix addressed); no pass discusses the extend-failure or lapse-mid-enqueue residual of the fix itself. **NEW.**

### NEW LOW K2-2 — scheduler tick has no per-site error isolation: a mid-tick enqueue failure orphans the rest of the tick with no resume
**Files:** `backend/src/scheduler.ts:46-78` (`enqueueForVerifiedSites`, `for (const s of r.rows) { await enqueue(...) }` at `:69-77`).

**What's wrong:** The per-site `enqueue` calls run in a bare sequential loop — no per-site try/catch. If `Queue.add` throws mid-loop (Redis flap: the leader lock and the sites query succeeded, then Redis stutters), the tick aborts; every site after the failure point gets **no job for that cycle**, and nothing records how far the tick got. The cron wrapper (`startScheduler`, `:252-260`) only logs the error. The next tick is a week later with a *new* idempotency key — the missed sites simply lose a cycle (weekly crawl, rank-check, report, geo, backlink sweep). BullMQ jobId dedupe would make a manual re-tick safe, but no re-tick mechanism exists.

**Impact:** LOW — missed scheduled work for a subset of sites during infra trouble; self-heals next cycle; no money/data corruption (the tick is leader-gated and per-key idempotent, just not atomic — partial application is silent).

**Fix direction:** per-site try/catch collecting failures with a summary log (and a metric), so one bad site/Redis moment doesn't cancel the rest of the tick.

**Duplicate check:** grepped all `.audit-pass{1..10}-*.md` for tick-abort/partway/per-site failure — zero hits. Pre-existing, never reported. **NEW.**

### NEW LOW K2-3 — J2-LOW-2 residual: session-scoped release never matches a `'creating'` claim with NULL `stripe_session_id`
**Files:** `backend/src/providers/stripe.ts:619-622`; `backend/src/routes/billing.ts:382-385`, `:430-433`.

**What's wrong:** The claim INSERT (`billing.ts:388-391`) sets no `stripe_session_id` (NULL); it's populated by the `'open'` UPDATE (`:430-433`), which is `.catch(() => undefined)`-swallowed — and a process crash between `createCheckoutSession` and the UPDATE leaves the same state: a `'creating'` claim with NULL session id **for a live, payable Stripe session**. When that session's `checkout.session.completed` arrives, the scoped DELETE (`stripe_session_id = $2`, `stripe.ts:621`) compares NULL ≠ `'cs_…'` → no release. The claim then sits in `'creating'` until the 10-min steal: a tenant who just paid and immediately starts another checkout (second workspace, mistaken cancel+retry) gets 409 `CHECKOUT_IN_PROGRESS` for up to 10 minutes. The pre-fix tenant-wide DELETE would have cleared it — this is a direct residual of the J2-LOW-2 fix.

**Why not just widen the DELETE:** the J2-LOW-2 invariant must hold — a newer stealer's `'creating'` row (also NULL session id) must NOT be wiped by an older session's completion event. So the fix direction is on the *write* side, not the release side: don't swallow the `'open'` UPDATE error (log + retry), shrinking the NULL-session state to true crashes, with the 10-min steal as the existing bound.

**Impact:** LOW — needs swallowed-UPDATE-failure/crash + completed payment + re-checkout within 10 min; UX confusion only, no money impact; self-heals via the steal.

**Duplicate check:** J2's pass#10 analysis covered the orphaned-`'creating'`-claim crash case only for *unpayable* sessions ("its URL was never delivered, so it can never be paid") — the payable-session + NULL-session-id + scoped-release-miss combination is unreported in passes 1–10. **NEW.**
