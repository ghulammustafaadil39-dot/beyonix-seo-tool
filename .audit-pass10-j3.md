## 2. NEW findings

### J3-M-1 — MEDIUM — `?success=1` notice promises an active plan that the fail-closed `incomplete` state contradicts
**Files:** `frontend/app/dashboard/billing/page.tsx:191-192`, `:288`, `:420-428`

**What's wrong.** The billing page shows the success notice purely on the query param, with no check of actual subscription state:

```tsx
if (params.get('success') === '1') {
  setNotice({ kind: 'success', text: 'Payment successful — your plan is now active.' });
}
```

But on the **real Stripe path**, `checkout.session.completed` carries the subscription as an unexpanded string id, so the backend **deliberately fail-closes the local row to `'incomplete'`** (`backend/src/providers/stripe.ts:613-627`, G5-M#1) — and a genuinely failed first payment keeps it `incomplete` for up to 23h of auto-retry (E4-H-2). Meanwhile `BILLABLE_SUBSCRIPTION_STATUSES = ['active','trialing','past_due']` **excludes** `incomplete`: `requireSubscription` flips the tenant `read_only` — the user has no paid access.

So a user landing on `?success=1` with an `incomplete` subscription is told **"Payment successful — your plan is now active"** while payment did *not* succeed and the plan is *not* active. Compounding it, frontend `hasSubscription` (`:288`) counts `incomplete` as subscribed, so the plan card renders a **"Current plan"** badge, the direct **Subscribe CTAs are hidden** (`:420-428`), and there is **no `incomplete` explainer banner** — unlike `past_due`, which gets a dedicated "Your last payment failed… update your payment method in the portal" alert (`:357-361`). The locked-out user is given no surfaced recovery path (pay the open invoice via the portal); they must discover it themselves.

**Trigger (reachable, not theoretical).**
1. Customer completes Stripe Checkout; first payment fails asynchronously (declined off-session / abandoned SCA variant) — or simply the status-carrying `customer.subscription.created/updated` webhooks haven't been processed yet when the browser lands on `success_url`.
2. Local `subscriptions.status = 'incomplete'` (fail-closed by design) → redirect to `/dashboard/billing?success=1`.
3. UI asserts payment success + active plan + "Current plan"; backend enforces read-only. Contradictory state persists until the subscription flips to `active`/`trialing` (happy path: seconds; failed payment: up to 23h, then `incomplete_expired`).

**Impact.** User-facing billing misrepresentation: users believe they paid and are subscribed when they are locked out; "paid but no access" support load; failed payers may never complete payment because the UI told them it succeeded. No funds are mis-moved and no auth boundary is bypassed (the backend correctly fail-closes) — hence MEDIUM, not HIGH.

**Suggested fix (frontend, no backend change needed):** gate the success notice on the fetched subscription — e.g. only show "plan is now active" when `sub.status` is `active`/`trialing`; when it is `incomplete`, show an amber "Your payment is still processing / didn't complete — complete it in the billing portal to activate your plan" banner (mirroring the `past_due` pattern), and don't hide the recovery CTA behind `hasSubscription`.

**Duplicate check:** grepped all 35 `.audit-pass{1..9}-*.md` files for `now active`, `success=1`, `Payment successful` — **zero hits**. Prior `incomplete` discussion (pass#2–9) is entirely backend-side (webhook clobbering, billable sets, dunning, E4-H-2) and never touches this frontend copy. **NEW.**

## 3. Hunt results — clean areas (spot-verified, no findings)

- **XSS:** zero `dangerouslySetInnerHTML` in `app/`, `components/`, `lib/`. `QrCode.tsx` renders the QR as React SVG attributes (no HTML injection surface). All `target="_blank"` anchors (`ReportsV2Panel`, `BacklinksTab`, `ContentV2Panel`, billing invoice links) carry `rel="noreferrer"` (implies noopener).
- **Token leakage:** no tokens in `localStorage` (only the cookie-banner consent key). Team-invite token is scrubbed from the URL immediately and kept in `sessionStorage` only as a login-redirect fallback, cleared on both success and failure (`accept/page.tsx`). The OAuth/TOTP challenge token is read once into component state and stripped from the URL via `router.replace` (`login/page.tsx:215-251`). Impersonation JWT never touches JS — set as httpOnly cookie by the same-origin proxy route (`app/api/admin/impersonate/route.ts`), response body carries no token. API keys and webhook signing secrets are shown exactly once with "copy it now, it won't be shown again" copy. Zero `console.log/warn/error` calls that could leak secrets.
- **Open redirects:** login `?next=` is restricted to relative paths (`/^\/[^/]/`, `login/page.tsx:30`); signup's post-signup `dest` is allowlisted to plan/billing enum values (`signup/page.tsx:23-30`); GA4 OAuth `window.location.href` target comes from the API (`sites/[id]/page.tsx:112-115`).
- **PII:** nothing beyond the expected (own email in team member lists, invite email input). Forgot-password is enumeration-safe (backend always returns success; UI confirms generically).
- **React 19 / Next 15:** every `useSearchParams` consumer is under a `<Suspense>` boundary (login, reset-password); no prerender-breaking patterns spotted. Account-security flows (2FA setup/verify/disable, backup codes, password change with all-session revocation + re-login redirect) match the hardened backend endpoints.
- **Billing copy otherwise:** pricing page's "Prices are illustrative; Stripe checkout shows the final price" and "14-day free trial — no credit card required" match the server-side trial model (`signupTrialDays()` default 14, tenant-level trial; plan-level `trial_days: 0` means subscribe = charged immediately, consistent with "subscribe below to keep full access"). Cancel flow copy is honest (takes effect at period end, data stays exportable).

**Observation (not filed):** the "14-day" figure is hardcoded in pricing/billing copy while the length is env-overridable (`SIGNUP_TRIAL_DAYS`, `backend/src/services/billing.ts:178-183`) — copy drifts if ops changes the knob. Prior passes already covered the knob's documentation gap from the backend side; the default matches the copy, so this stays an observation, not a finding.
