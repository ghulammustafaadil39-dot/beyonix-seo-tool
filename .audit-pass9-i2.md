## 2. NEW findings

### NEW LOW #1 — `reportProcessor`: the ON CONFLICT loser still sends the weekly email + Telegram (D1-L-1's "idempotent" claim is true for the row, false for the side effects)

**Files:** `backend/src/services/reportJobs.ts:48-102`

**What's wrong:** The processor does a non-atomic `SELECT existing` check (`:48-54`), then `generateReport` (LLM), then `INSERT … ON CONFLICT (site_id, period_start) DO NOTHING` (`:62-68`). The D1-L-8 comment (`:59-60`) claims "ON CONFLICT makes concurrent jobs idempotent — the loser gets the winner's row instead of a raw 23505." The row part is true; but execution then falls through to the notify block (`:84-102`) **unconditionally** — the loser, which generated its own summary and fetched the winner's id, also calls `notify.sendEmail` ("Weekly SEO report for …") and `notify.sendTelegram`. The early `existing` SELECT only closes the *sequential* case (a report committed before this attempt started), not the concurrent one.

**Concrete triggers:**
1. **BullMQ retry after `withJobTimeout`:** the report queue's timeout is 15 min (`queues.ts:61`). Attempt 1 times out mid-`generateReport` while still running; attempt 2 starts, passes the `existing` SELECT (attempt 1 hasn't inserted yet), both generate, both INSERT (one wins), **both notify** → two identical weekly-report emails.
2. **Scheduler job vs. manual generate:** the Monday 08:00 UTC `weekly-reports` tick uses raw `enqueue` (dedupe arbiter = BullMQ `jobId` = `report:${site}:${week}`), while `POST /sites/:id/reports/generate` (`routes/reports.ts:77-84`) uses `enqueueDeduped` (dedupe arbiter = a *separate* Redis claim `dedup:report:${site}:${weekStart()}`, 7-day TTL). The two dedupe domains never see each other, so a user clicking "Generate" on Monday morning while the scheduled job is still generating produces two live `WEEKLY_REPORT` jobs for the same site+week → both pass the SELECT → both notify.

**Impact:** LOW — duplicate customer-facing "Weekly SEO report" email + Telegram per incident (same class as the H1-L-2/H2-L-1 dunning dupes). No money movement: each attempt's LLM spend goes through `generateMetered` → `withUsageReservation`, so the double generation stays within the tenant's atomic plan limit. No data corruption (one report row).

**Fix:** only notify when this attempt actually inserted the row (`inserted.rowCount === 1`); on the ON CONFLICT path return `{ reportId: winner }` without notifying. (Or claim-first: INSERT the report row with a `generating` marker before `generateReport`.)

**Duplicate check:** grepped all `.audit-pass{1..8}-*.md` for `D1-L-8`, `reportProcessor`, `loser`, `duplicate.*report`. D1-L-8 (pass#4) filed only the raw-23505 crash; the pass#4 fix (ON CONFLICT) addressed the crash, and no pass since has examined the notify path that follows it. I3/I4 (pass#9) are frontend/docs scope. **NEW.**

### NEW LOW #2 — PageSpeed daily quota is check-then-act: concurrent crawls can overshoot the free-tier quota

**Files:** `backend/src/services/pagespeed.ts:95-108` (`getPageSpeedMetrics`)

**What's wrong:** The quota gate is `getQuotaCount` (read) → `quotaAllows(used, quota)` → `fetchPageSpeed` (up to 90 s of network I/O) → `bumpQuota` (write). Two code smells compound it: (a) the read-check and the increment are separate statements with a network round-trip between them — N concurrent `getPageSpeedMetrics` calls (the Sunday 02:00 UTC weekly-crawl tick fans out across 6 heavy worker slots) can all read `used < quota` and all fire the Google API before any of them bumps the counter; (b) `bumpQuota` runs unconditionally *after* the fetch, even when the fetch failed/returned null, so 429s and timeouts also burn quota.

**Trigger:** weekly-crawl tick with ≥2 uncached sites crawled concurrently near the daily quota (default `PAGESPEED_DAILY_QUOTA=25`). All pass `quotaAllows`, all fetch, all bump → count lands above quota.

**Impact:** LOW — Google 429s on the excess; `fetchPageSpeed` returns null and the crawl degrades gracefully (no PageSpeed issues reported for those audits — silent feature degradation, no error surfaced). No money (free tier), no data loss, no privilege issue. The quota is a soft cost-control, not a billing boundary, so this stays LOW.

**Fix:** atomic claim — `INSERT … ON CONFLICT (quota_key, day) DO UPDATE SET count = count + 1 … RETURNING count` and compare the *post-increment* value against the quota (overshoot impossible; at most the quota is reached exactly), or gate the fetch on a single conditional UPDATE (`… WHERE count < quota` → `rowCount=1` means "slot claimed").

**Duplicate check:** grepped all `.audit-pass{1..8}-*.md` for `quotaAllows`, `daily_quotas`, quota races. Prior pagespeed mentions (pass#7-g1, pass#8-h1) are SSRF-only (`pagespeed.ts:61` raw fetch). No pass filed the quota check-then-act. **NEW.**
