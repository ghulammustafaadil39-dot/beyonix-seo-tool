## NEW LOW

### H3-L-1 — LOW — Signup page advertises an 8-char password minimum; backend enforces 12
- **File:** `frontend/app/signup/page.tsx:84-88` (`minLength={8}`, hint "At least 8 characters.")
- **Trigger:** sign up with a 9-character password → passes client validation → backend `POST /api/v1/auth/signup` runs `validatePassword()` (`backend/src/services/passwordPolicy.ts:9`, `MIN_PASSWORD_LENGTH = 12`) and rejects with "Password must be at least 12 characters". Every other password surface already requires 12 (change form `SecuritySection.tsx:442`, reset page `reset-password/page.tsx:92`).
- **Impact:** UX-only — the backend enforces the stronger policy, so this is not a security hole; the user just gets a confusing round-trip rejection. Misleading hint text.
- **Fix:** change signup to `minLength={12}` and hint "At least 12 characters." to match the backend policy and the other forms.
- **Duplicate check:** no prior pass mentions signup-vs-policy minimum mismatch (pass5-e5 mentions `passwordPolicy.ts` only in a secret-scan context). **NEW.**

### H3-L-2 — LOW — Download URL builders interpolate IDs without `encodeURIComponent`
- **Files:** `frontend/lib/api.ts:563` (`contentApi.exportUrl`), `:1173` (`auditsApi.exportUrl`), `:1240` (`keywordsApi.exportUrl`), `:1411` (`geoV2Api.llmsTxtUrl`), `:1465` (`backlinksV2Api.disavowUrl`) — all do `` `${BASE_URL}/api/v1/.../${siteId}/...` `` raw.
- **What's wrong:** the one sibling that was hardened — `jobsApi.streamUrl` (`:1621-1622`) — uses `encodeURIComponent(siteId)` with an explicit "path-injection hygiene" comment, so the codebase already decided this matters; the five builders above were missed. IDs here come from route params (`[id]`) and backend UUIDs.
- **Impact:** minimal — self-only (a user can only reshape their own requests; backend must validate UUIDs anyway; React escapes attribute values so no XSS). Defense-in-depth inconsistency, not an exploitable finding on its own.
- **Fix:** wrap the interpolated IDs in `encodeURIComponent(...)` like `streamUrl` does.
- **Duplicate check:** prior passes mention `encodeURIComponent` only for the login `?next=` bounce and cookie writes; no pass filed the un-encoded export/disavow builders. **NEW.**

## Verified clean (no finding)

### QR encoder (`lib/qr.ts`) — independently validated, CORRECT
The hand-rolled byte-mode/ECC-M encoder was verified against two independent references plus published test vectors (compiled the repo file to /tmp; repo untouched):
- **Data encoding:** hand-verified bit layout for "HELLO" and 120-char input; segment bytes identical to `segno` reference output.
- **Reed–Solomon ECC:** matches the independent `reedsolo` library byte-for-byte on identical input, and the generator polynomial values match Thonky's published degree-10 generator (`[1, α^251, α^67, α^46, α^61, α^118, α^70, α^64, α^94, α^32, α^45]`).
- **Format info:** 0 cell diffs vs `segno` across all 8 masks (v10 test).
- **Version info (v7+):** 0 cell diffs vs `segno`; bit order matches Nayuki's reference implementation logic.
- **Masks / placement zigzag / finder / timing / alignment / dark module:** all match `segno`.
- Two apparent "failures" during verification were harness bugs on my side, not encoder bugs: (a) `segno`'s `boost_error=True` default silently upgrades M→H — disabled for comparison; (b) my Python zigzag replication mishandled the `right===6 → 5` timing-column skip (`for` continues with `right-=2` → pairs `(3,2)`, `(1,0)`, not `(4,3)`, `(2,1)`). After fixing the harness, the only residual delta is `segno`'s own spec deviation (it appends a spurious `0x00` pad byte when the stream is already byte-aligned — ours follows the spec: terminator + EC/11 pads). Both decode fine.
- **Operational:** `encodeQr` throws past v10-M capacity (~213 bytes); `SecuritySection.startSetup` pre-validates with `encodeQr()` and falls back to manual secret entry — graceful. Typical otpauth URLs (~90 chars) fit comfortably.

### Password change / forgot / reset
- Change: client checks (match, ≥12 chars, differs from current) → `POST /api/v1/auth/password/change` → redirects to `/login?password-changed=1` (backend revokes all sessions; login shows the notice). Correct endpoint, proper error mapping (`INVALID_CREDENTIALS` → "Current password is incorrect").
- Forgot: backend always returns success; UI shows the identical confirmation regardless — **no enumeration**. Errors shown only for network/server failure.
- Reset: token read once from `?token=` into a POST body (never logged/stored); missing-token and `INVALID_TOKEN` states handled; 12-char policy enforced client-side matching backend.
- Login has the "Forgot password?" link (G3-M-1 fix verified present, `login/page.tsx` label row).

### Login / session hygiene
- `totpToken` lives in component state only; OAuth-callback variant (`?totp=1&token=`) is read once on mount and immediately scrubbed via `router.replace` — never lingers in history/shareable URLs.
- `?next=` redirect validated against `/^\/[^/]/` (open-redirect guard intact).
- Session JWT is httpOnly-cookie-only; no token in response bodies, `localStorage`, or URLs. `localStorage` holds only the cookie-banner flag; `sessionStorage` holds only the single-use invite token (scrubbed from URL via `history.replaceState`, removed on success AND failure).
- API-key creation shows the raw key once, in state only.
