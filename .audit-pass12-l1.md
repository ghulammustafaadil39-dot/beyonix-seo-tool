### Fix 2 — K2-1: `enqueueDeduped` extend is now Lua compare-and-exists ✅ VERIFIED HOLDING
- `backend/src/queues.ts:251-256`: `EVAL "if redis.call('exists',KEYS[1])==1 then return redis.call('expire',KEYS[1],ARGV[1]) else return 0 end"` — atomic; `.catch(() => 0)` converts an eval failure into the warn path instead of a throw (the enqueue already succeeded — failing the request would be wrong).
- **Adversarial Q — extend racing a re-taken claim:** the Lua checks `exists`, not ownership (claim value is the constant `'1'`, no token). If the 60s claim lapsed mid-enqueue and claimant B re-took the key, our extend lengthens *B's* claim to the full window. Consequence analysis: B already enqueued, so extending B's dedupe window is semantically harmless (it protects B's job); the duplicate enqueue already happened and no additional harm flows from the extend. Not a bypass of the fix's intent.
- **Adversarial Q — crash between `enqueue` resolve and the Lua eval:** leaves a 60s phantom guarding a live job; a duplicate enqueue can land after 60s while the first job runs. The window is now a single `await` (vs the pre-fix 7-day phantom); processors are DB-idempotent (the loser's LLM spend is the residual cost, per K2's analysis). Sub-finding; recorded as observation, not filed — no inflation.
- The swallowed-`expire`-failure path (K2-1's sharp case) is closed: eval failure → `extended = 0` → warn logged, no silent 60s collapse. ✅

### Fix 4 — K2-3: `checkout.session.completed` falls back to deleting `'creating'`-NULL claims ✅ VERIFIED HOLDING
- `backend/src/providers/stripe.ts:619-640`: scoped DELETE captures `rowCount` (`.catch(() => ({rowCount: 0}))` — a DB error degrades to "no rows released" and still attempts the fallback, fail-safe direction); fallback fires only when `rowCount === 0 && completedSessionId` is non-null, deleting `status='creating'` rows for the tenant.
- **Adversarial Q — redelivered `completed` wiping a newer claim:** the event-id ledger INSERT (`stripe.ts:524-544`) runs **before** the claim DELETE; a redelivery with the same event id hits the conflict, sees `processed_at` set, and returns `{deduplicated: true}` without ever reaching the fallback. The fallback is unreachable on redelivery.
- **Adversarial Q — fallback deleting a *newer* in-flight `'creating'` claim (S2) on a *crashed-first-attempt* retry of S1's `completed`:** reachable only if (a) S1's first attempt crashed between the scoped DELETE and `markProcessed` (E4-M-2 reprocessing path), (b) the tenant started checkout S2 before Stripe's retry, and (c) S2's claim is still `'creating'` at retry time. Blast radius even then: S2's route continues (the `'open'` UPDATE is `.catch`-swallowed, URL still delivered, payment still works, `completed` still activates); the only loss is the claim row, i.e. a transient gap in the double-checkout 409 guard. Four-condition coincidence for a bounded UX-guard gap — observation, not filed.
- The fix comment's safety claim ("a concurrent in-flight 'creating' claim can't coexist with a completed session for a different checkout") is slightly overconfident given the crash-retry interleaving above, but the residual is as narrow as analyzed. Regression test (`w4-pass11-fixes.test.ts:105-134`) genuinely exercises the fallback path. ✅

### L1-1 — LOW — `rank-checks` tick's per-site loop has no error isolation: the K2-2 fix missed this schedule
**Files:** `backend/src/scheduler.ts:128-140` (the `rank-checks` `run`), contrast the fixed `enqueueForVerifiedSites` at `:70-79`.

**What's wrong:** the pass#11 K2-2 fix ("scheduler isolation", commit `566065e`) wrapped the per-site loop in `enqueueForVerifiedSites` in try/catch — but the `rank-checks` schedule has its **own** per-row loop that was not touched:

```ts
for (const row of r.rows) {
  const freq = getPlan(row.plan_id).rankcheck_freq;
  if (freq === 'daily' || (freq === 'weekly' && isSunday)) {
    await enqueue(QUEUES.rankCheck, Jobs.RANK_CHECK,
      { siteId: row.site_id, tenantId: row.tenant_id },
      { idempotencyKey: `rank:${row.site_id}:${today}`, rateLimit: false });
  }
}
```

If `enqueue` throws mid-loop (BullMQ `add` failure — Redis flap with a non-retryable error, queue closed during shutdown; note the scheduler passes `rateLimit: false`, so the 429 path in `queues.ts:147-157` does not apply here), the `run` rejects, `startScheduler`'s `.catch` (`scheduler.ts:257-260`) merely logs `[scheduler] job rank-checks failed`, and **every site after the failure point misses that day's rank check with no resume**. The next tick is 24h later with a new date-keyed idempotency key — the missed sites simply lose a day. (A Redis *stall* rather than a hard error hangs the retry-forever `add` mid-loop instead of throwing — same net effect for the remaining rows.)

**Impact:** LOW — missed daily rank checks for a subset of sites during infra trouble; self-heals the next day; no money movement, no data corruption, no privilege vector. A manual re-tick would be safe (BullMQ `jobId` dedupe on `rank:${site}:${today}`), but no re-tick mechanism exists. This is the exact defect class K2-2 was filed for, on the one schedule the fix didn't cover.

**Fix direction:** same as K2-2 — per-row try/catch collecting failures with a summary log (and ideally a metric), in the `rank-checks` loop. (The other schedules either funnel through the fixed `enqueueForVerifiedSites` or are single claim-then-work service calls — `processDigests`, `processWebhookRetries`, `processBillingGrace` — verified atomic by K2; `scheduler.ts:282`'s `t.stop()` loop cannot throw meaningfully.)

**Duplicate check:** grepped all `.audit-pass{1..11}-*.md` plus fellow pass#12 reports. K2-2 (pass#11) filed the identical defect **only** for `enqueueForVerifiedSites` (`scheduler.ts:46-78`); the fix commit's diff confirms the `rank-checks` loop was untouched. No prior report mentions per-site isolation (or its absence) for the `rank-checks` loop specifically. **NEW** — same class, different unfixed instance, not a duplicate.
