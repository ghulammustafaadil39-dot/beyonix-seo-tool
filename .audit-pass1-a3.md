## Findings

### H-1 — HIGH — Admin impersonation writes the session JWT to a JS-readable cookie
- **File:** `frontend/app/admin/page.tsx:130`
- **What:** After `adminApi.impersonate()` returns `{ token }`, the page runs
  `document.cookie = \`bseo_token=${encodeURIComponent(res.token)}; path=/; max-age=${res.expiresInSec}; SameSite=Lax\``.
- **Why it's wrong:** The entire auth design (S-06) rests on `bseo_token`
  being a host-only **httpOnly** cookie so XSS can never steal the session.
  Setting it via `document.cookie` creates a cookie entry that is readable
  by any JavaScript on the page, with no `Secure` flag. The impersonation
  token is a live, 5-minute tenant session. Any XSS on any page during that
  window (or a malicious browser extension) can read `document.cookie` and
  exfiltrate the full session. It also coexists/conflicts with the real
  httpOnly cookie of the same name, so logout/cleanup behavior is murky.
- **Trigger:** Admin opens a tenant → "Impersonate" → confirm. From that
  moment until the cookie expires or is overwritten, `document.cookie`
  contains a valid session JWT in cleartext.
- **Fix:** Never let the token touch JS. Have the backend expose
  `POST /api/v1/admin/impersonate` as a redirect/204 that issues the
  impersonation session via `Set-Cookie: bseo_token=...; HttpOnly; Secure;
  SameSite=Lax` itself (the frontend already goes through the same-origin
  proxy, so the cookie scopes correctly). Alternatively keep the JSON
  response but add a `?set-cookie` backend step the frontend navigates to.

### M-1 — MEDIUM — Rankings UI shows mock SERP data with no mock label
- **File:** `frontend/components/tabs/RankingsTab.tsx` (fetch at line 47
  via `ranksApi.latest`); type at `frontend/lib/api.ts`
  (`ranksApi.latest` returns `api<{ data: RankEntry[] }>`).
- **What:** The backend honestly returns `dataSource: 'mock' | 'real'` on
  `GET /api/v1/sites/:id/ranks` (`backend/src/routes/ranks.ts:18-19,81`),
  but the frontend type drops the field and the tab renders positions with
  no indication of provenance.
- **Trigger:** Deploy without DataForSEO keys (the documented default) →
  deterministic seeded mock positions are presented as the site's real
  rank tracking. This directly contradicts the README's "labeled
  `dataSource: 'mock'`" claim for this surface.
- **Fix:** Thread `dataSource` through the type and render a badge
  ("Mock data — add DataForSEO keys for live ranks") when `'mock'`.

### M-2 — MEDIUM — Keyword research volume/difficulty mock not labeled in KeywordsTab
- **File:** `frontend/lib/api.ts` (`keywordsV2Api.expand` returns
  `api<{ data: Keyword[]; total: number }>`); `frontend/components/tabs/KeywordsTab.tsx`
  (no mock labeling anywhere in the file).
- **What:** Backend returns `dataSource: 'mock'|'real'` on research/expand/

### L-1 — LOW — Settings inputs lack programmatic label association
- **File:** `frontend/app/dashboard/settings/page.tsx:75,87`

- **What:** `<label className="bx-label">Notification email</label>` is a
  sibling of the `<input>`, with no `htmlFor`/`id` pairing and no

- **Trigger:** Screen-reader user tabs to "Notification email" field —
  announced without its label.
- **Fix:** Add matching `htmlFor`/`id` (or wrap the input in the label).

### L-3 — LOW — Invite debug token can render in the UI on a production deploy without SMTP
- **Files:** `frontend/app/dashboard/team/page.tsx:90-96`;
  `backend/src/routes/account.ts:204-210` (`inviteDebugFields`).
- **What:** The frontend renders the raw invite accept link (with token)
  whenever `res.token` is present. The backend includes the token whenever
  mail is in mock mode — which includes `NODE_ENV=production` with no SMTP
  configured (`!hasSmtp()` → mock). So a production deploy that forgot
  `SMTP_*` will display single-use invite tokens in the inviting admin's
  browser (page HTML → possible caching/logging of the token URL).
- **Why low:** The token is single-use, bound to the invited email, and only
  shown to the admin who created the invite; not a session credential.
- **Fix:** Gate `inviteDebugFields` on non-production as well, or add a
  loud UI warning when the link is shown outside dev.

### L-4 — LOW — Invite token held in `sessionStorage`
- **File:** `frontend/app/dashboard/team/accept/page.tsx:31-33`.
- **What:** The one-time invite token is kept in `sessionStorage` so the
  flow survives the login redirect. This is the standard pattern and the
  token is single-use and email-bound, but it is exfiltratable by XSS
  (unlike the httpOnly session cookie used everywhere else).
- **Fix:** Acceptable as-is; noted for the record. A stricter design would
  complete the accept server-side before the login bounce.
