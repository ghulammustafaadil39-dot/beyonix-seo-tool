## HIGH

### H-1 — Grace-expiry downgrade marks the local subscription `canceled` while Stripe keeps it `past_due` → double-subscription + broken recovery
**Files:** `backend/src/services/billing.ts:128-146` (`downgradeTenant`), called by
`processBillingGrace` (`billing.ts:155-167`, daily scheduler)
**What's wrong:** When the 3-day grace expires, `downgradeTenant` sets the local
`subscriptions.status='canceled'` and `tenants.plan_id='starter'` — but never touches the
Stripe subscription, which stays `past_due` with Smart Retries running for weeks. The pass#3
H-1/H-2 fix closed this hole for delete/erase but not for the dunning path. Consequences:
1. **Double billing:** `POST /billing/checkout` blocks only when local status ∈
   `['active','trialing','past_due']` (`routes/billing.ts:56,275`). After the downgrade the
   local status is `'canceled'` → the check passes → the user starts a *second* Stripe
   subscription while the first is still live and retrying. Two subscriptions, one tenant.
2. **Recovery miss:** `invoice.paid` clears past-due with
   `UPDATE subscriptions SET status='active' … WHERE tenant_id=$1 AND status='past_due'`
   (`providers/stripe.ts:685-689`) — matches zero rows because the row is `'canceled'`.
   A customer whose retry succeeds pays full price while the product still shows Starter
   until/unless `customer.subscription.updated` arrives to repair it.
**Concrete trigger:** card fails → `subscription.updated(past_due)` → grace 3d → scheduler
`processBillingGrace` downgrades locally → user sees Starter, clicks upgrade → new
checkout succeeds → two live Stripe subscriptions; or Stripe retry succeeds → charged,
product still shows Starter/canceled.
**Fix:** on grace-expiry downgrade, either cancel the Stripe subscription too (same
`cancelSubscription` primitive as the delete/erase fix — kills dunning but ends the
mismatch), or keep the local status truthful (`past_due`, grace cleared) so the checkout
block and the `invoice.paid` recovery both keep working.

### H-2 — Pass#3 C2-M-1 fix makes every first-attempt crawl failure terminal; BullMQ retries are silently dead
**Files:** `backend/src/services/crawlJobs.ts:239-250` (`markFailed`), `:319-335`
(conditional claim), `:521-526` (catch path)
**What's wrong:** `markFailed` unconditionally sets `status='failed'` on ANY processor
throw, then rethrows. The pass#3 fix made the retry's row-claim conditional
(`WHERE … AND status='queued'`). So BullMQ attempt 2 always finds 0 rows and throws
`UnrecoverableError` ("no longer queued — dropping job"). The configured
`attempts: 3` + backoff (`queues.ts:75-76`) is now dead code for every route-created
audit: a transient failure (robots fetch blip, provider timeout) that would have
succeeded on retry now terminally fails the audit and forces the user to re-trigger
manually. The DLQ also fills with misleading "no longer queued" entries.
**Concrete trigger:** audit job fails once on a transient network error → user sees
"failed" with no automatic retry; DLQ records a bogus drop reason.
**Fix:** make the failure path attempt-aware — the processor can read
`job.attemptsMade`: on non-final attempts reset the row to `'queued'` (so the retry's
conditional claim succeeds); only on the final attempt mark `'failed'` + DLQ. Reaped
rows are still protected because the reaper sets `'failed'`, which the retry claim
rejects.

## MEDIUM

### M-1 — `POST /auth/logout` revokes ALL sessions; identical to `/auth/logout-everywhere`
**File:** `backend/src/routes/auth.ts:528-547`
**What's wrong:** The comment says "Revokes the jti session and bumps token_version",
but the code calls `revokeAllSessions(payload.uid)` with no `exceptJti` — revoking every
session and bumping `token_version`. Logging out on one device kills all other devices.
A dedicated `/auth/logout-everywhere` (`auth.ts:959-964`) does exactly the same thing,
so the two endpoints are functionally identical and the per-session revoke UI
(`GET/DELETE /auth/sessions/:id`) is undermined.
**Concrete trigger:** user logs out on their phone → their desktop session dies too
(token_version bump invalidates the JWT even though the session row was the target).
**Fix:** revoke only the current session: `revokeSession(uid, sessionId)` using the
token's `jti` (already in the payload, cf. `req.tenant.jti` at `auth.ts:927`), without
bumping `token_version`.

### M-2 — Soft-deleted domain can never be re-added: unique index + no deleted-site listing = dead end
**Files:** `backend/src/routes/sites.ts:118-140` (`POST /sites`), `migrations/001_init.sql:39`
**What's wrong:** `UNIQUE (tenant_id, domain)` is not partial, so re-adding a soft-deleted
domain hits `ON CONFLICT … DO NOTHING` → 409 `SITE_EXISTS` ("This domain is already
added"). `GET /sites` filters `deleted_at IS NULL`, and no endpoint lists soft-deleted
sites — but `POST /sites/:id/restore` needs the deleted site's id. The tenant can
neither re-add nor discover-and-restore their domain.
**Concrete trigger:** delete site `example.com` → realize it was a mistake →
`POST /sites {domain:"example.com"}` → 409 forever; the restore URL is unknowable via the API.
**Fix:** make the unique index partial (`WHERE deleted_at IS NULL`) and have `POST /sites`
restore-instead-of-conflict when a soft-deleted row exists, or add
`GET /sites?include_deleted=true`.

### M-3 — `rescoreToxicLinks` is N+1: one UPDATE per backlink after every CSV upload / rescore
**File:** `backend/src/services/toxicLinks.ts:106-140`
**What's wrong:** the loop does one `UPDATE backlinks … WHERE id=$1` per active link.
A 5,000-row CSV upload (`routes/backlinks.ts:169` caps at `MAX_CSV_ROWS=5000`) therefore
fires 5,000 sequential round-trips inside a request handler — the same N+1 class as the
A1-L1/C1-M-8 fixes. `findLinkOpportunities` has the same shape (up to ~150 sequential
upserts, `services/linkOpportunities.ts:88-96`).
**Concrete trigger:** upload a 5k-link GSC export → `/backlinks/upload` runs batched
inserts and then 5k sequential UPDATEs; likely to blow past the route timeout while the
client sees a 504 (work already done server-side).
**Fix:** batch the score writes with `unnest()` arrays (single statement), or one
`UPDATE … FROM (VALUES …)` per chunk, mirroring the batched inserts.

### M-4 — Crawl budget reservation TTL (15 min) is shorter than realistic crawl durations
**Files:** `backend/src/metering.ts` (reservation), `migrations/011_metering.sql:17`
(`expires_at DEFAULT now() + interval '15 minutes'`), `backend/src/services/crawlJobs.ts:360-473`
**What's wrong:** the C1-M-5 reserve→commit fix holds the budget only while the
reservation is unexpired. A 500–2000-page crawl routinely exceeds 15 minutes; at expiry
the hold is silently released (`getUsage` stops counting it), `commitUsage` throws
`RESERVATION_EXPIRED`, and the fallback `recordUsage` re-adds the spend — but between
expiry and completion a concurrent audit can reserve the same budget. The atomic
guarantee degrades to check-then-act for long crawls (overshoot up to one extra
`plan.crawl_pages`).
**Concrete trigger:** two 30-minute audits for different sites of the same tenant; the
first's reservation expires mid-crawl; the second reserves the freed budget → monthly
`crawl_pages_month` overshot.
**Fix:** heartbeat/extend the reservation for long crawls (like the fairness-slot
heartbeat), or scale the TTL with the reserved page count.

## LOW

### L-1 — Abandoned mock checkouts leak coupon reservations; mock-confirm coupon is query-tamperable
**Files:** `backend/src/routes/billing.ts:235-238`, `:250-257`, `:392-431`
**What's wrong:** `/billing/checkout` reserves a coupon slot for every provider (mock
included), but in mock mode no `checkout.session.expired` webhook ever fires, so an
abandoned mock checkout's `reserved_count` is never released — the cap is permanently
burned in dev/test. Separately, `mock-confirm` takes the coupon from the tamperable
querystring (`?coupon=XXX`) rather than the checkout-time reservation, so a user can
redeem a coupon code that was never validated/reserved at checkout (A1-M6 hardened
`trial_days` server-side but left `coupon` query-sourced).
**Fix:** have mock-confirm resolve the coupon from the checkout session record (or
re-validate + reserve there); add a mock-mode expiry sweep for stale reservations.

### L-2 — `POST /keywords/:kwId/track` burns a metering unit when the keyword is already tracked
**File:** `backend/src/routes/keywords.ts:111-126`
**What's wrong:** `withUsageReservation(tenantId, 'keywords_tracked', 1, …)` runs before
checking whether `tracked` is already TRUE — the `UPDATE … SET tracked=TRUE` affects the
row regardless and the reservation commits 1 unit for a no-op. `commitUsage` for
`keywords_tracked` writes no `usage_events` row (pure count), so the damage is
reservation churn + alert noise rather than billed spend, but the pattern is wrong.
**Fix:** `SELECT tracked` first and return early (200, no reservation) when already tracked.

### L-3 — `/sites/:id/keywords/research` seeds have no per-item length cap (expand has one)
**File:** `backend/src/routes/keywords.ts:47-50`
**What's wrong:** `seeds` items are `{ type: 'string' }` with no `maxLength` (the
`/expand` endpoint caps at 200). A multi-MB seed string flows into `researchKeywords` →
`getKeywordMetrics` → the DataForSEO request and the grouping logic.
**Fix:** add `maxLength: 200` (matching `/expand`) to the research schema.

### L-4 — `/content/:id/optimize` and `/content/:id/duplication` lack `requireVerifiedEmail`
**File:** `backend/src/routes/content.ts` (`/content/:id/optimize`, `/content/:id/duplication`)
**What's wrong:** every other LLM/provider-spending content endpoint carries
`requireVerifiedEmail` (S-01 defense-in-depth); these two don't. `optimize` can trigger
a fresh DataForSEO SERP fetch via `getSerpSnapshot` and 5 outbound `safeFetch` calls.
Spend is still bounded by the atomic `serp_checks` reservation, so this is consistency,
not a hole — but the gate exists everywhere else for a reason.
**Fix:** add `requireVerifiedEmail` to both preHandler arrays.

### L-5 — `provider_spend` records requested units while metering commits actual units
**File:** `backend/src/services/keywordCache.ts:43`
**What's wrong:** `recordProviderSpend(tenantId, 'dataforseo', 'keyword_metrics', missing.length, 0, q)`

(B1-9 fix). On partial provider results the spend evidence overstates real provider
consumption; `/admin/spend` and the global budget guard read the overstated number.
**Fix:** record `fresh.length` (move the call after the provider response, like the
metering commit).

### L-6 — `optimizeDraft` does up to 5 sequential 8s fetches inside a request handler
**File:** `backend/src/services/contentWorkflow.ts:81-128`
**What's wrong:** the loop awaits `safeFetch(url, …, 8000)` sequentially for up to 5
competitor URLs — up to ~40s+ in `POST /content/:id/optimize`, far past the ~8s route
budget noted in C1-M-8. The client gets a 504 while server-side work already consumed
provider/metered budget.
**Fix:** fetch in parallel with an overall deadline (e.g. `Promise.all` + 12s total
budget), or move analysis to a job.

### L-7 — `getSiteInsights` content-gap loop is N+1 on `keywords.volume`
**File:** `backend/src/services/insights.ts:76-90`
**What's wrong:** for every tracked keyword it issues `SELECT volume FROM keywords
WHERE id=$1` — `volume` was already available from the `keywords k` rows in the main
query above. Same N+1 class as A1-L1/C1-M-8.

### L-8 — `reportProcessor` races on the (site, week) check: plain INSERT without ON CONFLICT
**File:** `backend/src/services/reportJobs.ts:48-60`
**What's wrong:** the existing-report check is SELECT-then-INSERT with no
`ON CONFLICT` guard, although `POST /sites/:id/reports/build`
(`routes/reports.ts:150-158`) relies on a unique constraint on `(site_id, period_start)`.
Two concurrent report jobs → the loser gets a raw 23505 → job fails → retry (which
then sees the row and skips). Self-healing but noisy; the route already proved the
constraint exists.
**Fix:** `ON CONFLICT (site_id, period_start) DO NOTHING` + re-select, like the route.

### L-9 — `PATCH /keyword-lists/:listId` rename-to-duplicate is a raw 500
**File:** `backend/src/routes/keywords.ts:319-352`
**What's wrong:** create handles `ON CONFLICT (site_id, name)` → 200 `{existed:true}`,
but the rename PATCH does a bare `UPDATE` with no 23505 translation — renaming a list
to an existing name returns 500 INTERNAL instead of 409.
**Fix:** catch 23505 → 409 `LIST_EXISTS` (same pattern as competitors/sites).

### L-10 — No GSC disconnect endpoint; stale OAuth tokens retained indefinitely
**Files:** `backend/src/routes/gsc.ts`, `backend/src/routes/ga4.ts:148-163`
**What's wrong:** GA4 has `POST …/ga4/disconnect` (clears `ga4_connected`/`ga4_property_id`),
but GSC has no disconnect — once `gsc_refresh_token_enc` is stored there is no API
path to revoke it (it also backs GA4 property listing). A user who wants to unlink
their Google account cannot.
**Fix:** add `POST /sites/:id/gsc/disconnect` clearing `gsc_connected` and
`gsc_refresh_token_enc` (editor+/sites:write, like GA4's).

### L-11 — `GET /apikeys` lets viewers enumerate API-key metadata
**File:** `backend/src/routes/apikeys.ts:54-66`
**What's wrong:** any session role (viewer included) can list every API key's
`key_prefix`, `scopes`, `rate_limit_per_min`, `last_used_at`, `revoked_at`.
Create/revoke are owner/admin, but enumeration of key metadata (which scopes exist,
when keys were last used) is available to the lowest-privilege role.
**Fix:** gate the list at owner/admin like create/revoke.

### L-12 — Invitation endpoint has no rate limit (email bombing via compromised editor)
**File:** `backend/src/routes/account.ts:379-447`
**What's wrong:** `POST /account/invitations` requires owner/admin/editor +
`requireVerifiedEmail`, but has no per-tenant rate limit or invitation cap —
`getNotify().sendEmail` fires to an arbitrary address per call. A compromised editor
session can email-bomb arbitrary addresses at will (the C1-L-15 throttle covers
`/auth/email/change`, not this).
**Fix:** add `expensiveTenantLimit()` (or a dedicated invite throttle, e.g. 20/hour/
tenant) and/or a cap on pending invitations per tenant.

### L-13 — Invite-accept shell dissolve doesn't cancel a Stripe subscription with no local row yet
**File:** `backend/src/routes/account.ts:586-640`
**What's wrong:** the shell guard refuses the move when any `SHELL_TENANT_TABLES` row
exists (including `subscriptions`), but a Stripe subscription created moments ago —
checkout completed, webhook not yet processed — has no local row. Dissolving the shell
then leaves the Stripe subscription billing forever with no tenant to cancel it
(the pass#3 H-1 pattern, in miniature).
**Concrete trigger:** user completes Stripe checkout → immediately accepts an invite
as a sole user → shell dissolves before `checkout.session.completed` is processed →
Stripe keeps charging; the late webhook resolves to no tenant and is ignored.
**Fix:** in the dissolve branch, call `cancelTenantBilling(oldTenantId)` first (best
effort: proceed on 404-customer, abort on 5xx), mirroring the delete/erase fix.

### L-14 — Erase cancels Stripe *before* the DB transaction: cancel-then-fail leaves a live tenant with a canceled subscription
**Files:** `backend/src/routes/account.ts:1066-1067` (erase), `providers/stripe.ts:770-792`
**What's wrong:** the fix correctly aborts when cancellation *fails*, but the reverse
ordering hazard remains: `cancelTenantBilling` succeeds, then the erase transaction
rolls back (deadlock, constraint) → the tenant still exists but their paid
subscription is canceled. No re-activation path is offered; the user must re-checkout.
**Fix:** run the erase in a transaction first (rows deleted but not committed), cancel
Stripe, then commit — or on erase failure, attempt to reinstate / surface a
"subscription was canceled, re-subscribe" recovery state. (Low probability, real
billing impact.)

### L-15 — SSE job-stream `settled` misses queued audits beyond the LIMIT 5 window
**File:** `backend/src/services/jobStream.ts:24-53`
**What's wrong:** `collectJobsSnapshot` takes the 5 most recent audits and reports
`settled: true` when all are done/failed. A 6th-oldest audit stuck `'queued'` (e.g.
deferred past the 2h reaper window, cf. C2-M1) is invisible → the client closes the
stream while a job is still pending.
**Fix:** compute `settled` from an un-limited `EXISTS (… status IN ('queued','running'))`
query instead of the LIMIT 5 list.
