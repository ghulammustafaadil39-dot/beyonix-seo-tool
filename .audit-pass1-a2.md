## HIGH

### H-1. Tenant BYOK LLM key is sent to the WRONG provider (credential disclosure)
**File:** `backend/src/providers/llm.ts:93-99`

```ts
export function getLLM(override?: 'gemini' | 'openai' | 'mock', apiKey?: string): LLMProvider {
  const want = override ?? config.llmProvider;
  if (want === 'mock') return new MockLLMProvider();
  if (want === 'gemini' || (!want && (apiKey || config.geminiApiKey)))
    return new GeminiProvider(apiKey || config.geminiApiKey);   // ← apiKey here may be an OPENAI key
  if (want === 'openai' || (!want && (apiKey || config.openaiApiKey)))
    return new OpenAIProvider(apiKey || config.openaiApiKey);
```

**What's wrong:** `getLLMForTenant()` (`llm.ts:112-135`) passes a tenant's BYOK key with `override=undefined`. When the tenant has no explicit `llm_provider` set, `want` falls back to the *server* default — and whichever provider branch matches first swallows the tenant's key. Concrete trigger: tenant stores an **OpenAI** BYOK key, server has `GEMINI_API_KEY` set → `new GeminiProvider(openaiKey)` → the tenant's OpenAI secret is placed in the query string of requests to `generativelanguage.googleapis.com` (and vice-versa for a Gemini key when the server default is OpenAI). That is a live credential disclosure to the wrong third party, plus broken generation.
**Fix:** when a BYOK key is supplied without an explicit provider, require the provider to be explicit (fail closed) — never guess the provider from server config. E.g. `getLLMForTenant` should only pass `byokKey` together with the tenant's chosen provider, and `getLLM` should refuse `apiKey` without `override`.

### H-2. Production Docker image never ships `src/prompts/*.txt` — every LLM feature 500s in prod
**Files:** `backend/Dockerfile:9-14`, `backend/src/services/prompt.ts:7-18`

`renderPrompt()` resolves templates at `path.join(dirname(import.meta.url), '..', 'prompts')` → `dist/prompts/<name>.txt` when running compiled code. The Dockerfile does `COPY src ./src` + `npm run build` (`tsc`), and **tsc never emits `.txt` assets** — confirmed: `backend/dist/prompts/` does not exist in the repo's own build output, and no Dockerfile step copies the files. Every caller (`geoService.ts:98` geo-answer, `contentEngine.ts:30,46` content-outline/content-draft, `contentWorkflow.ts:312` content-brief-outline, `routes/onpage.ts:248` onpage-suggest) throws `ENOENT` in the production container, while dev (`tsx`) and tests (vitest, run from `src/`) work fine — so the entire suite is green and the failure is invisible until deploy. This breaks content generation, GEO checks, and on-page suggestions in production.
**Fix:** add `COPY src/prompts ./dist/prompts` (or `RUN cp -r src/prompts dist/prompts`) after `npm run build` in `backend/Dockerfile`; add a build-smoke test asserting `dist/prompts/*.txt` exist.

## MEDIUM

### M-1. `requireScope` passes all team sessions freely — viewers can mutate audits/content/geo/reports
**Files:** `backend/src/middleware/access.ts:105-118`, e.g. `backend/src/routes/audit.ts:217`, `routes/content.ts:184`, `routes/geo.ts`, `routes/reports.ts`

`requireScope()` returns immediately for any non-API-key caller (`if (!t?.apiKeyId) return; // user session: roles gate elsewhere`). But on most feature routes it is the **only** gate — e.g. `PATCH /issues/:issueId` (`audit.ts:217`), content write routes, geo prompt routes — no `requireRole`/`requireRoleOrScope` is stacked. The "roles gate elsewhere" comment is false on these routes. Trigger: a team member invited with role `viewer` (F-09 hierarchy exists precisely to restrict this) can PATCH audit issues, create/edit content, manage geo prompts, etc. — full intra-tenant privilege escalation.
**Fix:** either make `requireScope` role-aware for sessions, or (cleaner) replace bare `requireScope(...)` on mutating routes with `requireRoleOrScope([...roles], ...scopes)`.

### M-2. `checkLimit('sites')` counts soft-deleted sites — deleted sites burn the plan slot for 30 days
**Files:** `backend/src/metering.ts:104-107` (checkLimit) and `:130` (reserveUsage), `backend/src/routes/sites.ts:120`

```ts
used = Number((await q('SELECT COUNT(*)::int c FROM sites WHERE tenant_id=$1', [tenantId])).rows[0].c);
```

Everywhere else (`routes/sites.ts:133`, `routes/admin.ts:95`, `routes/account.ts:723`, scheduler) uses `deleted_at IS NULL`. Migration 013 introduced soft-delete with a 30-day restore window and the retention job hard-purges after 30 days — so a Starter user (1 site) who deletes their site and tries to add a replacement gets `402 LIMIT_EXCEEDED` for up to 30 days. The downgrade path (`services/billing.ts:112`) *does* use `deleted_at IS NULL`, so the two code paths also disagree with each other.
**Fix:** add `AND deleted_at IS NULL` to both site-count queries in `metering.ts`.

### M-3. The atomic reserve-then-commit metering is dead code in production; all real enforcement is check-then-act
**Files:** `backend/src/metering.ts:225-290` (reserveUsage/commitUsage/cancelUsage), callers `services/keywordCache.ts:37,76`, `services/keywordService.ts:425`, `services/rankJobs.ts:105`, `services/serpSnapshots.ts:175`

`reserveUsage` (per-tenant advisory xact lock, atomic check-and-insert — the C-02 race fix) is called **only by tests**; every production choke point calls `assertDataBudget()`, which is `checkLimit` → later `recordUsage`. Trigger: the daily scheduler tick enqueues N rank jobs for one tenant; two workers process two jobs concurrently, both read `used=400/500`, both proceed → 600 serp_checks consumed against a 500 limit. The operator pays DataForSEO per call, so this is operator-cost overspend plus plan-limit bypass. The `getUsage` reservation accounting is consequently also dead weight.
**Fix:** route the choke points through `reserveUsage`/`commitUsage` (reserve before the provider call, commit with actual units, cancel on failure).

### M-4. Leader-election TTL (30s) can expire mid-tick → two processes run the same schedule → duplicate digests and duplicate webhook deliveries
**Files:** `backend/src/scheduler.ts:25-30`, `backend/src/services/leaderElection.ts:39-58`, `backend/src/services/notifications.ts:198-238`, `backend/src/services/webhookDelivery.ts:201-257`

`onlyLeader()` acquires a 30s-TTL lock per tick; the re-entry extension only fires when *another* tick from the *same* process lands within the window. A tick that runs longer than 30s alone (e.g. `processWebhookRetries` or `processDigests` over many rows, or a slow `enqueueForVerifiedSites` loop) lets the key expire; a second worker process then legitimately wins `SET NX` and runs the same schedule concurrently. Neither consumer is concurrency-safe:
- `processDigests` SELECTs due users, sends email, *then* UPDATEs `last_sent_at` — no atomic claim → **duplicate digest emails**.
- `processWebhookRetries` SELECTs pending deliveries, delivers, then UPDATEs — no `UPDATE … WHERE status='pending' … RETURNING` claim → **duplicate deliveries to customer endpoints** (signature timestamps differ, so receivers can't dedupe by signature either).
**Fix:** (a) heartbeat/extend the leader lock for the duration of each tick (or use a fencing token), and (b) make both consumers claim-then-work: `UPDATE … SET status='in_progress' … WHERE status='pending' AND id = ANY($1) RETURNING …` (digests: conditional `UPDATE notification_digests SET last_sent_at=now() WHERE … AND last_sent_at IS NOT DISTINCT FROM $old` before sending).

### M-5. `incr`-then-`expire` race can permanently rate-limit a tenant / API key
**Files:** `backend/src/queues.ts:140-147` (`checkTenantRateLimit`), `backend/src/middleware/auth.ts:141-146` (per-API-key limit)

```ts
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, RL_WINDOW);
```

If the process crashes (or the connection drops) between `INCR` and `EXPIRE`, the key persists with **no TTL**; the counter then grows forever and every subsequent request gets 429 — a stuck, self-inflicted denial of service for that tenant (queue enqueues) or that API key (all API traffic), requiring manual Redis surgery. Also the key omits `redisKeyPrefix()`, so it ignores `BSEO_REDIS_PREFIX` namespacing used by the test suites.
**Fix:** use `SET key 1 EX 60 NX` + `INCR`, or a single Lua script that increments and sets expiry atomically; include `redisKeyPrefix()` in the key.

### M-6. Fairness deferral (`moveToDelayed` then return) likely double-executes heavy jobs
**File:** `backend/src/worker.ts:70-81`

```ts
if (!slot) {
  await job.moveToDelayed(Date.now() + 60_000);
  return { deferredForFairness: true, tenantId };   // ← processor returns normally
}
```

In BullMQ, once the processor returns, the Worker calls `moveToCompleted` on a job that is no longer active (it was moved to delayed; its lock is gone) — this fails, producing a spurious `failed` event, a retry, and (at exhaustion) a dead-letter entry for a job that never actually ran. Worse, the retry chain and the 60s-delayed copy can both execute the heavy job → double crawl/LLM/provider spend. No test covers this path (grep for `deferredForFairness`/`moveToDelayed` hits only `worker.ts`).
**Fix:** don't return normally after `moveToDelayed` — throw a dedicated non-retryable `DeferredForFairness` error that the `failed` handler explicitly ignores (no retry, no dead-letter), or restructure to re-queue without completing.

### M-7. GEO check prompt injects the raw user query — no `delimitUntrusted`
**File:** `backend/src/services/geoService.ts:98`

```ts
const prompt = await renderPrompt('geo-answer', { platform, query: queryText });
```

`promptSafety.delimitUntrusted()` exists and is used in `contentWorkflow.ts:264,318` and `routes/onpage.ts:250-253`, but the GEO path interpolates the user's arbitrary query text directly into the system prompt with no delimiters. Trigger: a user (or anyone with geo access on a shared workspace) submits a query like "Ignore all previous instructions and …" — the real LLM follows it, and the output is persisted as `geo_checks` rows (stored prompt-injection artifacts that then feed reports/digests).
**Fix:** wrap with `delimitUntrusted(queryText, { label: 'user-query', maxChars: … })` like the other call sites.

## LOW

### L-1. `jwt.verify` without an explicit `algorithms` whitelist
**Files:** `backend/src/middleware/auth.ts:190`, `backend/src/routes/auth.ts:489` (2FA challenge), `:527` (logout)

All three call `jwt.verify(token, config.jwtSecret)` with no `algorithms: ['HS256']`. `signToken` only ever mints HS256, so pin the verifier to match. (HS256-vs-RS256 confusion doesn't apply here since the secret isn't a public key, hence low.)
**Fix:** pass `{ algorithms: ['HS256'] }` at all three sites.

### L-2. Duplicate indexes (write amplification, slower migrations)
- `migrations/040_wave3.sql:27` creates `idx_w3_usage_tenant_type_time ON usage_events(tenant_id, event_type, created_at)` — identical column list to the index already created in `001_init.sql`. Two indexes, double write cost on every `recordUsage` insert.
- `migrations/017_api_keys.sql:18` creates `api_keys_hash_idx ON api_keys(key_hash)` — `key_hash` already has a UNIQUE constraint, which creates its own btree. Redundant.
**Fix:** drop the duplicates (`DROP INDEX IF EXISTS` in a new migration).

### L-3. Dead exports
- `middleware/idempotency.ts:131` `storeIdempotentResponse` — "kept for API compatibility" but referenced nowhere in `src/` (only its own file). 
- `crypto.ts:81` `currentKid()` — no callers.
**Fix:** remove, or document the external consumer.

### L-4. CSRF guard treats `x-api-key` clients as cookie sessions
**File:** `backend/src/middleware/csrf.ts:66-72`

`hasAuthHeader` only checks `Authorization: Bearer …`. An API client authenticating via `x-api-key` that also happens to carry the `bseo_token` cookie (shared cookie jar / browser extension) will be CSRF-rejected on mutations despite using a non-ambient credential. Minor interop footgun.
**Fix:** treat presence of `x-api-key` like `Authorization` for the exemption.

### L-5. Local coupon codes are passed straight through as Stripe coupon IDs
**File:** `backend/src/providers/stripe.ts:78` (`discounts: [{ coupon: couponCode }]`)

`routes/billing.ts:135` validates the code against the *local* `billing_coupons` table, then the real provider hands that same string to Stripe, which expects a Stripe coupon *ID*. With real Stripe, a local code like `LAUNCH20` fails checkout-session creation unless an identically-ID'd coupon exists in the Stripe dashboard — a silent mock/real behavior split.
**Fix:** map local codes to Stripe coupon IDs at checkout (or create the Stripe coupon at validation time).

### L-6. Committed `usage_reservations` are never purged (slow table growth)
**File:** `backend/src/services/retention.ts:37-44`

The retention rule only deletes `cancelled` / long-expired `reserved` rows; `committed` rows are kept forever as "the usage record" — unlike `usage_events` (13-month retention). Over years this is unbounded growth on a table that `getUsage` scans per request.
**Fix:** align with the 13-month `usage_events` window for committed rows too.

### L-7. Fairness slot TTL (900s) is not refreshed by the holder
**File:** `backend/src/services/fairness.ts:25-38`

The Lua script sets `EXPIRE 900` once at acquire. A crawl job legitimately runs up to the 15-min queue timeout (`QUEUES.crawl` = 15 min); a job running slightly over 900s loses its slot while still running, letting another job acquire it — silently exceeding `HEAVY_CONCURRENCY_PER_TENANT`. (Crash-holders self-heal after 15 min, which is the intended side.)
**Fix:** heartbeat the slot (`EXPIRE`) periodically from long jobs, or set TTL ≥ max job timeout.

### L-8. Migration numbering gaps (informational, not a hazard)
Migrations present: 001–007, 010–030, 040. Missing: 008, 009, 031–039. Zero-padded names sort correctly so ordering is safe, and `runMigrations` skips absent files; no action needed, just noting the gap so nobody "fills" 008/009 with a backdated migration that sorts *before* already-applied ones (which would apply out of intended order on fresh installs).

## Explicitly checked and CLEAN

- **`db.ts` / `migrate.ts` / migration semantics:** per-file transactions with rollback-on-failure and no `migrations` row on failure (retry starts clean) — correct. Session-level advisory lock (`82011`) held for the whole run and explicitly released before `client.release()` — the pool-session deadlock footgun is handled with a comment. API (`index.ts:186`), worker (`worker.ts:112`), and the one-shot `migrate` service all funnel through it. No migration file contains its own `BEGIN`/`COMMIT` that would break the wrapper transaction.
- **All 29 migrations:** DDL is `IF NOT EXISTS`-guarded throughout (001's `CREATE TABLE` without the guard is fine — files run once, tracked in `migrations`). No `DROP TABLE`/`TRUNCATE`/`DELETE` of user data except: 003's PK-swap dedupe on `keyword_metrics_cache` (transactional, keeps newest), 007's defensive cross-tenant domain unverify (keeps earliest — data-affecting but justified, logged in comment), 020's `status='fixed'`→`'resolved'` rewrite (intended). No down-migrations exist anywhere, but none are promised by any doc I found (no "down" references in migrations/CONTRACTS).
- **`crypto.ts`:** AES-256-GCM with `crypto.randomBytes(12)` IV per encryption (no IV reuse), kid-versioned keys, strict hex/kid validation at parse, production fail-fast via `validateSecrets`, `plain:` refused outside dev/test. Rotation script (`scripts/rotate-encryption-keys.ts`) decrypts with the full key set, never logs plaintext, exits non-zero on failures before old keys are dropped.
- **`config.ts`:** fail-closed defaults (`NODE_ENV` → production), placeholder-secret denylist, Stripe webhook-secret consistency check. Minor nit: `planIdFromStripePrice` reads `process.env` live despite the "never read process.env elsewhere" rule (acknowledged in its own comment).
- **`scheduler.ts`:** all ticks in UTC (`SCHEDULER_TIMEZONE`), `isoWeek` uses UTC getters only. Idempotency keys per schedule are well-formed. (Concurrency limits of the leader gate are M-4.)
- **`queues.ts`/`worker.ts`:** jittered backoff, per-queue timeouts, stalled-job handling, DLQ capture only on terminal failure, graceful shutdown ordering (scheduler → workers → redis+db). (M-5, M-6 are the exceptions.)
- **`middleware/idempotency.ts`:** claim-before-execute via `ON CONFLICT DO NOTHING`, wait-and-replay for concurrent duplicates, 422 on body mismatch, stale-claim takeover after 5 min, failures release the claim. Solid.
- **`middleware/auth.ts` (sessions/JWT):** token_version + jti session registry checks, totp-purpose rejection, suspended/read-only enforcement at the choke point. API-key path hashes before compare, throttles `last_used_at` writes. (L-1, L-4, M-5 are the exceptions.)
- **`middleware/access.ts` role model** itself is coherent (`requireRoleOrScope`, `requireHumanSession` for key management, 404-not-403 for admin). The hole is only M-1 (bare `requireScope` on mutating routes).
- **`providers/`:** DataForSEO (honest null difficulty, circuit-broken), Google (mock provider fails closed outside test/dev — N-A1-6 handled), Stripe webhook ordering guard + coupon atomic redemption + `last_event_at` watermark, notify, captcha (fail-closed). (H-1, L-5 are the exceptions.)
