## HIGH

### D5-H-1 — Every signup gets the full paid Starter plan free forever — no payment gate, no expiry
**Files:** `backend/src/routes/auth.ts:169,277` (`INSERT INTO tenants … 'starter'`),
`backend/src/middleware/auth.ts` (no subscription requirement anywhere)
**What's wrong:** Starter is a paid plan ($29/mo per ARCHITECTURE.md pricing
decision). Yet every new tenant — email signup AND Google signup — is created
with `plan_id='starter'` and no subscription row, and **nothing anywhere
requires payment**: no middleware gate, no trial expiry (`trial_days=0` on all
plans), no "subscription required" check. The tenant immediately gets the full
Starter quota (50 tracked keywords, 5,000 AI words, 500 SERP checks, 500
keyword metrics, 20 geo checks / month) — including quota that burns **real
DataForSEO money** per call — and keeps it forever without ever visiting
`/billing/checkout`.
**Concrete trigger:** `POST /auth/signup` → use keyword research + rank tracking
up to Starter limits every month → never pay. Each such free user costs the
business real provider spend (500 SERP + 500 keyword-metrics tasks/mo at
DataForSEO list prices) with zero revenue. This is both free-plan abuse and an
unbounded DataForSEO overspend vector.
**Fix (product decision required):** either (a) make Starter an intentional
free tier with drastically smaller, documented limits (e.g. 5 keywords, 50 SERP
checks, no AI words) and a separate paid `starter` price, or (b) gate product
routes on an active/trialing/past_due subscription and put non-paying tenants
in a blocked state with an upgrade prompt. At minimum, record the intended
model — right now the code implements "everything free" while the pricing doc
says "$29/mo".

## MEDIUM

### D5-M-1 — The pass#3 PRICE_NOT_CONFIGURED fail-loud fix is dead: the idempotency ledger permanently swallows Stripe's retries
**Files:** `backend/src/providers/stripe.ts` — ledger insert (~line 397),
the C5-M-2 `throw new ApiError(502, 'PRICE_NOT_CONFIGURED', …)` (~line 524)
**What's wrong:** The pass#3 fix throws 502 on an unmapped Stripe price so that
"Stripe retries the event" after ops configures the price. But `applyPaymentEvent`
inserts the event id into `stripe_webhook_events` **before** any processing.
The 502 leaves that row in place (never marked processed, never removed).
On Stripe's retry the handler hits `ON CONFLICT (event_id) DO NOTHING` →
`rowCount === 0` → `markProcessed()` → returns `{ deduplicated: true }`. The
event is **never reprocessed**, even with the price mapping now configured.
The comment's retry assumption is false.
**Concrete trigger:** ops rotates a price in the Stripe dashboard without
updating `STRIPE_PRICE_*` → customer upgrades in portal → first delivery 502s
(no plan change applied, correct) → ops adds the env var → Stripe retries for
3 days → every retry returns `{received:true, deduplicated:true}` → the tenant
is billed the higher price while stuck on the old plan's limits indefinitely,
until someone hand-edits the DB. There is no reaper for unprocessed ledger
rows (confirmed: no reader of `processed_at IS NULL` exists).
**Fix:** on the 502 path, delete the ledger row (or mark it failed-but-retryable
and make the conflict branch re-attempt rows whose `processed_at IS NULL`),
so a later delivery actually reprocesses. Alternatively keep the throw but
write the row with a `failed` status that the conflict branch treats as
"not yet handled".

### D5-M-2 — Grace-expiry downgrade strands a later successful payment: customer pays, stays on Starter
**Files:** `backend/src/services/billing.ts` (`downgradeTenant` sets
`subscriptions.status='canceled'`), `backend/src/providers/stripe.ts`
(`invoice.paid` recovery: `UPDATE subscriptions SET status='active' …
WHERE tenant_id=$1 AND status='past_due'`)
**What's wrong:** When the 3-day grace expires, `downgradeTenant` flips the
**local** subscription row to `'canceled'` — but the Stripe-side subscription
is still alive (past_due, Smart Retries still scheduled). If Stripe then
succeeds on a retry, the `invoice.paid` recovery only matches
`status='past_due'` → 0 rows → the tenant stays on the downgraded Starter plan
(and `read_only` if it was set) while Stripe keeps billing the paid plan.
**Concrete trigger:** payment fails → `past_due`, grace +3d → daily
`processBillingGrace` downgrades (local `canceled`, plan starter) → Stripe
Smart Retry succeeds on day 5 → `invoice.paid` → recovery UPDATE matches
nothing → customer charged Pro, limited to Starter quotas. (Related: a retry
that *fails* after the downgrade flips status back to `past_due` with a fresh
grace and re-sends dunning emails — the downgraded tenant gets "payment
failed" emails for a subscription we already canceled locally.)
**Fix:** don't locally write `'canceled'` while the Stripe subscription is
still alive — keep `'past_due'` (so the `invoice.paid` recovery path works),
and reserve `'canceled'` for the genuine `customer.subscription.deleted`
webhook. Or extend the `invoice.paid` recovery to also revive `'canceled'`
rows by re-resolving the plan from the Stripe price id.

### D5-M-3 — Coupon slot double-release: `releaseReservation` fires even when the reservation never committed
**Files:** `backend/src/routes/billing.ts` — `releaseReservation` in the
checkout catch-all; `resolveStripeCoupon` (BEGIN … row-lock UPDATE … ROLLBACK
on `ensureCoupon` failure)
**What's wrong:** `resolveStripeCoupon` increments `reserved_count` inside its
own transaction. If `ensureCoupon` (the Stripe network call) throws — or the
coupon is invalid/exhausted — the transaction **rolls back**, so the increment
never committed. Control then reaches the checkout route's `catch`, which
unconditionally calls `releaseReservation()` → `reserved_count =
GREATEST(reserved_count - 1, 0)` on the **committed** value — stealing a slot
belonging to another in-flight checkout (or clamping at 0, harmlessly).
**Concrete trigger:** coupon `LAUNCH` (`max_redemptions=10`, 9 reserved by
legit checkouts) → checkout A fails at `ensureCoupon` (Stripe timeout) →
rollback → catch releases → `reserved_count` 9→8 → an 11th checkout can now
reserve → cap overshoot by 1 per such failure. Bounded but real, and it is a
bug *in the pass#3 fix itself*.
**Fix:** only call `releaseReservation()` when `resolveStripeCoupon` returned
successfully (track with a boolean flag); the already-rolled-back path needs
no release.

## LOW

### D5-L-1 — Coupon deactivated mid-flight leaks its reserved slot forever
**File:** `backend/src/providers/stripe.ts` (~line 508, redeem UPDATE)
**What's wrong:** the pass#3 fix added `AND active` to the completion redeem
(`reserved → redeemed`). Correct behavior — except when the predicate fails
(inactive, or cap edge), `rowCount` is 0, the code only `console.warn`s, and
`reserved_count` is **never decremented**. The slot is burned permanently.
**Trigger:** admin deactivates a coupon (SQL) while N checkouts are in flight
→ all N completions warn and leak → `reserved_count` stuck > 0 →
`max_redemptions` effectively reduced by N forever.
**Fix:** on `rowCount === 0`, still release the hold:
`UPDATE billing_coupons SET reserved_count = GREATEST(reserved_count - 1, 0)
WHERE code = $1` (without the `active`/cap predicates).

### D5-L-2 — Admin suspend doesn't touch Stripe billing
**File:** `backend/src/routes/admin.ts` (`POST /admin/tenants/:id/suspend`)
**What's wrong:** suspend sets `suspended_at` (product fully blocked) but never
pauses/cancels the Stripe subscription — a suspended tenant keeps being
charged monthly for a product they cannot use.
**Trigger:** platform admin suspends a paying tenant (ToS/abuse) → Stripe
renews next month → charge for zero service; guaranteed refund dispute.
**Fix:** on suspend, either cancel-at-period-end via `cancelSubscription` or
record an explicit policy decision; at minimum surface the active Stripe
subscription in the suspend confirmation.

### D5-L-3 — Global daily provider circuit is check-then-act across tenants
**Files:** `backend/src/services/providerGuard.ts`
(`assertGlobalProviderBudget`), call sites in `keywordCache.ts`,
`keywordService.ts`, `serpSnapshots.ts`
**What's wrong:** the pass#3 cents-pricing fix made the *knob* live, but the
check itself is a non-atomic pre-flight: it reads `SUM(cost_cents)` then the
provider call happens later. The per-tenant budget is atomic (advisory lock),
but **across tenants** N concurrent callers can each pass the global check
before anyone records spend, collectively overshooting
`GLOBAL_PROVIDER_DAILY_CAP_*` by up to N in-flight calls. Acceptable as a
soft circuit, but it is not a hard cap as the name/503 suggests.
**Fix:** document it as best-effort, or gate the spend *recording* with a
global advisory lock / Redis INCR-based daily counter.

### D5-L-4 — `processBillingGrace` aborts the whole daily run on one tenant's failure
**File:** `backend/src/services/billing.ts` (`processBillingGrace`)
**What's wrong:** the loop `await downgradeTenant(...)` has no per-tenant
try/catch — one tenant's throw (DB hiccup, hook failure) aborts the run and
every tenant behind it keeps an expired grace until the next day's run.
Self-healing, but a persistently-failing tenant delays everyone daily.
**Fix:** wrap each iteration in try/catch, log, continue.

### D5-L-5 — `resolveStripeCoupon` holds the coupon row lock across the Stripe network call
**File:** `backend/src/routes/billing.ts` (`resolveStripeCoupon`: BEGIN …
`FOR UPDATE`-style conditional UPDATE … `await getPayments().ensureCoupon()`
… COMMIT)
**What's wrong:** the B1-10 lesson (never hold a DB lock across a Stripe call)
was applied to the tenant row but not here: the `billing_coupons` row lock is
held for the full `ensureCoupon` round-trip (1–3s real Stripe). Concurrent
checkouts using the *same* coupon serialize on Stripe latency.
**Trigger:** flash sale, 50 concurrent checkouts with one coupon → 50
serialized Stripe `coupons.retrieve/create` calls under an open transaction
each. Throughput collapse, not incorrectness.
**Fix:** move `ensureCoupon` before BEGIN (accept a tiny create-duplicate
window — Stripe ids are deterministic via `stripeCouponIdFor`, so the second
create just retrieves), or do the reserve UPDATE, COMMIT, then ensureCoupon,
then store the id in a second short transaction.

## Adversarial re-verification of the five named pass#3 fixes

1. **cancelSubscription on delete/erase (C1-H-1/H-2)** — HOLDS.
   `routes/auth.ts` (last-user delete) and `routes/account.ts` (`/account/erase`)
   both call `cancelTenantBilling(tenantId)` *before* any row deletion; on
   failure it throws 502 and the flow aborts with no rows deleted.
   `tenant_credits` are tombstoned into `admin_audit_log`, not silently
   dropped. Residual (theoretical): if `tenants.stripe_customer_id` is NULL
   the cancel silently no-ops — unreachable in the real flow (checkout always
   sets it), noted only.
2. **Coupon atomic reserve (C5-H-1)** — HOLDS, with two new edge bugs filed
   above (D5-M-3 double-release on `resolveStripeCoupon` failure, D5-L-1 slot
   leak on mid-flight deactivation). The core race (concurrent checkouts vs
   `max_redemptions`) is genuinely closed by the conditional
   `reserved_count + 1 … WHERE redeemed_count + reserved_count < max_redemptions`.
3. **Invoice `amount_paid` (C5-M-1)** — HOLDS. Paid invoices now use
   `amount_paid ?? total ?? amount_due`; failed ones use `amount_due`.
4. **Portal price fail-loud (C5-M-2)** — FIX IS WRONG → filed as D5-M-1. The
   502 fires correctly, but the idempotency ledger makes Stripe's retry a
   permanent no-op, so the "configure the price and the event will be
   retried" promise is false.
5. **Coupon id collision (C5-M-6 / C1-L-3)** — HOLDS. `stripeCouponIdFor`
   appends a sha256-of-raw-code suffix (distinct codes → distinct ids), and
   `resolveStripeCoupon` fail-louds on a namespace clash.
