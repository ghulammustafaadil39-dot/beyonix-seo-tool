## 2. NEW findings

### NEW MEDIUM #1 — `checkout.session.completed` records `'active'` for `incomplete` subscriptions on the real Stripe path (C5-L-2 detection is dead code there)

**File:** `backend/src/providers/stripe.ts:553-555`

**What's wrong:** The C5-L-2 guard reads the subscription status from `subObj?.status`, where `subObj` is `data.subscription` when it is an *expanded object*. On the real Stripe path `data` is the Checkout **Session** object, and `session.subscription` is always a plain string ID — Stripe never expands it in webhook payloads. So `subObj` is `undefined`, `subStatus` is `undefined`, `incomplete` is `false`, and the row is written `status='active'` (or `'trialing'`) with `tenants.plan_id` upgraded to the paid plan — even when the subscription is actually `incomplete` in Stripe. Pass#5 (e4:20) explicitly described this mechanism as working ("stripe.ts sets it from `checkout.session.completed` with `subObj.status='incomplete'`"); no prior report questioned the expansion.

**Concrete money-impact exploit chain:**
1. Attacker starts a Pro checkout with a payment method whose first charge stays *pending* (async/debit methods, abandoned 3DS) — subscription is `incomplete` in Stripe for up to 23h.
2. `customer.subscription.created(incomplete)` correctly writes local status `'incomplete'` (not billable — the E4-M-1/F2-M-1 fix).
3. `checkout.session.completed` arrives later with a **newer** `created` timestamp, so the C-01 stale-guard does not drop it — and its `ON CONFLICT (tenant_id)` upsert **clobbers** the correct `'incomplete'` row back to `'active'`, upgrades `tenants.plan_id` to Pro, and wipes `grace_until` to NULL.
4. `BILLABLE_SUBSCRIPTION_STATUSES` includes `'active'` → the never-payer gets full Pro-limit spend access (real DataForSEO/LLM provider cost) for up to 23h, until `incomplete_expired` downgrades them. The grace-wipe also defeats the "no fresh grace for consumed-grace rows" rule: the next retry's `invoice.payment_failed` sees `grace_until IS NULL` and mints a brand-new 3-day grace.
5. The trial gate's `'incomplete'` exclusion — the headline pass#6 fix — is bypassed, because the row says `'active'`.

**Suggested fix:** In `checkout.session.completed`, when the provider is real and `data.subscription` is a non-expanded string id, retrieve the subscription via the Stripe API to get its true status (fail closed to `'incomplete'` if the retrieve fails); never overwrite a stored `'incomplete'`/`'past_due'` status with `'active'` when the true status is unknown. Keep the mock path behavior unchanged (mock has no Stripe object by design).

### NEW MEDIUM #2 — `invoice.paid` recovery after grace-expiry does not restore plan or `read_only`: payer stranded on Starter

**File:** `backend/src/providers/stripe.ts:882-885`

**What's wrong:** The D1-H-1 design comment in `services/billing.ts` promises: *"a later successful retry's `invoice.paid` recovery still matches the row and revives the paid plan instead of stranding a payer on Starter."* The code does not do this. After grace expiry, `downgradeTenant(..., {subscriptionStatus:'past_due'})` sets `tenants.plan_id='starter'` and possibly `read_only=TRUE`, while the subscription row stays `'past_due'`. When Stripe's retry succeeds, the `curStatus === 'past_due' || curStatus === 'incomplete'` branch only runs `UPDATE subscriptions SET status='active', grace_until=NULL` — it never restores `tenants.plan_id`, never restores `subscriptions.plan_id`, and never calls `recomputeReadOnly`. The `'incomplete'` variant is worse: `tenants.plan_id` was never upgraded at checkout, so a payer ends up `status='active'` + Starter limits while `subscriptions.plan_id` says Growth. Plan restoration currently depends entirely on a *subsequent* `customer.subscription.updated` event arriving (it re-resolves the plan from the price and recomputes read-only) — if that event is lost, delayed, or stale-dropped (`created` ≤ the invoice's `created`), the customer keeps paying the Growth/Pro price while the product shows Starter, possibly fully `read_only` (all mutations blocked).

**Concrete trigger:** Growth tenant → payment fails → 3-day grace → `processBillingGrace` downgrades product to Starter (read-only if over limits) → Stripe Smart Retry succeeds → `invoice.paid` flips status to `active` only → payer billed $X/mo for Growth, product serves Starter, possibly read-only, until/unless `subscription.updated` arrives.

**Suggested fix:** In the `past_due`/`incomplete` recovery branch, resolve the plan from the invoice price exactly like the `'canceled'`-revival branch below it does (`planIdFromStripePrice(data.lines?.data?.[0]?.price?.id)`), write it to both `subscriptions.plan_id` and `tenants.plan_id`, and call `recomputeReadOnly` — making `invoice.paid` the self-sufficient recovery the design comment claims it is.

### NEW LOW #1 — `charge.refunded` over-credits on multiple partial refunds (cumulative `amount_refunded`)

**File:** `backend/src/providers/stripe.ts:948-970`

**What's wrong:** The credit amount is `data.amount_refunded`, which on a Stripe charge object is the **cumulative** refunded total. Each partial refund generates its own `charge.refunded` event (distinct event id → passes the F2-L-1 guard). Two $5 partial refunds on a $10 charge produce credits of 500 + 1000 = **1500¢** against an actual $10 refund.

**Impact:** LOW — `tenant_credits` are never auto-applied against invoices (only summed for the admin view and tombstoned on erase), so this inflates the admin credit balance and the erase forfeit record, not real payouts. No prior report mentions `amount_refunded`.

**Suggested fix:** Credit per refund object instead of per charge event — iterate `data.refunds?.data`, insert one credit row per refund keyed by the refund id in the idempotency guard — or compute the delta against existing credits already recorded for the same charge.
