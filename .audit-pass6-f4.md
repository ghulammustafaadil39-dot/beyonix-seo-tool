## NEW findings (introduced by the pass#5 fix round)

### LOW-1 — NEW — DEPLOY.md troubleshooting row still blames `bash` and cites UNVERIFIED-5, whose rewrite resolved exactly that

**File:** `DEPLOY.md:283`:
`| \`backup\` container restarting | Read \`logs backup\`; first suspects:
\`bash\` missing in the image (UNVERIFIED-5) or DB unreachable |`

**What's wrong:** the E5-L-3 fix (commit `7696191`) rewrote UNVERIFIED-5 to
state the scripts are POSIX-`sh` clean and the old bash-shebang concern is
**resolved** — but the troubleshooting table's one remaining reference to
UNVERIFIED-5 was not updated. The row predates pass#5 (it was accurate when
UNVERIFIED-5 was the bash check), but the rewrite changed UNVERIFIED-5's
meaning out from under it. An operator following the doc now chases a fixed
non-issue ("bash missing") as a *first suspect*, exactly the false alarm
E5-L-3 was filed to prevent.

**Fix:** change the row to match the new UNVERIFIED-5, e.g.
"first suspects: `_pg_env.sh` misconfiguration or DB unreachable; if the
sidecar never ran a successful restore, treat backups as untrusted until the
scratch-DB restore test passes (UNVERIFIED-5)."

**Duplicate check:** grepped all `.audit-pass{1,2,3,4,5}-*.md` — E5-L-3
flagged UNVERIFIED-5 itself, but no pass flagged this surviving
troubleshooting cross-reference. **NEW.**

### LOW-2 — NEW — DEPLOY.md's new Wave-4 line describes `global_provider_guard` as "backing the atomic circuit"; after the E2-M-1 fix the table backs nothing

**File:** `DEPLOY.md:163-166`:
"- **045** replaces the sites `UNIQUE (tenant_id, domain)` constraint with a
  partial unique index (`WHERE deleted_at IS NULL`), so soft-deleted domains
  can be re-added; and creates `global_provider_guard` (one row per UTC day)
  backing the atomic global provider-spend circuit."

**What's wrong:** the E2-M-1 fix (commit `bd6fbff`, same round but landed
*after* the docs commit `7696191`) replaced the guard-row mechanism with
`pg_advisory_xact_lock(hashtext('global_provider_guard'))` — a *virtual*
lock key that merely shares the name. Grep confirms production code never
reads or writes the `global_provider_guard` table anymore
(`backend/src/` has zero `INSERT`/`SELECT` on it; only the lock-key string
at `providerGuard.ts:122`). The table is vestigial — it will be empty in
production, with no "one row per UTC day". An operator debugging the spend
circuit per this doc would query an empty table and draw wrong conclusions
(or build monitoring on rows that never arrive). (The 045 migration's own
comment — "SELECT FOR UPDATE on this row makes the check atomic" — is
similarly stale, but migration history is immutable; the live doc should be
corrected.)

**Fix:** reword to reflect the current mechanism, e.g. "045 also creates the
(now-vestigial) `global_provider_guard` table; the spend circuit is currently
serialized by an xact-scoped advisory lock (`pg_advisory_xact_lock`), not by
guard rows."

**Duplicate check:** grepped all `.audit-pass{1,2,3,4,5}-*.md` — E2-M-1
covered the mechanism fix; no pass covered this doc sentence (it was written
during the fix round). **NEW.**
