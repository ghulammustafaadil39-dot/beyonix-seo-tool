## NEW findings

### G3-M-1 — MEDIUM — No account-security self-service anywhere in the frontend: 2FA enrollment, password change, and password reset have zero UI

**Files:** `frontend/app/login/page.tsx` (no "Forgot password" link), `frontend/app/dashboard/settings/page.tsx` (no security section at all), `frontend/lib/api.ts` (only `authApi.login/logout/me/signup/verifyTotp` are ever called — grep of `app/ + components/` confirms).
**Backend side exists and is fully built:** `POST /auth/totp/setup`, `/auth/totp/enable`, `/auth/totp/disable` (`backend/src/routes/auth.ts:873-911`, human-session gated, encrypted secret, one-time backup codes), `POST /auth/password/reset-request` (`:420`), `POST /auth/password/reset` (`:449`), plus `password/change`.

**What's wrong:** the Wave-1 gate verified 2FA as a live security control and the frontend even implements the *consumer* side of it (TOTP challenge + backup-code toggle at login, `login/page.tsx:216-238`), but there is no way for a user to *enable* 2FA through the product: no settings section, no enrollment flow, no QR-code/secret display step, no disable control. The same holds for password change (no UI for `password/change`) and password reset (no "Forgot password" link on the login page, no reset-confirm page). A user who wants to harden an account that holds billing relationships, API keys (which spend provider budget), and CMS publish credentials cannot do so; a user who forgets their password has no in-product recovery path — the account is recoverable only via raw API calls or operator intervention.

**Concrete trigger:** Sign in → Settings → no security/2FA/password section exists. Log out → login page → no "Forgot password" link. A locked-out user has zero self-service recovery.

**Fix:** wire the existing backend endpoints into the UI: a "Security" section in Settings (TOTP setup with QR code + one-time backup-code display, disable with password confirmation), a password-change form, and a forgot-password link + reset-confirm page on the login flow.

**Duplicate check:** grepped all `.audit-pass{1,2,3,4,5}-*.md` for "2fa ui", "totp setup", "enrollment", "enable 2fa", "password change", "forgot password". The only hits are backend-context mentions (pass#2-b1:60 lists the endpoints in an API-key userId bug; pass#4-d1:313 mentions them in backend verification). No pass filed the missing frontend UI. **NEW.**

### G3-L-1 — LOW — Billing page treats a fully-canceled subscription as "has subscription": churned tenants get no direct resubscribe CTA

**Files:** `frontend/app/dashboard/billing/page.tsx:289` (`const hasSubscription = Boolean(sub && sub.status !== 'none')`); `:398-413` (plan-card actions branch on it).

**What's wrong:** for `status === 'canceled'`, `hasSubscription` is true, so every plan card renders "Switch to X via portal" and never the "Subscribe to X" checkout button — even though the backend *allows* a fresh checkout for canceled tenants (`backend/src/routes/billing.ts:306-311`: the 409 block only fires for statuses in `ACTIVE_SUBSCRIPTION_STATUSES`). A churned tenant who wants back in is funneled exclusively to the Stripe customer portal, whose default experience for a fully-canceled subscription is not a clean resubscribe flow (the in-app cancel flow only promises portal resubscription for the `cancel_at_period_end` case). Related copy nuance: `ErrorBanner`'s `SUBSCRIPTION_REQUIRED` branch unconditionally sets `noPlan: true`, so a churned *paid* customer is told "Free trial ended." — factually off (they had a plan), even though "Choose a plan" still lands them on billing.

**Concrete trigger:** cancel fully (not at-period-end), return later → billing page shows only portal buttons; no direct subscribe path.

**Fix:** treat `status === 'canceled'` like `'none'` for the plan-card CTA (`Subscribe to X` → `billingApi.checkout`), keeping the portal button for plan changes on live subscriptions.

**Duplicate check:** grepped all prior passes for "canceled" + resubscribe/subscribe CTA/billing page — no hits. **NEW.**
