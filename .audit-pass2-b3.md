## Findings

### M-1 — MEDIUM — Report highlights present the SIMULATED GEO score as a measured fact
- **File:** `frontend/components/tabs/ReportsTab.tsx:36`
- **What:** `HighlightList` renders
  `['AI visibility score', `${h.geoScore}% of AI answers mentioned your brand`]`
  with no "simulated" qualifier. `geoScore` comes from the `geo_checks`
  table — the simulated GEO checks (every GEO surface labels them
  "Simulated estimate"). The backend's own report renderings label the same
  value honestly: `reportBranding.ts:90` ("% of **simulated** AI answers
  mentioned the brand") and `:141` ("Mention rate **(simulated)**"), and
  `ReportsV2Panel.tsx:277` renders "AI visibility (simulated)" in the
  compare view. Only the v1 `ReportsTab` highlights state it as fact.
- **Trigger:** Generate a weekly report → expand it → "Key numbers" lists
  "AI visibility score — 42% of AI answers mentioned your brand". A customer
  (or their client, via the white-labeled shared report flow) reads this as
  a measured claim about real AI platforms.
- **Fix:** Same treatment as A3-M1/M-2: label the row
  "AI visibility score (simulated estimate)" with a tooltip/note matching
  the GEO tab wording. This is the same finding class pass #1 fixed on two
  other surfaces and missed here.

### L-1 — LOW — Invite-accept forces an unnecessary re-login; comment is stale
- **Files:** `frontend/app/dashboard/team/accept/page.tsx:13-18` (comment),
  `:92-97` (done-state UI: "Your session still points at your previous
  workspace — sign in once more to enter the new one.")
- **What:** The header comment says "the accept endpoint returns a fresh
  session token in the body but does not set the httpOnly session cookie, so
  after a successful accept the user signs in once more (flagged for LA)".
  That was true when written, but backend commit `345b563` ("F-09 fix: invite
  accept sets fresh bseo_token session cookie (login parity)") changed it:
  `backend/src/routes/account.ts` now calls `setAuthCookie(reply, fresh)` +
  `setCsrfCookie(reply, issueCsrfToken())`, and the same-origin proxy
  forwards `Set-Cookie` to the browser — so the user is already signed into
  the new workspace when `accept` resolves. The "Sign in to continue" step
  is pure friction and the "flagged for LA" comment is outdated.
- **Trigger:** Accept a team invite → success screen tells you to sign in
  again, even though your session is already valid for the new workspace.
- **Fix:** Update the comment; on `done`, navigate straight to
  `/dashboard` (session already switched) instead of prompting re-login.

### L-2 — LOW — Cookie-consent control is theater; privacy policy misdescribes cookies
- **Files:** `frontend/components/CookieBanner.tsx:41-50`,
  `frontend/app/legal/privacy/page.tsx:41-45` (§3 Cookies)
- **What:** The banner offers "Accept all" for "Optional analytics cookies",
  and the privacy policy states "Optional analytics cookies (only if you
  accept them in the cookie banner) help us understand aggregate product
  usage." But: no analytics script is loaded anywhere in the frontend, and
  the consent value (`bseo_cookie_consent_v1`) is written by the banner and
  **never read by any code**. Accepting changes nothing; declining changes
  nothing. For a product about to be sold, the legal document misdescribes
  actual cookie behavior (in the over-disclosing direction, but still
  false), and the consent control does not function as presented.
- **Trigger:** Any visitor clicks "Accept all" → nothing is enabled; read
  the privacy policy → told analytics cookies may run on consent, which
  never happens.
- **Fix:** Either wire real consent-gated analytics, or (simpler and honest)
  drop the "Accept all" option and reword §3 to say only essential
  (login/CSRF) cookies are used.

### L-3 — LOW — Caddy image not digest-pinned in prod compose
- **File:** `docker-compose.prod.yml:194` (`image: caddy:2-alpine`)
- **What:** Every other image in both compose files is digest-pinned
  (postgres, redis, node:24-alpine in both Dockerfiles) per S-10 container
  hardening — except the internet-facing TLS terminator. There is a TODO
  ("pin to a reviewed digest in CI before first deploy"), so this is
  acknowledged-but-open supply-chain risk on the prod edge proxy.
- **Trigger:** `docker compose -f docker-compose.prod.yml pull` on deploy day
  resolves `caddy:2-alpine` to whatever is current — a tag-mutation or
  compromised push lands silently in front of all traffic.
- **Fix:** Pin the digest now (same as the other images); don't leave it to
  a CI job that hasn't run.
