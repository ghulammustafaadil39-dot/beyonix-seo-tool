## 2. NEW findings

### NEW HIGH #1 — G5-M#1's fail-closed write is order-unsafe: `checkout.session.completed` permanently clobbers a correct `'active'` row to `'incomplete'` for real payers

**Files:** `backend/src/providers/stripe.ts:567-576` (case c), `:580-604` (upsert), `:507-516` (C-01 stale guard)

**What's wrong:** On the real Stripe path `checkout.session.completed` always takes case (c) — `data.subscription` is an unexpanded string id — and writes `status='incomplete'` **unconditionally** via `ON CONFLICT (tenant_id) DO UPDATE SET … status = EXCLUDED.status` (`:588`). The write carries no status information (the string id tells nothing), yet it overwrites whatever the earlier subscription/invoice events established — including `'active'` for a fully-paid subscriber.

The real Stripe delivery order is: `customer.subscription.created` (earlier) → `invoice.paid` → `checkout.session.completed` (later). The G5-M#1 fix comment itself acknowledges this order ("CLOBBERED a correct `'incomplete'` row written by the **earlier** `customer.subscription.created` event", `:556-562`), and a real production incident found via web search confirms Stripe delivers subscription events before `checkout.session.completed` (93 ms skew observed in the wild). Stripe does **not** guarantee webhook order, and all these events share ~the same `created` second, so the C-01 stale guard (`new Date(last).getTime() > eventAt.getTime()`, strict `>`) does not arbitrate — arrival order decides the final state.

**Concrete money-impact chain:**
1. Real customer completes a paid card checkout (Growth/Pro). Stripe charges them.
2. `customer.subscription.created(active, expanded)` → row `'active'`, `tenants.plan_id` upgraded; `invoice.paid` → G5-M#2 recovery confirms `'active'` + plan + `read_only` recompute.
3. `checkout.session.completed` arrives last (newer `created`, so the stale guard lets it through) → case (c) → row **clobbered to `'incomplete'`**. `tenants.plan_id` stays paid (the `incomplete` branch only touches `stripe_customer_id`), but the subscription row — the gate's source of truth — says `'incomplete'`.
4. No later event corrects it: no `customer.subscription.updated` fires for a steady subscription; the next `invoice.paid` is ~30 days away (and G5-M#2 is what finally heals it at renewal).
5. Worse interleaving: if `checkout.session.completed` is *processed* first, its `last_event_at` watermark makes the later-arriving (earlier-`created`) `created`/`updated`/`invoice.paid` events look stale → they are **dropped**, so even the G5-M#2 recovery never runs.
6. The trial gate masks the damage for 14 days (`tenants.trial_ends_at` signup trial still live → allowed). On day 15 the signup trial expires → **402 `SUBSCRIPTION_REQUIRED` + `read_only=TRUE`** (the gate flips it itself) and the scheduler stops the tenant's rank-check/crawl/report jobs. A paying customer is locked out of the product for ~15 days while Stripe keeps billing them → refunds, chargebacks, churn.

**Why this wasn't caught:** the pass-7 test (`backend/tests/wave4/w4-pass7-billing-fixes.test.ts`, test ii) only covers the checkout-first order — and with an artificial `created: t1+5` skew on the subscription event that **inverts the real timestamp relationship** (in reality the created event is *older* than the checkout event). The mock path (`sub_mock_` → case (a) → `'active'`) is unaffected, so dev/test never sees this; it only manifests on the real Stripe path, in production, masked for two weeks by the signup trial.

**Why HIGH:** it denies paid service to paying customers on a normal (commonly observed, in-repo-acknowledged) delivery interleaving — not an attack, not an exotic race. It is a direct regression introduced by the pass-7 G5-M#1 fix, which traded the never-payer free-access hole for a payer lockout hole. The suggested fix in the G5 report ("retrieve the subscription via the Stripe API… never overwrite a stored status with 'active' when the true status is unknown") was only half-implemented: the code fails closed for the never-payer but also **blindly overwrites a known-good `'active'` with an unknown**.

**Suggested fix (either):**
- (a) Per G5's original recommendation: when `data.subscription` is a real (non-`sub_mock_`) string id, retrieve the subscription via the Stripe API and use its true status; fail closed to `'incomplete'` only if the retrieve fails. Order-independent, no guessing.
- (b) Cheaper, no API call: a status-less event must not overwrite a live status. In the upsert: `status = CASE WHEN subscriptions.status IN ('active','trialing','past_due') THEN subscriptions.status ELSE EXCLUDED.status END` — default to `'incomplete'` only when there is no row or the row isn't live. (This composes with the E4-L-1 desired fix: the upsert still runs, so coupon redeem + billing event still fire on stale drops; only the status write becomes conservative.)

**Duplicate check:** grepped all `.audit-pass{1..7}-*.md` for `fail.closed`, `clobber`, `delivery order`, `order.*unsafe/fragile`. G5-M#1 (pass#7) describes the fix as correct; no prior pass discusses the payer-side clobber or the timestamp inversion in test (ii). **NEW.**

### NEW LOW #1 — `charge.refunded` delta computation is not atomic: concurrent refunds for the same charge can double-credit

**File:** `backend/src/providers/stripe.ts:1021-1027` (SELECT SUM) + `:1041-1050` (INSERT)

**What's wrong:** The G5-L#1 delta fix reads previous credits (`SELECT COALESCE(SUM(amount_cents),0) … WHERE starts_with(reason, 'Refund <chargeId>')`) and then inserts the delta in two separate statements with no lock. Two `charge.refunded` events for the same charge (distinct event ids — e.g. two partial refunds delivered concurrently, which Stripe does) can interleave: both read `prev = 0`, then both insert their full delta. Two partials of 500¢/1000¢ cumulative become 500 + 1000 = 1500¢ credited against a 1000¢ actual refund — the exact over-credit G5-L#1 fixed, reintroduced through concurrency.

**Impact:** LOW — `tenant_credits` are never auto-applied against invoices (summed for the admin view, tombstoned on erase, per G5), so this inflates the admin credit balance, not real payouts. Narrow window (requires concurrent delivery of same-charge refund events).

**Suggested fix:** serialize per (tenant, charge) — e.g. `SELECT pg_advisory_xact_lock(hashtext('refund:' || tenant_id || charge_id))` before the SELECT, or fold the delta into a single `INSERT … SELECT` that computes `cumulative − existing` atomically.

**Duplicate check:** G5-L#1 (pass#7) covers the sequential cumulative bug; no prior pass discusses the concurrent-interleaving residual. **NEW.**
