## 1. Pass#10 fix verification (all on main — all HOLD ✅, adversarial questions answered)

### 1a. J5-LOW-1: `$0 invoice.paid` amount guard on past_due revival — VERIFIED ✅
`providers/stripe.ts:1093` `const paidInFull = amount > 0;`, applied at `:1095`: `((curStatus === 'past_due' && paidInFull) || curStatus === 'incomplete') && invMatchesTracked`. `amount` is computed at `:1020-1022` as `Number(data.amount_paid ?? data.total ?? data.amount_due ?? 0)` — cents; `??` does not fall through on `0`, so a genuinely-$0 invoice reads `0` and a paid invoice reads its real total. Regression test `w4-pass10-fixes.test.ts:82` covers all three legs ($0 past_due blocked, positive past_due revives, $0 incomplete revives).

**Adversarial Q — does the $0-guard break any legitimate revival?** No, on all three named cases:
- **100%-off coupon on `past_due`:** the direct revival is (correctly) blocked, but it self-heals: paying the outstanding invoice — even at $0 via coupon — moves the Stripe subscription `past_due → active`, which always emits `customer.subscription.updated`; the `else` upsert branch (`stripe.ts:977-1000`) then flips the row to `active`, restores `tenants.plan_id`, and recomputes `read_only`. If other invoices remain open Stripe keeps the sub `past_due` and the block is correct. Either event order converges.
- **Trial conversions:** `trialing`/`active` never enter the revival branch (`:1094-1096` only matches `past_due`/`incomplete`/`canceled`); conversion flips via `subscription.updated`. The guard cannot touch it.
- **Credit-balance / partial-data payments:** Stripe's `amount_paid` reflects the full settled total including credit-balance application, so it is `> 0` whenever real value moved; the `??` chain (`amount_paid → total → amount_due`) only substitutes when the field is absent, not when it is `0`.

### 1b. J5-LOW-2: coupon release on same-URL return — VERIFIED ✅
`routes/billing.ts:372`: `if (couponReserved) await releaseReservation();` on the idempotent same-URL return (`:360-377`), after `ROLLBACK`. Regression test `w4-pass10-fixes.test.ts:151` covers it.

**Adversarial Q — double-redeem or lost redeem?** Neither. Slot accounting is per-request: request 1 reserved slot A and attached the coupon to Stripe session S1; request 2 reserved slot B, found the open claim, released **only slot B** (`reserved_count - 1`, floored at 0), and returned S1's URL. Slot B was never attached to any Stripe session, so it can never be redeemed — releasing it cannot create a double-redeem. Slot A is still reserved and converts to redeemed exactly once on `checkout.session.completed`, guarded by `coupon_redemptions.event_id` (`stripe.ts:743-770`). Both orderings (release-before-redeem, redeem-before-release) net to `reserved=0, redeemed=1`. One cosmetic-adjacent note (not filed): if request 2 carried a *different* coupon than request 1, the reuse hands back S1's URL without request 2's coupon applied — inherent to idempotent session reuse, pre-existing design trade-off.

### 1c. J1-LOW-1: status-aware claim steal — VERIFIED ✅
`routes/billing.ts:356-359`: `stealable = (creating && age>10min) || (open && age>25h)`; `:360` keeps 409/URL-reuse otherwise; `:381-384` deletes scoped to the claim's status. Migration `050` comment updated to match. Regression test `w4-pass10-fixes.test.ts:176` covers all three steal classes. The 25h threshold is sound: Stripe caps checkout-session `expires_at` at 24h, so `open`+>25h is definitively dead.

**Adversarial Q — does it strand any legitimate checkout?** One narrow residual, filed as NEW K5-LOW-3 below (dead-URL reuse in the 24–25h window when the `expired` webhook was lost). Otherwise no: a live `open` claim 409s or returns a usable URL; `creating`+>10min is unpayable by construction (the URL was never delivered — the crash happened before the `:432` `open` transition or before the response); `open`+>25h is definitively expired.

### 1d. J2-LOW-2: session-scoped claim release — VERIFIED ✅
`providers/stripe.ts:618-621` (completed) and `:786-789` (expired): `DELETE FROM checkout_sessions WHERE tenant_id = $1 AND (stripe_session_id = $2 OR $2 IS NULL)`. A newer claim created after a steal can no longer be wiped by an older session's completion. Mock-confirm carries no session id → NULL → tenant-wide fallback, which the code comment correctly flags as load-bearing there (mock-only). Regression test `w4-pass10-fixes.test.ts:234` covers the scoping. Residual checked: completing session whose claim row still has `stripe_session_id IS NULL` (crash between INSERT and the `open` UPDATE) leaves a `creating` row that self-heals via the 10-min steal — bounded, not filed.

### 1e. J1-LOW-2 / J2-LOW-4: `recentDunningSent` gating — VERIFIED ✅
New helper `providers/stripe.ts:447-466` (15-min window, types `invoice.payment_failed`/`subscription.past_due`, `sent` or live `sending`; **fail-open**: any query error returns `false` → duns normally). Applied at `:962` (`justMinted && !recentDunningSent`) and `:1190-1191` (no-row fallback). Regression test `w4-pass10-fixes.test.ts:287` covers the vacuous-dun-then-mint single-email case.

**Adversarial Q — does it suppress any legitimate first dun?** No. The suppressed case is exactly the one where the customer *already received* the vacuous `invoice.payment_failed` email seconds/minutes earlier for the same failure (identical subject/body — both templates render "Payment failed — please update your payment method"), and the suppressed `subscription.past_due` email would be a near-duplicate. The genuine first-failure path (no prior send in 15 min) is untouched. Cross-episode suppression (new failure <15 min after an old episode's dun) only collapses two duns 15 min apart into one — the customer was dunned, not left silent. The >15-min-late-mint case double-duns rather than suppressing (narrow, email-only, not filed).

## 3. NEW findings (3 LOW)

### K5-LOW-1 — `canceled`-revival branch has no $0 guard: a $0 `invoice.paid` revives a dead subscription to paid `active`
**File:** `backend/src/providers/stripe.ts:1128-1132` (the `else if (curStatus === 'canceled' && invSubId && invSubId === stored)` branch).

**What's wrong:** The pass#10 J5-LOW-1 fix added `paidInFull = amount > 0` to the `past_due` revival (`:1095`) but the D1-H-1 `canceled`-revival branch directly below it still revives on **any** `invoice.paid` for the tracked subscription — including a $0 one. Stripe auto-"pays" $0 invoices on finalization and emits `invoice.paid` even when the subscription is dead (a final $0 invoice after cancellation: metered/unbilled usage netting to $0, credit-balance finals, or a late-delivered/redelivered $0 invoice from the 100%-off-coupon era). The branch then flips the row to `'active'`, re-resolves the plan from the invoice price, restores `tenants.plan_id`, and recomputes `read_only` — full paid limits plus scheduler spend (`scheduler.ts` status filter passes on `'active'`) for a subscription Stripe considers terminated. The branch's own rationale ("the invoice proves the Stripe subscription is still alive") is *false* for $0 invoices: a $0 `invoice.paid` proves nothing about liveness.

**Trigger / impact:** narrower than J5-LOW-1 (flat-rate plans rarely emit post-cancel final invoices), but the impact is *permanent*, not transient: unlike the past_due case there is no Smart-Retry cycle to self-heal — no further events will ever arrive for a dead subscription, so the phantom `active` row persists until manual intervention. Also reachable via event ordering: `customer.subscription.deleted` processed before a delayed $0 `invoice.paid` for the same sub id. LOW: narrow trigger, permanent paid-without-paying.

**Fix direction:** apply the same `paidInFull` requirement to the `canceled` branch (a genuinely-alive-but-locally-canceled subscription self-heals via its ongoing `subscription.updated` events anyway, exactly as in §1a). Alternatively gate on `billing_reason`.

**Duplicate check:** grepped all `.audit-pass{1..10}-*.md` for `$0`/zero-amount discussion of the *canceled* branch — zero hits. I5 (pass#9) added the `invSubId` match to the past_due branch "like the canceled-revival branch"; J5-LOW-1 guarded only `past_due`. The canceled branch's amount dimension was never discussed. **NEW.**

### K5-LOW-2 — refund confirmation email displays the raw cent amount
**Files:** `backend/src/services/billing.ts:167` (template); `backend/src/providers/stripe.ts:1308` (`detail: { amount, invoiceId }`).

**What's wrong:** `charge.refunded` credits are computed in cents (`cumulativeRefunded`, `credited` delta — `stripe.ts:1228,1257`), and the emitted event detail passes that raw cent value straight into the customer email: `"A refund of ${e.detail?.amount ?? ''} has been processed to your payment method."` A $10.00 refund tells the customer "A refund of 1000 has been processed" — a 100× overstatement in money communication. Cosmetic (no money moves wrongly — H5-L#1 accounting is correct), but it is customer-visible and refund-shaped, so it erodes trust exactly where trust matters most.

**Fix direction:** format as dollars in the template (`(amount/100).toFixed(2)` with currency), or pass a pre-formatted string in the event detail.

**Duplicate check:** G7-G1 (pass#7) covered refund *double-emails* (notification side effect), never the amount *formatting*. Grepped all passes for "cents" display / refund template — zero hits. **NEW.**

### K5-LOW-3 — same-URL idempotent return can hand back a dead (expired) checkout session in the 24–25h window
**File:** `backend/src/routes/billing.ts:360-377` (the `claim && !stealable` URL-reuse path).

**What's wrong:** the J1-LOW-1 fix keeps 409/URL-reuse for `open` claims younger than 25h. Stripe sessions expire at most 24h after creation. If `checkout.session.expired`'s webhook was lost, a claim aged 24–25h is *not* stealable, and the reuse path returns the expired session's URL without checking liveness — Stripe renders "this checkout session has expired" and the customer cannot pay. Every retry inside the window returns the same dead URL (same-plan) or 409s (different-plan): a legitimate paying customer is blocked for up to ~1h by a phantom claim. The window is ~1h wide × lost-webhook precondition, hence LOW.

**Fix direction:** on the reuse path, verify session liveness via `stripe.checkout.sessions.retrieve` (outside the txn, before the claim check) and treat an expired/missing session as stealable; or lower the `open` steal threshold to just above 24h.

**Duplicate check:** no pass discusses post-24h URL-reuse liveness; J1's pass#10 fix proposal and the K4 pass#11 doc review cover the 25h rule's *intent* (never steal a live session), not this residual. **NEW.**
