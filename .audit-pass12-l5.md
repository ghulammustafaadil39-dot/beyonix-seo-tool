## 1. Pass#11 fix verification (all on main — all HOLD ✅)

### 1a. K5-LOW-1: `paidInFull` on the `canceled`-revival branch — VERIFIED ✅
`providers/stripe.ts:1108` computes `const paidInFull = amount > 0;` (amount = `Number(data.amount_paid ?? data.total ?? data.amount_due ?? 0)`, cents; `??` doesn't fall through on `0`); applied at `:1153` in the `else if (curStatus === 'canceled' && invSubId && invSubId === stored)` branch. Regression test `w4-pass11-fixes.test.ts:50` covers both legs ($0 stays canceled; 2900 revives) — genuine, not vacuous.

**Adversarial Q — does the $0-canceled-guard break the D1-H-1/D5-M-2 "invoice proves alive" recovery for legitimate $0 cases?** No, on every constructible case:
- **The D1-H-1/D5-M-2 scenario itself** ("payer whose Stripe retry succeeded after a local downgrade"): grace-expiry downgrades keep the row `past_due`, and a successful retry of a real invoice is `amount_paid > 0` → passes the guard. Stripe does not retry $0 invoices (auto-paid on finalization), and a 100%-off-coupon subscription never goes `past_due` on $0 invoices — so there is no legitimate $0-retry recovery to break.
- **100%-off coupon first invoice on a locally-`canceled` row:** the only way the row becomes `canceled` is `customer.subscription.deleted` for the *tracked* sub id (E4-H-2 guards superseded subs; grace-expiry keeps `past_due`). Stripe never sends `deleted` for a live subscription, so a locally-`canceled` subscription with a later $0 `invoice.paid` is a dead subscription's final-invoice artifact — blocking revival is *correct*, not a regression.
- **False-race recovery (stale `deleted` processed, sub actually alive):** an alive subscription keeps emitting `customer.subscription.updated`; the `else` upsert branch (`stripe.ts:995-1009`) unconditionally writes the incoming status and flips `canceled → active` with `grace_until = NULL`. The $0 guard touches only the `invoice.paid` path, so this self-heal is intact.
- **Worst case if the guard were ever "wrong":** the tenant pays $0 (coupon) — the failure mode is a free tenant temporarily on Starter, a support ticket, never revenue loss. No money at stake.

### 1b. K5-LOW-2: refund email formats cents via Intl; currency added to event detail — VERIFIED ✅
`services/billing.ts:141-147`: `const cents = Number(e.detail?.amount ?? 0); const cur = String(e.detail?.currency ?? 'usd').toUpperCase(); const money = new Intl.NumberFormat('en-US', { style: 'currency', currency: cur }).format(cents / 100);` — renders "$10.00". Producer `providers/stripe.ts:1329` passes `currency: (data.currency as string | undefined) ?? 'usd'`.

**Adversarial Q — does the currency fallback behave sanely when `detail.currency` is absent on old events?** Yes, on all variants (verified with node, not assumed):
- Absent/undefined/null → `?? 'usd'` → "USD" → "$10.00". ✅
- Present but garbage 3-letter code → Node's Intl is lenient (`currency:'XYZ'` formats "XYZ 10.00", no throw). ✅
- Present as empty string → `RangeError` inside the hook → `emitBillingEvent` catches (`[billing] event hook threw`) → that email is skipped, logged. **Unreachable in practice:** Stripe always emits a valid 3-letter `currency`; the producer's `?? 'usd'` never yields `''`; the only direct (non-webhook) callers are tests. Checked and dismissed — not filed.
- `$0.00` email when `credited = 0` (E4-M-2 reprocessing): unreachable — F2-L-1 event-id dedupe at webhook entry prevents a reprocessed event from reaching the credit path with the same id, and Stripe never issues two distinct events with identical cumulative totals. Checked and dismissed.
- 0-decimal currencies (JPY): `cents / 100` would show ¥1000 as "¥10". **Checked and dismissed:** the product is USD-only — no currency config exists anywhere (`plans.ts`/`config.ts` carry none; prices come from the Stripe price objects), so a non-2-decimal currency cannot occur in this deployment. Latent only if multi-currency is ever introduced.
- Process note: this is the one pass#11 billing fix with **no regression test** (no test asserts the refund email body). Cosmetic, fix verified by reading — not filed.

### 1c. K5-LOW-3: `open` steal threshold 24h — VERIFIED ✅ (fix is *stronger* than K5 claimed)
`routes/billing.ts:360-361`: `stealable = ... || (claim.status === 'open' && claimAgeMs > 24 * 60 * 60_000)`. Migration `050` comment updated to match. Regression test `w4-pass11-fixes.test.ts:136` (24h05m claim stolen, fresh URL returned) — genuine.

**Adversarial Q — does the 24h threshold steal any live session?** No:
- `claimAgeMs` is measured from the claim row's `created_at`, which is written by the `'creating'` INSERT — strictly *before* `buildCheckoutSessionParams`/`checkout.sessions.create`. The `'open'` UPDATE (`routes/billing.ts:432-436`) does **not** touch `created_at`. So steal at claim age > 24h ⇒ Stripe session age > 24h − ε.
- This code sets no custom `expires_at`/`expires_after` (`buildCheckoutSessionParams`, `stripe.ts:66-96` — verified by reading); Stripe's max checkout-session lifetime is 24h from creation ⇒ the stolen session is expired. The residual ε-race (stealing a session in its final sub-second of life) is self-correcting: the steal only deletes the claim row, and the old session's `checkout.session.completed` still processes normally via the K2-3 fallback.
- **Stronger result:** K5 framed the fix as shrinking the dead-URL window. It actually **eliminates** it: the reuse path only fires for claim age < 24h, where session age < 24h − ε < expiry — so every URL handed back by the reuse path is provably live. No liveness check needed.

### 1d. K2-3: completed-fallback DELETE for `'creating'`-NULL claims — VERIFIED ✅
`providers/stripe.ts:628-633`: when the session-scoped DELETE matches 0 rows and `completedSessionId` is real, `DELETE FROM checkout_sessions WHERE tenant_id = $1 AND status = 'creating'`. Regression test `w4-pass11-fixes.test.ts:105` — genuine (NULL-session claim cleared, subscription still created).

**Adversarial Q — can the fallback nuke a live claim?** No: it deletes only `status = 'creating'`; a live `'open'` claim is never touched. The one cross-talk case (old session's `completed` arriving while a *newer* in-flight `'creating'` claim exists — the stolen-session-paid-late shape) deletes the newer claim early, which is benign: claim rows only gate *new* checkouts (409/reuse), and the newer session's own `completed` still creates the subscription (the fallback runs again harmlessly with rowCount 0). The 10-min 409 window for that checkout is lost a few minutes early — not a finding.
