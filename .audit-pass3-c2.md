### M1 — Stuck-audit reaper can be resurrected by its own still-pending job → duplicate concurrent audits, double crawl spend
**Severity:** medium · `backend/src/scheduler.ts:195-201` + `backend/src/services/crawlJobs.ts:319`

`reapStuckAudits()` marks any audit still `'queued'` after 2h as `'failed'`. But the
corresponding BullMQ job can legitimately still be pending past 2h: the fairness
deferral in `worker.ts:withFairness` does `moveToDelayed(60s)` + `DelayedError`, which
does **not** consume a retry attempt — deferral is unbounded under sustained heavy-slot
saturation (2 slots/tenant; the weekly-crawl tick bulk-enqueues every verified site at
once, so a tenant with dozens of sites easily backlogs >2h).

When the deferred job finally acquires a slot, the worker claims the row
**unconditionally**:

```sql
UPDATE audits SET status = 'running' WHERE id = $1 AND tenant_id = $2  -- crawlJobs.ts:319, no status predicate
```

so the reaped `'failed'` row is resurrected to `'running'` → `'done'`. Worse, between
the reap and the resurrection the partial unique index
`audits_one_active_per_site` (041) no longer blocks the site, so the user — who was
just told the audit "failed (stale queued audit reaped by scheduler)" — can start a
**second** audit that runs concurrently with the zombie: double crawl work, double
`crawl_pages` budget burn, duplicate `audit_issues` rows.

**Trigger:** tenant heavy-slot saturation lasting >2h (bulk weekly-crawl tick is the
realistic driver), or a worker outage where a *different* process runs the scheduler.

**Fix:** make the claim conditional —
`... WHERE id = $1 AND tenant_id = $2 AND status = 'queued'` — and if `rowCount = 0`,
drop the job (return early / throw non-retryable) instead of resurrecting the row.
Optionally exempt reaped rows only when no live BullMQ job references the audit id.

### M2 — BYOK decrypt failure silently falls back to the operator's server LLM key (fail-open on cost)
**Severity:** medium · `backend/src/providers/llm.ts:130-145`

```ts
if (row?.llm_api_key_enc) {
  try { byokKey = decrypt(row.llm_api_key_enc) || undefined; }
  catch { /* corrupted key — fall through to account provider */ }
}
if (row?.llm_provider === 'gemini' || row?.llm_provider === 'openai') {
  return getLLM(row.llm_provider, byokKey);   // byokKey undefined → uses config.geminiApiKey/openaiApiKey
}
```

A2-H1 made provider-*selection* fail closed, but a *decrypt failure* on an explicitly
BYOK-configured tenant silently routes that tenant's generations through the
**operator's** key — the operator pays for tenant workloads and tenant prompts flow
through the operator's account, with no error surfaced. Live path:
`generateMetered()` → `getLLMForTenant()` (used by content/GEO generation).

**Trigger:** `ENCRYPTION_KEYS` rotated without running `scripts/rotate-encryption-keys.ts`
for `tenants.llm_api_key_enc`, or a corrupted row; every subsequent generation for that
tenant bills the operator.

**Fix:** when `llm_provider` is explicitly set and the BYOK key exists but fails to
decrypt, throw (e.g. 502 `LLM_KEY_UNREADABLE`, "re-enter your API key") instead of
falling back. Log loudly.

### L1 — `DB_STATEMENT_TIMEOUT_MS` also throttles the migration connection (boot-loop footgun)
**Severity:** low · `backend/src/db.ts:24-31`

The statement-timeout `SET` is applied to every pooled connection, including the one
`runMigrations()` uses (same module, same pool). The comment says operators should
"enable it for API/worker roles only", but there is no per-role scoping mechanism —
compose env is typically shared, and the one-shot `migrate` service imports the same
module. A globally-set timeout kills long migrations/index builds mid-file →
transactional rollback → boot loop.

**Fix:** skip the `SET` when running the migrate entrypoint (e.g. an explicit
`BSEO_SKIP_STATEMENT_TIMEOUT=1` for the migrate service, or apply the timeout in
`index.ts`/`worker.ts` pools rather than the shared module).

### L2 — `requireRole()` with zero roles permits any authenticated user (latent)
**Severity:** low · `backend/src/middleware/access.ts:17`

```ts
const minRank = Math.min(...allowed.map((r) => ROLE_RANK[r] ?? 99)); // Math.min() === Infinity
```

With no `allowed` roles, `minRank` is `Infinity` and `rank < Infinity` is always true —
any authenticated caller (any role, API key with no `admin` scope… actually API keys
with the `admin` scope pass the earlier branch; keys *without* it are rejected) passes.
Verified: no current callers use zero args, so this is a latent footgun, not a live hole.

**Fix:** `if (allowed.length === 0) throw new Error('requireRole requires at least one role')`
at factory time.

### L4 — Leader-election re-entry permits overlapping ticks from the same process
**Severity:** low · `backend/src/services/leaderElection.ts` (`tryAcquire` re-entry branch), `backend/src/scheduler.ts:24-44`

`onlyLeader` never calls `release()`; when a tick outlasts its cron interval, the next
firing in the *same* process hits the re-entry branch (`SET NX` fails → `GET == token`
→ `pexpire` → `true`) and runs `work()` **concurrently** with the still-running tick.
node-cron does not serialize executions, so the documented "exactly one tick executes"
holds across processes but not across overlapping firings in one process.
Blast radius is limited because the consumers claim atomically (webhook retries,
digests), but e.g. `processBillingGrace` / `runRetentionCleanup` double-running is
wasteful and the invariant is weaker than the comment claims.

**Fix:** track an in-flight flag per schedule name and skip (log) overlapping ticks, or
release the lock in `onlyLeader`'s `finally` and re-acquire fresh per tick.

### L5 — `commitUsage` CTE is atomic (verified), but commits expired reservations and doesn't cap actual ≤ reserved
**Severity:** low · `backend/src/metering.ts:356-370` (adjacent to scope; flagged per the explicit verify list)

The single-statement CTE fix from passes #1–#2 is correct and atomic. Two residual gaps:
(a) no `expires_at > now()` predicate — a reservation that expired (15-min TTL, already
excluded from `getUsage`'s hold accounting) can still be committed later, re-adding
budget that was already freed and letting concurrent callers collectively overshoot;
(b) `units = COALESCE($2, units)` accepts `actualUnits > reserved` with no limit
re-check, despite the `(<= reserved)` contract in the docstring.

**Fix:** add `AND expires_at > now()` to the CTE's UPDATE, and cap committed units at
the reserved amount (or re-check the limit when actual > reserved).

### L6 — Scheduler date-key computed per row (midnight-split, very narrow)
**Severity:** low · `backend/src/scheduler.ts:110`

The `rank-checks` tick builds the idempotency key with `new Date()` *inside* the
per-site loop. If a tick spans a UTC midnight, sites processed after midnight get a
different date key → the same site could be enqueued twice for two "days".

**Fix:** compute `const today = new Date().toISOString().slice(0, 10)` once before the loop.
