## 2. NEW findings

### NEW LOW #1 — G1-L-1 email dedupe has a check-then-act TOCTOU race: concurrent duplicate deliveries can still double-email

**Files:** `backend/src/services/billing.ts:93-121` (the `send` closure in `registerDefaultBillingHooks`); migration `049_wave4_pass7_billing_dedupe.sql`.

**What's wrong:** The fix is check-then-send-then-record: `SELECT 1 FROM notification_log WHERE event_id=$1 AND notification_type=$2 AND status='sent'` → if absent, `notify.sendEmail(...)` → `INSERT` the `'sent'` row. There is no atomic claim. The F2-L-1 scenario — a concurrent duplicate Stripe delivery whose ledger insert loses the race and is reprocessed — runs the whole handler twice in parallel. Both handlers can pass the SELECT check before either inserts, so **both send the same customer lifecycle email**; the second INSERT then fails on the partial unique index (`notification_log_event_dedupe_idx`), and the `.catch(() => {})` swallows it. The email is already out. The money paths use atomic `ON CONFLICT DO NOTHING` claims; the notification path — the very path G1-L-1 was filed for — does not.

**Concrete trigger:** Stripe redelivers an event while a crash-retry or concurrent duplicate of the same event is still mid-flight (sendEmail takes ~100ms+). Both attempts' SELECTs return 0 → two identical "Payment failed"/"Refund processed" emails.

**Why LOW:** rare window (requires overlapping duplicate processing), one extra email, no money movement, no data loss.

**Fix:** claim-first: `INSERT INTO notification_log (..., status='sending', event_id) ... ON CONFLICT (event_id, notification_type) DO NOTHING` *before* `sendEmail`; only send when `rowCount === 1`; then `UPDATE ... SET status='sent'`. (Keep the accepted semantic that a `'failed'` send should not suppress a retry: use a distinct claim status rather than reusing `'sent'`/`'failed'`.) The unique index needed for this already exists.

**Duplicate check:** grepped all `.audit-pass{1..7}-*.md` for `notification_log`, `emitBillingEvent`, `registerDefaultBillingHooks`. G1's pass#7 report describes the fix as "check before send, record the event id after send" and never discusses the concurrency race. No prior pass reports it. **NEW.**

### NEW LOW #2 — Duplicate dunning emails across distinct Stripe events for the same failed payment

**Files:** `backend/src/providers/stripe.ts:815` (`subscription.past_due` emit), `:994`/`997` (`invoice.payment_failed` emits), `backend/src/services/billing.ts:137-144` (email hook).

**What's wrong:** Both event types map to the identical email — same subject ("Payment failed — please update your payment method"), same body — and the G1-L-1 dedupe keys on `(event_id, type)`, which never fires across *distinct* events. Two sub-triggers:

(a) **Two events, one failure.** A single failed payment produces *both* `invoice.payment_failed` and `customer.subscription.updated(past_due)` → `subscription.past_due` emit (`:815`, fired unconditionally in the past_due branch, even when a grace already exists). Two distinct event ids, two distinct types → the customer gets two identical "Payment failed" emails for one failed charge.

(b) **One email per retry during grace.** The `else` branch at `:997` emits `invoice.payment_failed` on every retry while the grace is active; each Stripe Smart Retry is a distinct event id → passes the dedupe. With Stripe's 1/3/5-day retry cadence inside the 3-day grace window, a failing card produces 2–3 identical dunning emails total (plus the `:815` one from (a)).

**Why LOW:** customer-visible and trust-eroding (the same class G1-L-1 was filed for), but bounded to the grace window, no money movement, no privilege/data impact. The D1-H-1 grace-consumed case is correctly silent (`:983-986`) and E4-M-3's canceled case is correctly silent — only the in-grace duplicates remain.

**Fix:** suppress `invoice.payment_failed`/`subscription.past_due` emails while a grace is already active — i.e., email only on the grace-minting branch (`!existingGrace`), not on retries — and/or dedupe across both types per tenant per grace window rather than per `(event_id, type)`.

**Duplicate check:** grepped all `.audit-pass{1..7}-*.md` for `subscription.past_due`, "identical email", duplicate dunning. Prior passes filed state-resurrection dunning (D4-D5, E4-M-3) — different defects (newer event, wrong state; both fixed). G1-L-1 was same-event reprocessing. No pass discusses identical-email duplication across the two distinct event types or per-retry emails during grace. **NEW.**
