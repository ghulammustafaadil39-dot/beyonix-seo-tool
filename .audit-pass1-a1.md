## HIGH

### H-1. Audit double-submit / enqueue-failure leaves a permanent orphan `queued` audit → all future audits 409 forever

- **File:** `backend/src/routes/audit.ts:68-105`
- **What is wrong:** `POST /sites/:id/audits` does a non-atomic check-then-insert: it SELECTs for audits in `('queued','running')` (line 89-94), throws 409 `AUDIT_RUNNING` if found, otherwise INSERTs a `queued` row (line 98-101) and *then* enqueues the BullMQ job with a dedupe `idempotencyKey: crawl:${siteId}:${isoWeekKey()}` (line 104-108). There is no transaction and no partial unique index preventing two `queued/running` audits per site (confirmed: no UNIQUE constraint on `audits` in migrations).
- **Trigger / exploit:**
  1. **Double-click / retry:** two concurrent POSTs both pass the SELECT, both INSERT. BullMQ dedupes the *job* (same jobId), so only one audit row is ever processed; the other row sits in `status='queued'` forever → every subsequent `POST /sites/:id/audits` returns 409 `AUDIT_RUNNING` permanently. Requires DB surgery to recover.
  2. **Simpler:** if `enqueue()` throws *after* the INSERT (Redis down, `TENANT_QUEUE_RATE_LIMITED` 429 at `queues.ts:107-113`, worker unreachable), the same orphan `queued` row is left behind with the identical permanent-409 outcome — no second request needed.
- **Fix:** wrap the SELECT-check + INSERT in a transaction with `SELECT ... FOR UPDATE` on the site row (or add a partial unique index `CREATE UNIQUE INDEX ... ON audits (site_id) WHERE status IN ('queued','running')` and translate the 23505 into the 409), and on enqueue failure mark the audit row `failed` instead of leaving it `queued`. A reaper for stale `queued` audits older than N minutes is defense-in-depth.

### H-2. F-09 team roles are unenforced on all product-domain mutations — any viewer can create/delete sites, content, keywords, audits, reports

- **File:** `backend/src/routes/sites.ts:176` (site soft-delete), `content.ts:99,179,229,245,...`, `audit.ts:68,217,381,438,529`, `keywords.ts:109,130,232,...`, `ranks.ts:388`, `geo.ts:49,107,138,155`, `backlinks.ts:121,139,223,245`, `competitors.ts:73,95`, `reports.ts:68,275,351`, `onpage.ts`, `gsc.ts`, `ga4.ts:99,132` — ~48 mutating routes total.
- **What is wrong:** every one of these routes gates writes with `requireScope(...)` only. But `requireScope` (`backend/src/middleware/access.ts:66-80`) is an explicit no-op for user sessions: `if (!t?.apiKeyId) return; // user session: roles gate elsewhere`. "Elsewhere" never happens — a repo-wide scan finds **zero** uses of `requireRole`/`requireRoleOrScope` on any domain mutation route. `requireRole` is used only on account/apikeys/settings/webhooks routes. The F-09 hierarchy (owner > admin > editor > viewer) therefore does nothing for the product surface.
- **Trigger:** an invited `viewer` (or `editor`) team member can: soft-delete any site (`DELETE /sites/:id`, no role gate), change site domains, create/publish content pieces (including CMS publish to WordPress), trigger audits/crawls/rank refreshes/geo checks, delete keywords and reports, manage competitors and backlinks. Within-tenant privilege escalation → data loss and budget spend by users who should be read-only.
- **Fix:** apply `requireRoleOrScope(['owner','admin','editor'], '<resource>:write')` (the dual gate that already exists for exactly this purpose — see `routes/webhooks.ts:67`) to all mutating domain routes; keep reads open to `viewer`. Decide whether `editor` may delete sites or only owners/admins.

## MEDIUM

### M-1. Plan-limit enforcement is check-then-act everywhere (race to overspend); the atomic `reserveUsage` is dead code in production

- **File:** `backend/src/routes/sites.ts:120` (sites), `routes/keywords.ts:119` (keywords_tracked), `routes/geo.ts:81,176` (geo_checks), `routes/content.ts:126,260,362` + `routes/onpage.ts:242` + `routes/reports.ts:149` (ai_words), `routes/audit.ts:77` (crawl_pages), `services/rankJobs.ts:105`, `services/keywordCache.ts:37,76`, `services/serpSnapshots.ts:175` (assertDataBudget).
- **What is wrong:** all of these call `checkLimit`/`assertDataBudget` (a bare SELECT) and then proceed to spend. Two concurrent requests both see `used < limit` and both proceed — the classic TOCTOU. `reserveUsage()` (`backend/src/metering.ts:240`) fixes this with a per-tenant advisory xact lock, but a repo-wide grep shows it (and `commitUsage`/`cancelUsage`) is used **only in tests** — zero production callers.
- **Trigger:** fire N concurrent `POST /sites` (or keyword-track, geo-check, content-create) against a tenant at its limit; the count ends above the plan limit. For paid-data budgets (serp/keyword_metrics) the same race spends real DataForSEO money past the cap.
- **Fix:** route the choke points through `reserveUsage` + `commitUsage`/`cancelUsage` (that's what it was built for), or delete the dead code and document the accepted race.

### M-2. CSRF guard 403s legitimate API-key browser clients that also carry a session cookie

- **File:** `backend/src/middleware/csrf.ts:44-61` (registered at `backend/src/index.ts:149`)
- **What is wrong:** `csrfGuard` exempts only requests with an `Authorization: Bearer ...` header. API keys may also travel via the `x-api-key` header (`middleware/auth.ts:113-119`, and `authPlugin` checks the API key *first*, before the cookie). A browser client using `x-api-key` while also holding the `bseo_token` session cookie gets `hasSessionCookie=true, hasAuthHeader=false` → CSRF check required → 403 `CSRF_INVALID` on every mutation.
- **Trigger:** any script/browser extension using `x-api-key` auth from a browser that has an active Beyonix session — all writes fail with 403.
- **Fix:** in `csrfGuard`, treat a present `x-api-key` header like an Authorization header (exempt), since it proves non-ambient credentials.

### M-3. `checkLimit('sites')` counts soft-deleted sites — deleted sites permanently consume plan quota

- **File:** `backend/src/metering.ts:131` (`SELECT COUNT(*)::int c FROM sites WHERE tenant_id=$1` — no `deleted_at` filter)
- **What is wrong:** the site-create gate counts soft-deleted sites, but the downgrade/read-only logic (`backend/src/services/billing.ts:115`) and listings (`routes/sites.ts:133`) correctly filter `deleted_at IS NULL`. A starter tenant (1 site) that deletes its site and adds a new one is told `LIMIT_EXCEEDED` forever — there is no path to free the quota short of the 30-day hard purge. Same inconsistency for `keywords_tracked`: keywords on soft-deleted sites still count.
- **Trigger:** starter plan → delete site → `POST /sites` → 402 `LIMIT_EXCEEDED` with `used: 1, limit: 1`.
- **Fix:** add `AND deleted_at IS NULL` to the `sites` count in `checkLimit` (and consider excluding keywords belonging to soft-deleted sites from `keywords_tracked`).

### M-4. Slack dispatch validates the webhook URL then uses raw `fetch()` — DNS-rebinding TOCTOU

- **File:** `backend/src/services/notifications.ts:77-84`
- **What is wrong:** `sendSlack` calls `validateWebhookUrl()` (resolves + checks the IP at T0) and then does a plain `fetch(webhookUrl)` which re-resolves DNS at T1. `webhookDelivery.ts:143-151` fixed this exact pattern by routing through `safeFetch` (DNS pinning + per-hop re-validation); the Slack path was left on raw fetch despite the "SSRF-checked like other webhooks" comment.
- **Trigger:** a notification-rule Slack URL whose DNS flips between validation and fetch (rebinding) can make the server POST alert payloads (which may include tenant data) to an internal address.
- **Fix:** send via `safeFetch` like `webhookDelivery` does.

### M-5. Admin plan override leaves the tenant stuck in `read_only` and out of sync with `subscriptions`

- **File:** `backend/src/routes/admin.ts:139-152`
- **What is wrong:** `POST /admin/tenants/:id/plan` does `UPDATE tenants SET plan_id = $2` only. It never clears `read_only` (set by `downgradeTenant` when usage exceeded starter limits), and it never touches the `subscriptions` row — which `downgradeTenant` set to `status='canceled'`. The comment claims "the next real Stripe event will re-sync", but a canceled subscription produces no further events, and `getBillingWindow` will now read a canceled row.
- **Trigger:** support comps a lapsed tenant to `pro` via the back-office; the tenant remains in read-only mode and its usage window falls back to calendar month while `subscriptions` still says `canceled`.
- **Fix:** on override, recompute `read_only` against the new plan's limits (same check as the webhook re-activation path in `providers/stripe.ts`) and update/insert the `subscriptions` row to match.

### M-6. Checkout accepts client-controlled `trialDays` up to 90 days

- **File:** `backend/src/routes/billing.ts:28` (`trialDays: { type: 'integer', minimum: 1, maximum: 90 }`), consumed at `routes/billing.ts:143` → `buildCheckoutSessionParams` (`providers/stripe.ts:61-72`, `trial_period_days`) → `applyPaymentEvent` sets `status='trialing'` (`providers/stripe.ts:344-348`).
- **What is wrong:** any email-verified user can request the maximum 90-day free trial on any plan at checkout. Trials are a pricing decision, not a client parameter — nothing in the docs pins trial length server-side.
- **Trigger:** sign up → `POST /billing/checkout { planId: 'pro', trialDays: 90 }` → 90 days of Pro for free, repeatable per new account.
- **Fix:** remove `trialDays` from the client schema; set the trial length server-side (fixed per plan or via an admin/coupon mechanism).

### M-7. Admin tenant-detail endpoint returns the full tenant row, including the encrypted LLM API key

- **File:** `backend/src/routes/admin.ts:100-116` (`SELECT t.*, ...` then `return { ...t.rows[0], ... }`)
- **What is wrong:** `t.*` includes `llm_api_key_enc` (and `stripe_customer_id`, `telegram_chat_id`, etc.). The encrypted key is shipped to the admin browser on every tenant-detail view. It is encrypted, but ciphertext in the browser is unnecessary exposure (offline attacks if the key is ever weak, and it violates the codebase's own "encrypted secrets never leave the API" posture — cf. `services/sites.ts` `toPublicSite` which explicitly strips `gsc_refresh_token_enc`).
- **Trigger:** any platform-admin session (or XSS in the admin UI) harvests every tenant's encrypted LLM keys.
- **Fix:** select explicit columns and never return `llm_api_key_enc` (mirror `toSettings` in `routes/settings.ts` which returns only `llm_key_set`).

## LOW

### L-1. Backlink CSV upload does up to 5000 sequential single-row INSERTs in the request handler

- **File:** `backend/src/routes/backlinks.ts:151-158`
- **What is wrong:** the per-link loop issues one `INSERT ... ON CONFLICT` per row — up to 5000 DB round trips inside a single HTTP request (plus `rescoreToxicLinks` afterwards). A large GSC export risks gateway/request timeouts mid-import (partial import, no resumability).
- **Fix:** batch multi-row INSERT (the codebase already does this for `insertIssues` in `services/crawlJobs.ts`), or move to a background job.

### L-2. `GET /metrics` is unauthenticated and exposes aggregate provider spend

- **File:** `backend/src/routes/metrics.ts:57` (`liveMetrics` sums `provider_spend` by provider, last 30 days)
- **What is wrong:** deliberate per the file comment, but aggregate DataForSEO/LLM spend is competitively sensitive business intelligence available to anyone who can reach the endpoint. Prometheus scrapers can use basic-auth or an IP allowlist.
- **Fix:** gate `/metrics` (and consider whether `/status` needs it too).

### L-3. Docs vs code: error envelope shape

- **File:** `CONTRACTS.md:239` vs `backend/src/errors.ts:21`
- **What is wrong:** the contract documents errors as `{ error: { code, message, ...extra } }`; the code (pinned by `tests/n-a1-2.test.ts`) returns `{ ok: false, error: { code, message, ... } }`. The extra `ok` wrapper is additive and intentional, so this is a doc bug, not a code bug.
- **Fix:** update CONTRACTS.md §5 to the pinned `{ ok: false, error: {...} }` shape.

### L-4. Dead code shipped in production

- `reserveUsage` / `commitUsage` / `cancelUsage` (`backend/src/metering.ts:240,302,313`) — zero production callers, tests only (related to M-1: the atomic path exists but is unused).
- `paged` (`backend/src/pagination.ts`) — no callers anywhere; only `paginate` is used.
- `GeoEngine` (`backend/src/services/geoService.ts`) — no references outside its own file.
- `needsRankCheck` (`backend/src/services/rankJobs.ts`) — referenced only in `tests/p3.test.ts`.

### L-5. Latent: `u(req)` (`"apikey:<id>"`) passed into UUID columns

- **File:** `backend/src/routes/account.ts:311-312` helper, call sites `account.ts:336,364,402(invited_by),417,461,654,684,699,734,943`
- **What is wrong:** for API-key callers `req.tenant.userId` is the string `"apikey:<uuid>"`, which Postgres rejects for UUID columns (`activity_log.user_id`, `team_invitations.invited_by`) → 500. Currently **unreachable**: every one of these call sites sits behind `requireRole(...)`, which rejects API keys outright (the `admin` scope is unmintable). The safe pattern (`actorUserId(req)` → null for keys) is already used in `routes/apikeys.ts` and `routes/admin.ts`.
- **Fix:** switch these call sites to `actorUserId(req)` so a future route without `requireRole` doesn't 500.

### L-6. `PATCH /settings` accepts an empty-string `llm_api_key`

- **File:** `backend/src/routes/settings.ts:33` (`llm_api_key: { type: 'string', maxLength: 4000 }`), written at line 78.
- **What is wrong:** an empty string encrypts and stores fine, flipping `llm_key_set` to true while no usable key exists — BYOK silently "configured" with nothing.
- **Fix:** `minLength: 1`, or treat `''` as "clear the key".
