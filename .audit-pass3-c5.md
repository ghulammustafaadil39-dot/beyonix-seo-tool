# Hostile Audit — Pass #3 — C5 (Billing / Metering Specialist)

**Scope:** `backend/src/plans.ts`, `metering.ts`, `services/billing.ts`, `providers/stripe.ts`,
`routes/billing.ts`, `routes/admin.ts` (plan override), `services/llmMetered.ts`, `services/fairness.ts`,
coupon flow (`billing_coupons`), webhook handling, dunning / read-only / downgrade paths, all
`checkLimit` / `reserveUsage` call sites.

**Method:** read-only code trace. Three money flows traced end-to-end in code (see §Traces).
No servers started, no files modified.

**Verdict: NOT clean.** 1 high, 6 medium, 5 low findings. Nothing is marked "verified".

---

## Findings

### HIGH

#### H-1 — Coupon `max_redemptions` is not enforced on the actual discount (validate-then-attach race)
- **Files:** `routes/billing.ts:56-70` (`validateCoupon`), `providers/stripe.ts:85-99`
  (`resolveStripeCoupon`), `providers/stripe.ts:433-447` (redemption at `checkout.session.completed`)
- **What's wrong:** `validateCoupon` is a plain `SELECT` with no lock and no reservation. The Stripe
  discount is attached to the subscription at checkout creation (`subscription_data.discounts`,
  built from the resolved Stripe coupon id). The local cap is only enforced later, at
  `checkout.session.completed`, via an atomic `UPDATE … WHERE redeemed_count < max_redemptions` —
  which merely stops the *counter* from incrementing; the Stripe-side discount was already granted
  and is never revoked.
- **Trigger:** admin creates coupon `LAUNCH50` with `max_redemptions = 10` (SQL — there is no coupon
  admin API). 50 users `POST /billing/checkout` with `couponCode: "LAUNCH50"` while
  `redeemed_count < 10` — all pass validation, all get Stripe subscriptions with the discount
  attached. All 50 complete payment. The redemption `UPDATE` increments the counter to 10 and then
  just `console.warn`s for the remaining 40 — who keep the discount. Cap overshoot is unbounded.
- **Fix:** reserve a redemption slot at checkout time under the `billing_coupons … FOR UPDATE` lock
  already taken in `resolveStripeCoupon` (increment a `reserved_count`, release on session expiry /
  failure), or re-validate-and-increment atomically inside the same transaction before creating the
  Stripe session.

### MEDIUM

#### M-1 — `invoice.paid` records `amount_due_cents = 0` for every paid invoice
- **File:** `providers/stripe.ts:555`
  (`const amount = Number(data.amount_due ?? data.amount_paid ?? 0);`)
- **What's wrong:** On Stripe's `invoice.paid` event the invoice is fully paid, so `amount_due` is
  `0` — and `??` does not fall through on `0`. Every paid invoice is stored with
  `amount_due_cents = 0`. (`amount_paid` / `total` hold the real figure.) The `/billing/invoices`
  ledger and any revenue reporting built on it understate revenue to zero.
- **Trigger:** any successful subscription payment → `invoice.paid` webhook → row inserted with
  `amount_due_cents = 0`, `status = 'paid'`.
- **Fix:** use `data.amount_paid ?? data.total ?? data.amount_due ?? 0` for paid invoices (or branch on
  event type: paid → `amount_paid`, failed → `amount_due`).

#### M-2 — Portal plan change with unconfigured price silently limits a paying customer to Starter
- **File:** `providers/stripe.ts:509`
  (`const effectivePlan = planFromEvent ?? (storedPlan && isPlanId(storedPlan) ? storedPlan : 'starter');`)
- **What's wrong:** If a customer upgrades via the Stripe customer portal and the corresponding
  `STRIPE_PRICE_*` env var is missing/stale, `planIdFromStripePrice` returns `null`, subscription
  metadata has no `planId` (portal changes don't carry our metadata), and the fallback chain lands
  on `'starter'`. `tenants.plan_id` is then overwritten to `starter` while Stripe bills the higher
  price. There is no log/alert on the unresolvable price.
- **Trigger:** ops creates/rotates a price in the Stripe dashboard without updating env; customer
  upgrades Starter → Pro in the portal; `customer.subscription.updated` arrives with an unknown
  price id → tenant charged Pro, limited to Starter quotas.
- **Fix:** when the price id is unresolvable, keep the stored plan (don't downgrade to starter),
  emit a loud log + admin alert, and/or resolve unknown prices via the Stripe API as a fallback.

#### M-3 — Global provider-spend *cents* cap can never fire (all spend recorded at cost 0)
- **Files:** `services/providerGuard.ts:33-41` (`assertGlobalProviderBudget`),
  `services/keywordCache.ts:43,86`, `services/serpSnapshots.ts:119,124`,
  `services/keywordService.ts:431` (all call `recordProviderSpend(…, 0)`)
- **What's wrong:** every `recordProviderSpend` call passes `costCents = 0` — no caller prices units.
  The global circuit trips on `costCents >= capCents OR units >= capUnits`. If ops configures only
  `GLOBAL_PROVIDER_DAILY_CAP_CENTS` (the natural dollar-denominated knob), the guard never fires and
  real DataForSEO spend is unguarded. The code comment acknowledges cost is 0, but the failure mode
  is silent.
- **Trigger:** set `GLOBAL_PROVIDER_DAILY_CAP_CENTS=500000`, leave `GLOBAL_PROVIDER_DAILY_CAP_UNITS=0`
  → `assertGlobalProviderBudget` returns without throwing no matter how much is spent.
- **Fix:** price DataForSEO units at record time (add a price table per feature), or make startup fail
  loudly when a cents cap is configured but no pricer is present.

#### M-4 — `commitUsage` does not clamp `actualUnits` to the reserved amount (limit overshoot)
- **File:** `backend/src/metering.ts:336-371` (`commitUsage`; `units = COALESCE($2, units)`)
- **What's wrong:** the reservation holds `estimate` units of budget, but commit writes whatever
  `actualUnits` the caller reports — including more than reserved. The atomic guarantee covers the
  estimate, not the commit.
- **Trigger:** `generateMetered` (`services/llmMetered.ts:57`) reserves `maxWords ?? 2000` ai_words;
  if the provider returns more words than `maxWords`, `commitUsage(reservationId, res.words)` records
  the larger figure. Concurrent generations can therefore push `ai_words` usage past the plan limit
  by the overshoot margin each.
- **Fix:** clamp in `commitUsage` (`LEAST($2, units)`) and surface the clamp, or re-check the limit
  when `actualUnits > reserved`.

#### M-5 — Read-only tenant cannot delete/untrack excess resources — the only documented escape is blocked
- **Files:** `middleware/auth.ts:259-283` (`enforceTenantState`), `routes/sites.ts:197`
- **What's wrong:** `enforceTenantState` blocks `POST/PUT/PATCH/DELETE` on all product routes for
  read-only tenants (allowlist is only billing/admin/account/apikeys/settings/auth/webhooks). The
  `READ_ONLY_MODE` error tells the tenant to "Upgrade your plan or **remove excess resources**" —
  but `DELETE /api/v1/sites/:id` and keyword untrack (`PATCH`) are blocked, so self-serve recovery
  is impossible. Only an upgrade (or platform admin) clears the state.
- **Trigger:** tenant downgraded to Starter with 3 sites (over the 1-site limit) → `read_only=true`
  → `DELETE /api/v1/sites/<id>` → `403 READ_ONLY_MODE`. Stuck until they pay or contact support.
- **Fix:** allow destructive/downward mutations that *reduce* usage (site delete, keyword untrack /
  delete) while read-only, or change the error message to not promise an impossible path.

#### M-6 — Local coupon codes can collide in the Stripe `bseo_` namespace (wrong discount attached)
- **File:** `providers/stripe.ts:190`
  (`` `bseo_${def.code.toUpperCase().replace(/[^A-Z0-9]/g, '')}` ``)
- **What's wrong:** sanitization strips non-alphanumerics before namespacing, so distinct local codes
  like `SAVE-20` and `SAVE_20` (or `SAVE20`) all map to Stripe coupon `bseo_SAVE20`. `ensureCoupon`
  retrieves the existing Stripe coupon idempotently — the second code silently inherits the first
  code's discount terms. There is no uniqueness guard on the sanitized form.
- **Trigger:** create `WELCOME10` (10% off) then `WELCOME-10` (50% off) via SQL → both resolve to
  `bseo_WELCOME10` → 50%-off redemptions actually apply 10% (or vice versa, whichever was created
  first wins).
- **Fix:** validate at creation that the sanitized Stripe id is unique (unique index on the derived
  id or reject codes that collide after sanitization); store the mapping and fail loudly on collision.

### LOW

#### L-1 — `recomputeReadOnly` / `downgradeTenant` count keywords on soft-deleted sites
- **Files:** `services/billing.ts:113-119`, `services/billing.ts:138-144`
- **What's wrong:** both count `keywords WHERE tracked=TRUE` without excluding keywords whose site
  is soft-deleted, while `checkLimit('keywords_tracked')` (`metering.ts:129-134`) explicitly excludes
  them (A1-M3). A tenant whose only tracked keywords live on deleted sites can be wrongly flagged
  `read_only=true` on downgrade/reactivation.
- **Fix:** add the same `NOT EXISTS (… sites … deleted_at IS NOT NULL)` predicate.

#### L-2 — `checkout.session.completed` grants the paid plan before payment is confirmed
- **Files:** `providers/stripe.ts:407-455`; `providers/stripe.ts:508-509` (`'incomplete'` falls into
  the active branch of `customer.subscription.updated`)
- **What's wrong:** the plan is activated on session completion without checking the subscription's
  payment status. A subscription in `incomplete` (first payment failed) still yields paid limits;
  exposure is bounded only by the later `invoice.payment_failed` → 3-day grace → downgrade chain,
  which depends on that webhook being delivered.
- **Fix:** treat `incomplete` like `past_due` (grace, not full activation), or gate plan activation on
  the subscription status.

#### L-3 — Deactivated coupons are still honored for in-flight checkouts
- **File:** `providers/stripe.ts:438-444` (redemption `UPDATE` has no `active` predicate)
- **What's wrong:** `validateCoupon` checks `active` at checkout time, but redemption at
  `checkout.session.completed` only checks the `max_redemptions` predicate. A coupon deactivated
  between checkout creation and payment completion is still redeemed (and the Stripe discount was
  already attached at session creation regardless).
- **Fix:** add `AND active` to the redemption `UPDATE`; note the Stripe-side discount attached at
  session creation can't be revoked locally — document or cancel it via API.

#### L-4 — Mock webhook replayable within the 300s tolerance when the payload lacks an event id
- **File:** `providers/stripe.ts:196-253` (`verifyMockWebhookEvent`); `routes/billing.ts:137-161`
- **What's wrong:** the `stripe_webhook_events` idempotency ledger only dedupes when `eventId` is
  present. `signMockWebhookEvent` doesn't include one; a mock payload without a top-level `id` can
  be replayed within `MOCK_WEBHOOK_TOLERANCE_SEC` and applied twice (e.g. double coupon redemption
  counting). Dev/test only — mock routes are disabled in production.
- **Fix:** require/assign an event id on the mock path, or keep a short-lived seen-signature cache.

#### L-5 — `checkLimit('sites')` ignores reservation holds that `reserveUsage` counts
- **Files:** `metering.ts:124-128` vs `metering.ts:276-296`
- **What's wrong:** `reserveUsage` for kind `sites`/`keywords_tracked` counts unexpired `reserved`
  holds; the plain `checkLimit` pre-flight for the same kinds counts only committed rows. Any future
  (or missed) `checkLimit`-as-gate path disagrees with the atomic path by the in-flight hold amount.
  Currently all site/keyword creation goes through `withUsageReservation`, so this is latent.
- **Fix:** make `checkLimit` count holds too, or remove the divergent pre-flight.

## Money-flow traces (end-to-end in code)

### (1) Signup → trial → paid → cancel → read-only
- **Signup:** `routes/auth.ts:169,267` → `tenants.plan_id = 'starter'` (migration default), no
  subscription row. Starter quotas apply immediately (50 keywords, 5k AI words, 500 serp checks/mo).
- **Trial:** effectively disabled — `PLANS.*.trial_days = 0` (`plans.ts:13,27,41`); checkout
  (`routes/billing.ts:145`) takes trial length server-side; no trial path is reachable.
- **Paid:** `POST /billing/checkout` (verified email, idempotent, blocks double-subscribe at
  `routes/billing.ts:218-256`) → Stripe session with `subscription_data.metadata={tenantId,planId}`
  → `checkout.session.completed` (`providers/stripe.ts:407`) upserts `subscriptions`, sets
  `tenants.plan_id` + `read_only=FALSE`, redeems coupon atomically.
- **Cancel:** customer portal → `customer.subscription.deleted` → `downgradeTenant`
  (`services/billing.ts:135`): `plan_id='starter'`, `read_only` iff over starter limits; data never
  deleted. Failed payments go `past_due` → 3-day grace (`graceDeadline`) → daily
  `processBillingGrace` (`scheduler.ts:143`) downgrades on expiry.
- **Read-only:** `enforceTenantState` (`middleware/auth.ts:259`) blocks product mutations; billing/
  admin/account stay writable. **Gap:** workers (rank/crawl/content/geo jobs) never consult
  `read_only` — but the tenant is legitimately on the Starter plan at that point, so continued
  spend is bounded by Starter quotas (design note, not a bypass). **Gap M-5:** the tenant cannot
  delete excess resources to exit read-only themselves.

### (2) Coupon create → redeem → Stripe mapping
- **Create:** no API exists — coupons are inserted via raw SQL into `billing_coupons`
  (`migrations/010_billing_completeness.sql:48`); `stripe_coupon_id` column added by
  `migrations/042_wave4_claims.sql:11`. (Ops gap: no admin UI/route to create, deactivate, or
  audit coupons.)
- **Redeem (checkout):** `validateCoupon` (active + cap check, no lock) → `resolveStripeCoupon`
  (`FOR UPDATE` lock, idempotent `ensureCoupon` → `bseo_<CODE>`, id stored back) → Stripe session
  created with `discounts: [{ coupon: stripeCouponId }]`.
- **Redeem (completion):** atomic `UPDATE … redeemed_count + 1 WHERE redeemed_count < max_redemptions`.
- **Findings:** H-1 (cap race — the money bug), M-6 (namespace collision), L-3 (deactivation gap).

### (3) Usage event → metering → limit enforcement
- Paid choke points use reserve → work → commit(actual)/cancel: `keywordCache.getKeywordMetrics` /
  `getSerp`, `serpSnapshots`, `geoService` (per-platform), `llmMetered.generateMetered`,
  `routes/sites.ts`, `routes/keywords.ts` — all via `withUsageReservation`, serialized per-tenant by
  `pg_advisory_xact_lock`, holds counted in `getUsage` so concurrent callers can't overspend.
  `commitUsage` is a single-statement CTE (flip + usage_events insert), idempotent via
  `status='reserved'` predicate; reservations expire after 15 min.
- **Residual races:** M-4 (over-commit past the reservation); crawl path still uses
  check-then-act `checkLimit` + `recordUsage` (`services/crawlJobs.ts:334,425,500`) — bounded quota
  overshoot only (own infra, no paid spend); `assertDataBudget` in `rankJobs.ts:98` is an intentional
  pre-flight, atomic enforcement lives per-call inside `getSerpSnapshot`.
- **DataForSEO overspend paths:** per-tenant budgets enforced at the single choke point
  (`keywordCache`); global daily circuit (`providerGuard.ts`) exists but M-3 neuters the cents knob;
  all provider spend is recorded with `cost_cents = 0`, so per-tenant *cost* tracking is units-only.

## Price → plan map coverage
`planIdFromStripePrice` (`providers/stripe.ts:16-41`) covers all six catalog prices: monthly
(`STRIPE_PRICE_STARTER/GROWTH/PRO` via frozen config + live env) and annual
(`STRIPE_PRICE_*_ANNUAL` via live env). Unknown/empty ids return `null` and callers fall back
(metadata → stored plan → starter) without ever writing garbage to `tenants.plan_id`. Coverage is
complete; the residual risk is M-2 (silent wrong-plan on unconfigured price).

## Top 3
1. **H-1 — coupon `max_redemptions` unenforced on the real discount.** Concurrent checkouts all pass
   the lock-free validation, all get the Stripe discount attached, and the atomic increment at
   completion only caps the local counter. A limited coupon can be honored without bound.
2. **M-1 — paid invoices recorded at $0.** `data.amount_due ?? data.amount_paid` picks `0` on
   `invoice.paid` (amount_due is 0 post-payment), so the invoice ledger shows 0¢ for every successful
   payment — revenue reporting is wrong from day one.
3. **M-3 — the dollar-denominated global DataForSEO circuit can never trip.** Every
   `recordProviderSpend` call passes cost 0, so `GLOBAL_PROVIDER_DAILY_CAP_CENTS` is a dead knob;
   only the units cap works. If ops relies on the dollar cap, paid-data overspend is unguarded.

## Explicitly checked and not flagged
- Webhook signature verification (real Stripe via `constructEvent`; mock via HMAC + 300s tolerance,
  disabled in production); idempotency ledger inserts event id before processing; ordering guard via
  `last_event_at` watermark with `charge.refunded` correctly exempted (doesn't mutate subscription
  state); stale events marked processed, not errors.
- Downgrade never deletes data; grace-period dunning flow (3 days) is coherent end-to-end.
- `planIdFromStripePrice` never writes unknown plans; checkout schema rejects client-controlled
  `trialDays` (`additionalProperties: false`); mock-confirm is auth'd, tenant-scoped, and
  non-production only; portal route requires owner/admin or `billing:write`.
- Advisory-xact-lock metering design is sound (no lock held across work — reservation commits before
  `work()` runs, so nested `generateMetered` inside geo checks cannot deadlock).
