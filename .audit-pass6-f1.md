## NEW findings

### F1-M-1 — MEDIUM — Scheduler still counts `incomplete` as a live subscription; the E4-M-1 fix never reached `scheduler.ts`, re-opening rolling free scheduled spend via never-funded checkouts

**Files:** `backend/src/scheduler.ts:60` (`enqueueForVerifiedSites`), `backend/src/scheduler.ts:113` (rank-checks query); contrast `backend/src/middleware/requireSubscription.ts:33`.

**What's wrong:** The pass#5 E4-M-1 fix removed `'incomplete'` from `BILLABLE_SUBSCRIPTION_STATUSES` in the route gate (`['active','trialing','past_due']`) with the explicit rationale: *"an incomplete subscription means the first payment never succeeded (async payment pending). Counting it as billable enables rolling free access via never-funded checkouts."* But the E4-H-1 scheduler fix (committed 5 minutes earlier, 23794db) hardcodes its own copy of the liveness list in **two** SQL queries:

```sql
OR sub.status IN ('active', 'trialing', 'past_due', 'incomplete')
```

— and the later E4-M-1 commit never updated it. Two parallel definitions of "live subscription" now disagree, and the scheduler's is the permissive one.

**Concrete trigger (rolling, verified against the code):**
1. `POST /auth/signup` → trial runs 14 days → expires, no subscription.
2. `POST /billing/checkout` (deliberately ungated — the subscribe path) with a payment method that never completes → webhook records the subscription as `incomplete` (`stripe.ts:541-547`, "WITHOUT granting paid limits").
3. Route layer: 402 `SUBSCRIPTION_REQUIRED` (correct — E4-M-1 closed this). **Scheduler layer: `sub.status='incomplete'` matches the filter → all 8 scheduled spend jobs keep running** — weekly crawl, daily rank checks, weekly reports, daily light checks, monthly keyword refreshes, weekly geo checks, weekly backlink sweeps, weekly domain reverifies. Real DataForSEO + LLM budget, zero revenue.
4. The attacker simply never touches a gated route (which would 402 and flip `read_only=TRUE`, and the scheduler also filters `t.read_only = FALSE`) — the route layer being closed is no defense here; this is pure provider-budget griefing.
5. ~23h later Stripe auto-expires the incomplete subscription (the codebase itself documents this: `billing.ts:62-64` "expires after 23h") → webhook `incomplete_expired` → `downgradeTenant` → status `'canceled'` → `'canceled'` is **not** in the checkout block list (`billing.ts:57`) → new checkout allowed → new `incomplete` → repeat indefinitely. One checkout request per ~23h buys another ~23h of scheduled spend.

Supporting weakness: the webhook grants `grace_until` to `incomplete` rows (`stripe.ts:691-699`), but `processBillingGrace` (`services/billing.ts:202-217`) only processes `status='past_due'` — so if the operator's webhook endpoint is ever down/misconfigured, the incomplete window (and the scheduler spend) extends past 23h with no local backstop.

**Why MEDIUM not HIGH:** requires sustained active attacker effort (a checkout per ~23h cycle); each cycle is bounded; the route layer is closed so the attacker gets no product value — it's cost-griefing, not data theft. But it directly re-opens the exact attack class E4-M-1 was filed to kill, through the exact surface E4-H-1 was filed to gate.

**Fix:** don't keep two lists. Either import `BILLABLE_SUBSCRIPTION_STATUSES` into `scheduler.ts` (it's exported) or drop `'incomplete'` from both scheduler queries. Consider also having `processBillingGrace` (or the scheduler filter) treat `incomplete` rows with expired `grace_until` as dead.

**Duplicate check:** grepped all prior passes for `incomplete` + scheduler/liveness/filter. E4-M-1 covered only the route gate; E4-H-1's fix predates E4-M-1 and no pass compared the two lists. **NEW** (a fix-commit sequencing miss).

### F1-L-2 — LOW — The E4-M-2 webhook fix (reprocess crashed events) introduces a double-processing window: crash-retry or concurrent delivery double-redeems coupons

**File:** `backend/src/providers/stripe.ts:461-472` (the E4-M-2 fall-through).

**What's wrong:** Before the fix, a redelivery that lost the `INSERT` race was always swallowed as a duplicate (safe, but crashed events were lost forever). After the fix, the loser does `SELECT processed_at` and **reprocesses the full handler** when it's NULL — which is also true while the winner is *still processing*. Two consequences:

1. **Crash-retry double-apply (the realistic one):** winner crashes *after* side effects (subscription upsert + coupon redeem) but *before* `markProcessed`. The retry finds `processed_at IS NULL` and reprocesses. The subscription upsert is idempotent (`ON CONFLICT DO UPDATE`), but the coupon redeem is not:
   ```sql
   UPDATE billing_coupons SET redeemed_count = redeemed_count + 1, reserved_count = GREATEST(reserved_count - 1, 0)
   WHERE code = $1 AND active AND (max_redemptions IS NULL OR redeemed_count < max_redemptions)
   ```
   → `redeemed_count` over-counts by 1 per crash-retry, `reserved_count` double-decrements (floored at 0), plus duplicate `billing_event` audit rows. Pre-fix, this exact crash sequence counted the coupon exactly once.
2. **Concurrent delivery:** Stripe doesn't normally deliver the same event twice simultaneously, so this needs a manual replay colliding with a Stripe retry — narrow.

The fix's benefit (crashed events no longer lost) outweighs the cost, but the trade is real and new: the old code had a lost-event bug; the new code has a double-apply bug. LOW because the window is narrow (crash must land between side effects and `markProcessed`) and the damage is bounded (one coupon slot, duplicate audit rows — `invoice.paid`/`payment_failed`/`downgradeTenant` paths are all idempotent).

**Fix:** make the redeem idempotent on the event id (e.g., a `coupon_redemptions(event_id)` guard table), or `SELECT … FOR UPDATE` the ledger row before deciding to reprocess.

**Duplicate check:** E4-M-2 filed the original lost-event bug; no pass discusses the reprocess race. **NEW** (introduced by the fix).

### F1-L-3 — LOW — The E4-M-4 fix (checkout ignores admin-override rows) re-opens double-billing when an admin overrides a tenant that has a *live* Stripe subscription

**Files:** `backend/src/routes/admin.ts:181-216` (plan override), `backend/src/routes/billing.ts:306-311` (E4-M-4 checkout check).

**What's wrong:** The E4-M-4 fix changed the checkout block to require `hasStripeSub` (`stripe_sub_id IS NOT NULL`) so a comped tenant (admin row, `stripe_sub_id=NULL`, status `'active'`) can start a real subscription. But the admin override itself (`POST /admin/tenants/:id/plan`) does **no check for a live Stripe subscription** — it "changes OUR plan record without touching Stripe" and unconditionally overwrites the subscriptions row with `stripe_sub_id = NULL, status = 'active'` (`admin.ts:198-208`).

So: admin overrides a tenant that *has* a live, paying Stripe subscription (support comp, migration — no malice needed) → the local evidence of the real subscription is destroyed, the real Stripe subscription **keeps billing the customer with no local record** (its webhook events now hit the E4-H-2 supersede guard and are ignored) → and checkout is now *allowed* (E4-M-4) → second Stripe subscription → customer double-billed. Before bd6fbff, the checkout block (`status='active'` regardless of `stripe_sub_id`) at least prevented the second subscription (at the cost of the dead-end E4-M-4 was filed for). The fix traded the dead-end for this footgun without guarding the transition.

LOW because it requires a platform-admin action to set up (admins are fully trusted and could already cause harm via DB), and the harm is accidental rather than exploitable by tenants.

**Fix:** refuse (or require explicit `cancelStripe: true` for) a plan override while the tenant has a live Stripe subscription — or cancel/pause the Stripe sub as part of the override.

**Duplicate check:** E4-M-4 filed the dead-end; no pass discusses override-of-a-live-sub. **NEW** (introduced by the fix).
