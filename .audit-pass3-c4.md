## HIGH

### H1 — Prod backup sidecar can never take a backup (silent data-loss exposure)
- **File:** `docker-compose.prod.yml` (`backup` service, env block) + `backend/scripts/backup.sh:18`
- **What's wrong:** The `backup` service sets only `PGPASSWORD`, `BACKUP_S3_BUCKET`,
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`. It does **not** set `DATABASE_URL`
  (nor `PGHOST`/`PGUSER`/`PGDATABASE`). But `backup.sh` hard-requires it:
  `: "${DATABASE_URL:?DATABASE_URL must be set}"` with `set -euo pipefail`, so the
  script exits 1 immediately. The sidecar entrypoint
  `while true; do sleep 86400; /usr/local/bin/backup.sh ...; done` swallows the
  failure and loops forever — no dump is ever written, and nothing alerts the
  operator. (Even if it got past the guard, `PGHOST` unset would point `pg_dump`
  at the sidecar's own localhost, not the `postgres` service.)
- **Concrete trigger:** First night after a prod deploy → `pgbackups` volume
  stays empty; a restore request per RUNBOOK ("Backups & restore") finds
  nothing to restore. Meanwhile RUNBOOK and the compose comment promise a
  "nightly pg_dump" and the operator has no reason to check.
- **Suggested fix:** Add to the `backup` service env:
  `DATABASE_URL: postgres://bseo:${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}@postgres:5432/bseo`
  (same pattern the api/worker/migrate services use), and/or add a loud failure
  (log + exit non-zero loudly / notify) instead of the silent retry loop.

## MEDIUM

### M1 — Caddy image unpinned in prod compose (floating tag on the TLS terminator)
- **File:** `docker-compose.prod.yml:186` — `image: caddy:2-alpine` (the only
  image in either compose file without a `sha256:` digest)
- **What's wrong:** All other images are digest-pinned (postgres, redis, node in
  both Dockerfiles). The in-file comment admits the digest "MUST be pinned at
  deploy time" — i.e. as committed, a prod deploy today pulls a floating tag
  for the internet-facing TLS terminator, the highest-value supply-chain
  target in the stack. The documented-but-unfixed state does not protect a
  deploy that happens before someone remembers to run the pinning ritual.
- **Concrete trigger:** `docker compose -f docker-compose.prod.yml up --build`
  → Docker resolves `caddy:2-alpine` to whatever the tag points to at that
  moment (mutated tag or compromised push ships silently).
- **Suggested fix:** Run the documented `docker pull` + `docker inspect`
  digest lookup, commit `caddy:2-alpine@sha256:<digest>`, delete the ritual
  comment.

### M2 — README Docker quick-start contradicts the compose `:?` guards
- **File:** `README.md` ("Quick start (Docker)"): *"at minimum set JWT_SECRET
  (everything else can stay empty = mock mode)"* → `docker compose up --build`
- **What's wrong:** `docker-compose.yml:15` (and the redis command / api-worker
  `DATABASE_URL`/`REDIS_URL` refs) uses `${POSTGRES_PASSWORD:?…}` and
  `${REDIS_PASSWORD:?…}` — compose **fails fast** unless those two are set.
  "Everything else can stay empty" is false, and `JWT_SECRET` itself is not
  even required for a dev boot (NODE_ENV=development + config.ts dev default).
  RUNBOOK's wording ("fill in EVERY value; compose fails fast on :? guards")
  is accurate; README is the stale one.
- **Concrete trigger:** New operator follows README → immediate cryptic
  `set POSTGRES_PASSWORD in .env` compose error; trust in the docs erodes on
  the first command.
- **Suggested fix:** Change the README block to: set `POSTGRES_PASSWORD` and
  `REDIS_PASSWORD` (compose requires them), `JWT_SECRET` optional in dev.

### M3 — Caddyfile.prod: `APP_HOST`/`API_HOST` both default to `localhost`
- **File:** `Caddyfile.prod` — `{$APP_HOST:localhost}` and `{$API_HOST:localhost}`
- **What's wrong:** Compose fails fast only on the DB passwords. An operator
  who sets those but skips `APP_HOST`/`API_HOST` (both look optional due to
  the `localhost` defaults) boots Caddy with two identical `localhost` site
  blocks, which Caddy merges — the two `reverse_proxy` directives collapse
  into one site and, in practice, all traffic lands on one upstream
  (`web:3000`), leaving the API unreachable through the proxy. No error is
  emitted; the misconfiguration is silent.
- **Concrete trigger:** Prod deploy with hosts unset → `https://<host>/api/*`
  never reaches the API; confusing 404s/HTML responses from the web container.
- **Suggested fix:** Drop the `localhost` fallbacks (`{$APP_HOST}`,
  `{$API_HOST}`) so Caddy refuses to start without real hostnames, and/or add
  `:?` guards or a comment in `.env.example`.

### M4 — `BACKUP_S3_*` vars are consumed by nothing; "optional S3 sync" doesn't exist
- **File:** `docker-compose.prod.yml` (`backup` service env) vs `backend/scripts/backup.sh`
- **What's wrong:** Compose sets `BACKUP_S3_BUCKET`/`BACKUP_S3_KEY`/
  `BACKUP_S3_SECRET` and its comment promises "nightly pg_dump to a local
  volume + **optional S3 sync**". `backup.sh` contains **zero** S3/AWS code —
  the vars are dead. They are also absent from `.env.example`, so the operator
  can't even discover them. (Compounds H1: not even the local part works.)
- **Concrete trigger:** Operator sets S3 creds expecting off-site backups →
  nothing is ever uploaded anywhere.
- **Suggested fix:** Either implement S3 sync in `backup.sh` (and document the
  three vars in `.env.example`), or remove the vars + the "S3 sync" comment so
  nobody relies on a feature that doesn't exist.

## LOW

### L1 — `web` service gets every backend secret via `env_file: .env`
- **File:** `docker-compose.yml` (`web`) and `docker-compose.prod.yml` (`web`)
- **What's wrong:** The frontend container only needs `API_INTERNAL_URL`
  (+ build args), but `env_file: .env` injects `POSTGRES_PASSWORD`,
  `STRIPE_SECRET_KEY`, `JWT_SECRET`, `ENCRYPTION_KEY`, `GOOGLE_CLIENT_SECRET`,
  etc. into the Next.js runtime. Secret sprawl: a frontend/container
  compromise yields every credential.
- **Suggested fix:** Drop `env_file: .env` on `web`; pass only
  `API_INTERNAL_URL` (+ the existing build args).

### L2 — Duplicate `"version"` key in `frontend/package.json`
- **File:** `frontend/package.json:19` and `:31` (both `"version": "1.0.0"`)
- **What's wrong:** Parses (last wins) but indicates sloppy JSON editing; the
  duplicate sits far apart, easy to desync. (Backend is `0.1.0` — version
  mismatch itself is cosmetic.)
- **Suggested fix:** Delete one occurrence.

### L3 — `Makefile` `migrate` target swallows build failures
- **File:** `Makefile` — `cd backend && (npm run build >/dev/null 2>&1 || true) && node dist/migrate.js`
- **What's wrong:** `|| true` means a broken `tsc` build still proceeds to run
  a **stale** `dist/migrate.js` — `make dev` can silently boot old code after
  a failed build with no visible error.
- **Suggested fix:** Remove `|| true` (let make fail loudly).

### L4 — `METRICS_BASIC_AUTH` not documented in `.env.example`
- **File:** `.env.example` (absent) vs `backend/src/config.ts:100`,
  `backend/src/routes/metrics.ts:62`
- **What's wrong:** The only env var that gates `/metrics` and `/status`
  (which expose spend/queue-depth intel) behind basic auth is documented only
  in code comments and a test. A prod operator reading `.env.example` won't
  know it exists, so both endpoints stay public by default. (Open-by-default
  is accepted design per A1-L2; this is purely the doc gap.)
- **Suggested fix:** Add a commented `METRICS_BASIC_AUTH=` entry with the
  existing `"user:password"` format note.
