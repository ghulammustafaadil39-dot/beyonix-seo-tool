## HIGH

### H-1 — Account deletion leaves the Stripe subscription billing forever
**File:** `backend/src/routes/auth.ts:747` (`DELETE /auth/account`)
**What's wrong:** The handler deletes the user row and (when last user) the tenant row, but never touches Stripe. There is no `cancelSubscription` anywhere in the codebase (confirmed: `providers/types.ts` has no cancel method; `grep` for `subscriptions.cancel`/`cancelSubscription` returns zero hits). The Stripe subscription stays `active` and keeps renewing/charging the customer.
**Concrete trigger:** Paying tenant → `DELETE /api/v1/auth/account` (GDPR delete-my-account) → local rows gone → Stripe keeps charging monthly. Worse: the customer no longer has an account, so they cannot reach the billing portal to cancel; support has no local record linking them. Webhooks for that customer resolve to no tenant (`resolveTenantForSubscription` falls through to `null`) and are silently ignored.
**Fix:** Add `cancelSubscription(subscriptionId, {atPeriodEnd})` to the `PaymentsProvider` interface (real + mock/disabled impls), and call it for the tenant's active subscription(s) *before* deleting rows. Alternatively block deletion while a subscription is active and direct the user to cancel via the portal first.

### H-2 — GDPR erase (`DELETE /account/erase`) has the same billing hole, plus destroys owed credits
**File:** `backend/src/routes/account.ts:992` (`DELETE /account/erase`)
**What's wrong:** Same as H-1 — the erase flow deletes `subscriptions`, `invoices`, `stripe_webhook_events`, `tenant_credits` and the tenant row, but never cancels the Stripe subscription. Additionally, `tenant_credits` (money the business owes the customer, e.g. recorded refunds from `charge.refunded`) are hard-deleted with zero refund/reconciliation — the credit simply vanishes.
**Concrete trigger:** Tenant with an active paid subscription and a $X credit from a prior refund invokes GDPR erase → keeps being charged by Stripe with no account, and the $X credit disappears from every record.
**Fix:** Same as H-1: cancel the Stripe subscription first; for credits, either refund via Stripe or retain a minimal tombstone (tenant id, amount, reason) outside the erased tables.

## MEDIUM

### M-1 — PATCH /sites/:id domain change keeps `verified=true` (verification bypass)
**File:** `backend/src/routes/sites.ts:170` (`PATCH /sites/:id`)
**What's wrong:** The domain UPDATE (`UPDATE sites SET domain = $1 …`) does not reset `verified`/`verified_at` or rotate `verify_token`. `verified` is the ownership proof gating **all** scheduled work (`scheduler.ts:48,84` — weekly crawls, rank checks, reports, light checks, geo checks, backlink sweeps).
**Concrete trigger:** Tenant verifies `evil.com` (they own it) → `PATCH /sites/:id {domain: "victim.com"}` → site stays `verified=true` → weekly scheduled crawls/rank-checks/reports run against `victim.com` on the tenant's budget until the weekly re-verify job (up to 7 days later) catches the missing token and unverifies it.
**Fix:** On domain change, set `verified=false, verified_at=NULL, verify_token=<new random>` (require re-verification), same as a fresh site.

### M-2 — GSC/GA4 `auth-url` routes have no authorization gate (integration hijack)
**Files:** `backend/src/routes/gsc.ts:49`, `backend/src/routes/ga4.ts:73`
**What's wrong:** Both `GET …/gsc/auth-url` and `GET …/ga4/auth-url` sit inside the authed scope but carry **no** `preHandler` — no role check, no scope check. Any viewer-role session user, and any valid API key **regardless of scopes** (even a key with zero scopes), can initiate the OAuth flow. The public callbacks (`/gsc/callback`, `/ga4/callback`) then write `gsc_refresh_token_enc` to the site row — a mutation with zero authorization.
**Concrete trigger:** Attacker with a stolen read-only API key (or a disgruntled viewer) calls `GET /sites/:id/ga4/auth-url`, completes Google consent with *their* Google account → the site's Google integration is now bound to the attacker's account; the owner's GSC/GA4 data flow breaks (queries fail or return the attacker's empty property list).
**Fix:** Gate both with `requireRoleOrScope(['owner','admin','editor'], 'gsc:read')` / `'ga4:read'` (matching the read endpoints' scope), consistent with `ga4/connect` which already requires editor+.

### M-3 — Content generation has the B1-M3 silent-dedupe bug (permanent jobId, fake `{queued:true}`)
**File:** `backend/src/routes/content.ts:57` (`enqueueGenerateContent`)
**What's wrong:** Uses raw `enqueue(…, { idempotencyKey: `content:${pieceId}` })` — a **permanent** per-piece jobId. Per the B1-M3 analysis in `queues.ts`, BullMQ silently dedupes on jobId: `Queue.add` with a duplicate id returns the pre-existing job (failed jobs are retained via `removeOnFail: 200`) without creating new work. The refresh routes were fixed with `enqueueDeduped` + honest reporting; content generation was missed.
**Concrete trigger:** Generation job fails terminally (LLM provider down, 3 attempts exhausted) → piece stays `draft` (processor throws; status unchanged) → user clicks "Generate" again → route's `status==='draft'` check passes → `enqueue` returns the retained *failed* job → response `{ok:true, queued:true}` → **nothing runs, ever**. The piece is stuck in draft until the failed job ages out of the failed set.
**Fix:** Use `enqueueDeduped` with a time-windowed key (e.g. `content:${pieceId}:${day}`) and return `{ok:true, queued:false, deduplicated:true}` on dedupe, exactly like the refresh routes.

### M-4 — `commitUsage` accepts `actualUnits` larger than reserved (metering atomicity voided)
**File:** `backend/src/metering.ts:383` (`commitUsage`)
**What's wrong:** `UPDATE usage_reservations SET units = COALESCE($2, units)` writes whatever `actualUnits` the caller reports — with no clamp to the reserved amount and no re-check against the plan limit. The whole point of `reserveUsage`'s per-tenant advisory-lock atomicity is voided when the commit can exceed the reservation.
**Concrete trigger:** `services/keywordCache.ts:56` reserves `missing.length` but commits `actualUnits: fresh.length`. If the DataForSEO provider returns more metric rows than requested (extra/related keywords), the excess units are committed without ever being reserved — overshooting the tenant's `keyword_metrics` budget and incurring unbilled provider cost. Same shape in `llmMetered.ts` if a provider ever returns more words than `maxWords`.
**Fix:** Clamp in `commitUsage`: `units = LEAST(COALESCE($2, units), <reserved units>)`, or re-assert the limit when `actualUnits > reserved`.

### M-5 — `crawl_pages` budget has no reservation (check-then-act at both layers)
**Files:** `backend/src/routes/audit.ts:72`, `backend/src/services/crawlJobs.ts:308`
**What's wrong:** The C-02 reserve→commit pattern was applied to `sites`, `keywords_tracked`, `ai_words`, `serp_checks`, `keyword_metrics`, `geo_checks` — but **not** `crawl_pages`. The route does a pre-flight `checkLimit` and the worker does a runtime `checkLimit`, but both are check-then-act; usage is `recordUsage`'d only *after* the crawl finishes.
**Concrete trigger:** Two audits for two sites of the same tenant start concurrently (or the Sunday `weekly-crawl` tick enqueues N sites): each passes the runtime `checkLimit` (neither has recorded usage yet), each crawls up to `plan.crawl_pages`, each records at the end → monthly `crawl_pages_month` budget overshot by up to N×. Conversely, a worker crash after crawling but before `recordUsage` under-counts spend permanently.
**Fix:** Reserve `plan.crawl_pages` (or a per-audit estimate) via `reserveUsage` at enqueue/worker-start and `commitUsage` with the actual fresh-page count at the end (cancel on failure).

### M-6 — Coupon `max_redemptions` enforced at redemption, not at checkout (discount overshoot)
**Files:** `backend/src/routes/billing.ts:183` (`validateCoupon`), `backend/src/providers/stripe.ts:430` (atomic redeem in webhook)
**What's wrong:** `validateCoupon` at checkout is advisory; the Stripe discount (`subscription_data.discounts`) is attached at checkout time, while the atomic cap (`redeemed_count < max_redemptions`) only runs later in the webhook. The comment claims the race is closed, but it only closes the *counter* — the discount was already granted by Stripe.
**Concrete trigger:** Coupon with `max_redemptions=10`: 15 concurrent paid checkouts all pass `validateCoupon` (count still 0), all complete → 15 Stripe subscriptions carry the discount; the webhook's atomic UPDATE caps `redeemed_count` at 10 and merely *warns* for the other 5. The business honors 5 discounts over the cap.
**Fix:** Reserve the redemption at checkout (atomic increment-under-cap in the checkout transaction; release the hold if the session never completes / expires), or accept and document the overshoot as a known limitation.

### M-7 — `restoreSite` re-activates sites without a plan-limit check (limit bypass)
**Files:** `backend/src/routes/sites.ts:197`, `backend/src/services/retention.ts:150`
**What's wrong:** `restoreSite` is a bare `UPDATE … SET deleted_at = NULL` — no `withUsageReservation`, no limit check. Soft-deleted sites don't count toward `max_sites` (`metering.ts` explicitly excludes them), so delete → create → restore is a persistent over-limit state.
**Concrete trigger:** Starter plan (`max_sites=1`): tenant has site A, soft-deletes A, creates site B (1 active — allowed), restores A → 2 active sites on a 1-site plan, indefinitely. Also bypasses the `read_only` state set by `downgradeTenant`.
**Fix:** Wrap restore in `withUsageReservation(tenantId, 'sites', 1, …)` (it cancels cleanly when the UPDATE affects 0 rows) and return 402 when over limit.

### M-8 — Competitor gap endpoints are N+1 (per-keyword `serp_snapshots` query)
**File:** `backend/src/routes/competitors.ts:196`, `:241`, `:139` (`keyword-gaps`, `content-gaps`, `compare`)
**What's wrong:** Each loops over keyword rows and issues one `SELECT items FROM serp_snapshots WHERE id = $1` per keyword — the same N+1 class as the A1-L1 backlinks fix.
**Concrete trigger:** Site with 1,000 tracked keywords → `GET /sites/:id/competitors/compare` fires ~1,000 sequential DB round-trips; response time degrades linearly and the endpoint can time out behind the 8s route budget.
**Fix:** Batch: `SELECT id, items FROM serp_snapshots WHERE id = ANY($1)` once, then join in memory.

## LOW

### L-1 — `PUT /account/sites/:siteId/onboarding` has no gate
**File:** `backend/src/routes/account.ts:895`. Inside authed scope but no `preHandler` — any viewer session or any valid API key with **zero scopes** can write onboarding state. (GET has `account:read`.) Add `requireScope('account:read')` at minimum; writes arguably deserve a role gate.

### L-2 — Mock-confirm replay double-redeems coupons + duplicates billing events
**File:** `backend/src/routes/billing.ts:326`. `applyPaymentEvent` is called with no `eventId`, so the webhook idempotency ledger is skipped. Re-visiting the mock-confirm URL re-runs the upsert (harmless) **and** `redeemed_count + 1` per visit (coupon burn) **and** re-emits billing events. Mock-mode only, but the coupon burn is real state corruption in dev/test. Pass a synthetic event id (e.g. `mock:<session_id>`) through the ledger.

### L-3 — `ensureCoupon` Stripe-id collision after sanitization
**File:** `backend/src/providers/stripe.ts:172`. `bseo_${CODE.replace(/[^A-Z0-9]/g,'')}` maps distinct local codes to the same Stripe coupon id (`SAVE-10` vs `SAVE10` → `bseo_SAVE10`); `ensureCoupon` returns the *existing* coupon regardless of params, so the second code silently applies the first code's discount. Guard: reject codes whose sanitized form collides with an existing row's.

### L-4 — Webhook endpoint list leaks bearer URLs to viewers, inconsistently with export redaction
**File:** `backend/src/routes/webhooks.ts:54`. `GET /webhooks` returns full `url` values (Slack/Discord/Zapier bearer URLs) to any session role (viewer included); the GDPR export (`account.ts: redactWebhookEndpointUrl`) redacts exactly these. Either redact in the list response too or document that endpoint URLs are visible to all team roles. (Note: `logActivity` on webhook create also stores the raw URL in `activity_log.meta`.)

### L-5 — Unbounded `breakers` map in webhookDelivery (tenant-controlled memory growth)
**File:** `backend/src/services/webhookDelivery.ts:29`. `breakerFor(host)` inserts one `CircuitBreaker` per webhook host with no eviction; hosts are tenant-controlled via `POST /webhooks`. A tenant registering many endpoints across unique hosts grows the map (and one Redis-backed breaker each) without bound. Cap the map (LRU, e.g. 1,000 entries) or scope breakers per endpoint id with cleanup on delete.

### L-6 — Admin impersonation returns the session token in the JSON body
**File:** `backend/src/routes/admin.ts:209` (`return { token, tenantId, expiresInSec: 300 }`). The auth routes deliberately moved to cookie-only token delivery ("JWT-in-body fix" — XSS can read bodies). The 5-minute impersonation token breaks that policy. Deliver via httpOnly cookie (or keep body-only with a documented exception).

### L-7 — DLQ replay is SELECT-then-enqueue-then-UPDATE (double-replay duplicates the job)
**File:** `backend/src/routes/admin.ts:235`. Two concurrent `POST /admin/jobs/failed/:id/replay` both pass the `status='pending'` SELECT, both enqueue, both mark replayed → the job runs twice. Use the invitation-claim pattern: conditional `UPDATE … SET status='replaying' WHERE status='pending'` first, enqueue only on claim win.

### L-8 — Read-only tenant allowlist is broader than documented
**File:** `backend/src/middleware/auth.ts:226` (`enforceTenantState`). The regex also exempts `/webhooks/*` mutations, but the comment only justifies billing/admin/account/apikeys/settings. A read-only (over-limit, unpaid) tenant can still create webhook endpoints and trigger outbound deliveries. Either document or drop `webhooks` from the exemption.

### L-9 — Digest `sent` count includes unsent/failed digests
**File:** `backend/src/services/notifications.ts:236` (`processDigests`). `sent += 1` runs even when there were no items or the send threw (the claim already moved `last_sent_at`, so the digest is also silently skipped for the period on send failure). Count only actual sends; consider not advancing the claim on send failure.

### L-10 — Hardcoded pagination on audit/report lists; wrong `total` on toxic list
**Files:** `backend/src/routes/audit.ts:168` (`GET /sites/:id/audits`), `backend/src/routes/reports.ts:35` (`GET /sites/:id/reports`) — `page: 1, limit: 20` hardcoded, no query params (every other list endpoint paginates). `backend/src/routes/backlinks.ts:206` (`GET …/backlinks/toxic`) returns `total: r.rows.length` — the *limited* count, not the true total. API inconsistency.

### L-11 — Inconsistent AI-word estimates across the content flow
**File:** `backend/src/routes/content.ts`. Create pre-flight uses `LENGTH_ESTIMATES` (800/1500/2500); `/content/:id/generate` pre-flights `+1600` but enqueues with estimate `1200`; the worker (`contentJobs.ts:47`) uses `targetWords + 400`. The route-level checks are advisory (the worker's reservation is authoritative), but the three numbers disagree — pick one estimate function.

### L-12 — `POST /content/:id/approve` bypasses the `canTransition` state machine
**File:** `backend/src/routes/content.ts:229`. Sets `status='approved'` unconditionally, while `PATCH /content/:id/status` enforces `canTransition`. A piece can jump `brief → approved` via approve but not via the status endpoint. Route approve through `canTransition` (or document the shortcut).

### L-13 — Provider API keys in query strings + default redirect-following
**Files:** `backend/src/providers/llm.ts:49` (Gemini `?key=${apiKey}`), `backend/src/services/pagespeed.ts:61` (`?key=${apiKey}`). Native `fetch` follows redirects and does not strip query params on cross-origin redirect (unlike `Authorization`), so a DNS-hijacked provider endpoint could 302 the key to an attacker host. Use `redirect: 'manual'` (or error) on these calls; prefer header-based auth where the API allows.

### L-14 — Self account-delete has no last-owner guard (ownerless tenant)
**File:** `backend/src/routes/auth.ts:747`. `DELETE /auth/account` lets the sole owner delete themselves while other members remain — unlike member-removal (`LAST_OWNER`, `account.ts:351`) and invite-accept (`INVITE_WOULD_ORPHAN_TENANT`), which both guard this. Result: a tenant with members but no owner (nobody can invite/promote owners afterward). Add the same last-owner check.

### L-15 — `POST /auth/email/change` has no resend throttle
**File:** `backend/src/routes/auth.ts:712`. Issues a fresh verification token + sends an email on every call; unlike `/auth/email/resend` and `/auth/password/reset-request`, it never calls `assertResendAllowed`. A stolen session can be used to email-bomb arbitrary addresses. Add the throttle.

### L-16 — `confirmEmailChange` clash check is check-then-act
**File:** `backend/src/routes/auth.ts:170`. Two users changing to the same address concurrently both pass the `SELECT` clash check; one `UPDATE` then dies on the unique constraint → raw 500 (no 23505 translation here). Wrap in the same 23505→409 handling as signup.

### L-17 — Global `retention_policies` readable by any tenant owner/admin
**File:** `backend/src/routes/account.ts:973` (`GET /account/retention`). The table is platform-global, not tenant-scoped; any workspace owner/admin can read (not change) the platform's retention config. Low sensitivity, but this is platform metadata — consider `requirePlatformAdmin`.

### L-18 — SSE job stream has no per-client concurrency limit
**File:** `backend/src/routes/jobEvents.ts:32`. Each connection polls the DB every 2s for up to 120s (`sseMaxDurationMs`). The global per-IP rate limit counts the initial request only; an authenticated user can hold many concurrent streams open → sustained DB polling load. Cap concurrent streams per tenant/IP or require the client to close on `done` (it does) plus a server-side per-tenant stream counter.

## Notes (checked, no finding)

- **Coupon atomicity at redemption** (`stripe.ts:430`): the `redeemed_count < max_redemptions` predicate genuinely closes counter overshoot — the remaining hole is M-6 (discount granted before redemption), not the counter.
- **`inviteDebugFields`** (`account.ts:120`): correctly returns `{}` in production+SMTP; token-in-response only in mock/test/dev.
- **TOTP backup codes** (`totp.ts:verifyTotpOrBackup`): single-use via atomic `array_remove … WHERE $2 = ANY(…)` — concurrent double-use is safe.
- **Email verification tokens** (`emailVerification.ts:48`): single-use with atomic claim; expiry + purpose binding enforced.
- **`enqueueDeduped`** (`queues.ts`): claim-released-on-failure, Redis (not jobId) as dedupe arbiter — correct.
- **`withFairness` + `DelayedError`** (`worker.ts`): deferral never double-executes; heartbeat covers the 15-min timeout TTL boundary.
- **Idempotency middleware** (`middleware/idempotency.ts`): claim-before-execute, 422 on body reuse, stale-claim takeover after 5 min. One theoretical edge (a >5 min Stripe hang letting a same-key retry double-execute) is not practically reachable — checkout completes in seconds; noted but not filed.
- **Global caches** (`keyword_metrics_cache`, `serp_cache`, `serp_snapshots` have no `tenant_id`): deliberate cross-tenant shared-cache design (documented in `account.ts` SHELL_TENANT_TABLES commentary) — cache hits serve other tenants without metering, trading metering precision for provider-cost savings. Accepted design, not a leak (snapshot ids are unguessable and always reached via the tenant's own rows).
- **`getPlan()` fallback** (`plans.ts`): returns `PLANS.starter` for unknown ids — safe because every caller validates with `isPlanId` before use (billing checkout throws 400 regardless).
