### Fix 2 — I2-L-2: atomic PageSpeed quota (`claimQuotaSlot`) ✅ VERIFIED
`backend/src/services/pagespeed.ts:46-57` — single conditional upsert `… ON CONFLICT (quota_key, day) DO UPDATE SET count = count + 1 WHERE count < $2 RETURNING count`; grant iff `Number(rows[0]?.count ?? Infinity) <= quota`.
- **WHERE-false RETURNING semantics:** PostgreSQL returns **no row** when the `ON CONFLICT DO UPDATE` WHERE is false (the conflicting row is skipped, not returned). So denial → `?? Infinity` → `Infinity <= quota` → `false`. Denies correctly.
- **`<= quota` check:** `RETURNING count` yields the *post-increment* value. Fresh row: `1 <= quota` granted iff quota ≥ 1 — and `pagespeedDailyQuota()` (`:21-24`) coerces to ≥ 1 always (default 25), so the fresh-row edge is safe. At `count = quota - 1` exactly one concurrent claimer wins (the loser's ON CONFLICT re-evaluates WHERE against the winner's committed version via EPQ → false → no row). Count can never exceed quota.
- **"Failures never burn quota" (code comment) — overclaim, not a defect:** the claim increments *before* the fetch with no refund on failure, so a failed fetch *does* consume a slot. The behavior is the safe direction (fail-closed; prevents a 429-loop from hammering Google unbounded) and matches the pre-fix failure behavior (`bumpQuota` was unconditional). Likewise the comment's "denies correctly either way" hedge is false in the hypothetical (if the unchanged row *were* returned, `quota <= quota` would grant-without-claim → unbounded overshoot) — but actual Postgres behavior is the no-row branch. Comments only; code correct.
- Regression test (`:238-250`) proves it on real PG: 5 racers, quota 3 → exactly 3 winners, `count = 3`.
- `daily_quotas` PK is `(quota_key, day)` (`027_crawl_v2.sql:12-17`) — the conflict arbiter is valid.

## 2. NEW findings (4 LOW)

### NEW LOW #1 — I2-L-1 residual: winner-crash-after-insert leaves the week with zero notification and no recovery path
**Files:** `backend/src/services/reportJobs.ts:48-55` (early-`existing` skip), `:69-78` (loser skip), `:83-102` (hooks + notify, winner-only).

**What's wrong:** The fix made notification strictly winner-only, but nothing records *whether the winner notified*. If the process dies between the `INSERT` (line ~62) and the notify block — or if a deploy/restart lands in that window — the report row exists, so every subsequent attempt takes the early-`existing` path and returns `{skipped: true}` without notifying: BullMQ retries (same job), the next manual "Generate" (same `period_start`), all skip. The Monday tick never re-fires for that week. Net: the tenant gets **no "Weekly SEO report" email, no Telegram, and no `report.ready` plugin/webhook delivery** for that site/week, with the report silently present in the dashboard. The notify block also swallows send errors (`catch` → `console.error`), so a transient notify failure on the winner is equally unrecoverable.

**Trigger / impact:** narrow crash window (INSERT→notify is ~2 DB reads + hooks fire-and-forget + sends), so LOW. But it is the direct mirror of the defect the fix closed (duplicate-notify → zero-notify), and the task's adversarial question ("winner-crash-after-insert acceptable?") deserves the honest answer: real, narrow, unhealed.

**Fix direction:** record delivery — e.g. a `notified_at` column on `reports` set after successful notify — and let the early-`existing`/loser paths notify when the row exists but `notified_at IS NULL` (at-least-once restored without reintroducing duplicates: the first notifier wins the column via conditional UPDATE).

**Duplicate check:** grepped all `.audit-pass{1..9}-*.md` for report-notify crash/winner discussion. I2-L-1 covered only the *loser* double-notify; no pass discusses the winner-crash side. **NEW.**

### NEW LOW #2 — checkout claim released by tenant-wide DELETE on `completed`/`expired`, not scoped to the completing session
**Files:** `backend/src/providers/stripe.ts:586` (`checkout.session.completed`), `:747` (`checkout.session.expired`); claim stores `stripe_session_id` (migration 050).

**What's wrong:** Both release paths do `DELETE FROM checkout_sessions WHERE tenant_id = $1` — tenant-wide, ignoring the claim's `stripe_session_id` even though the event's `data.id` *is* the completing session id. After a stale-steal (second checkout S2 created while abandoned S1 is still live — the status-blind steal J4 filed), S1's `checkout.session.completed` wipes **S2's** claim. The tenant can then create S3 while S2 is live; each completion overwrites the single per-tenant subscription row (`ON CONFLICT (tenant_id)`), so the extra live Stripe subscriptions stay locally invisible via E4-H-2 — the I1-L-3 double-billing shape, now reachable through *three* sessions instead of two. The defect is that the release path never verifies it is releasing the *right* claim.

**Note on mock mode:** tenant-wide is load-bearing there — `mock-confirm` carries no session id in `data` (`routes/billing.ts:530-545`), so a pure `AND stripe_session_id = $2` would leak mock claims. Correct fix: `AND (stripe_session_id = $2 OR $2 IS NULL)`.

**Relationship to fellow findings:** same *precondition* as J4-§1 (the status-blind steal, `.audit-pass10-j4.md` — independently confirmed, not double-counted; J4 filed the docs angle, "no code change required"). This is a **distinct code defect with a distinct code fix** (scope the DELETE). J5 marked the steal's money consequence as same-pass-duplicate under J4; this finding is the release-path half, unfiled by either.

**Impact:** LOW — needs steal + completion + further checkout(s); self-inflicted multi-payment, same class as I1-L-3 (customer-visible on their card statement, no cross-tenant angle).

**Duplicate check (passes 1–9):** I1-L-3 filed the concurrent-*creation* race; no pass discusses the release path's scoping. **NEW.**

### NEW LOW #3 — `enqueueDeduped`: process crash between the Redis claim and `Queue.add` leaves a phantom claim for the full TTL
**Files:** `backend/src/queues.ts:216-256` (`enqueueDeduped`).

**What's wrong:** The helper claims the idempotency window with `SET NX EX ttlSec`, then `enqueue`s. If `enqueue` **throws**, the claim is released (`:248-253`) — but if the **process crashes** between the two awaits, the claim persists for the full TTL with nothing ever queued. Every subsequent manual attempt returns `{deduplicated: true}` honestly-but-wrongly (nothing is queued, nothing will run) until the TTL expires: 7 days for `reports/generate`, 24h (default) for `ranks/refresh` and `backlinks/refresh`. The scheduled ticks are unaffected (separate BullMQ-`jobId` dedupe domain), so the blast radius is manual regeneration only, and it self-heals at TTL expiry.

**Impact:** LOW — ms-scale crash window; partial availability (manual refresh) for up to the TTL; scheduled pipelines unaffected.

**Fix direction:** claim with a short TTL and extend it after a successful `enqueue`, or delete-then-verify: on `deduplicated:true`, peek whether a live job actually exists for the key and reclaim if not.

**Duplicate check:** passes 1–9 (and the `queues.ts` B1-M3 comment) discuss only the *throw*-path release ("claim-released-on-failure"); the crash gap is unreported. **NEW.**

### NEW LOW #4 — `invoice.payment_failed` no-row fallback duns vacuously; the later `created`/`updated` event really mints and duns again (two identical emails)
**Files:** `backend/src/providers/stripe.ts:1119-1126` (no-row fallback `won=true`), `:882-916` (`justMinted` emit); identical template at `backend/src/services/billing.ts:151-157`.

**What's wrong:** The I1-L-1 atomic-mint fix's "exactly one minter duns" invariant assumes the winner actually *minted*. The no-row fallback (`SELECT 1 FROM subscriptions …` → 0 rows → `won=true`) duns **without writing anything** — a vacuous win. When the `customer.subscription.created`/`updated` event for the same failure arrives later (out-of-order webhook delivery — `payment_failed` before `created`/`completed` — or an out-of-band invoice), the upsert really mints the grace and `justMinted` fires → a second dunning email. Both types (`invoice.payment_failed`, `subscription.past_due`) render the **byte-identical** subject + body ("Payment failed — please update your payment method"), so the customer gets the exact duplicate pair H1-L-2/I1-L-1 were filed to eliminate.

**Trigger:** `payment_failed` processed with zero subscription rows (reordered delivery or out-of-band subscription), followed by the subscription event. Pre-existing — the I1-L-1 fix deliberately preserved the old emit behavior here ("nothing to race on"), but the *ordering* hole (as opposed to the *race* the fix closed) survives.

**Impact:** LOW — narrow trigger, email-only, no money/data impact.

**Fix direction:** in the `justMinted` branch, consult `episodeDunningSent` before emitting (the earlier vacuous dun is recorded in `notification_log`, so at-least-once is preserved while the duplicate is suppressed) — or make the no-row fallback emit only when no subscription row appears within the same processing (not knowable; the `episodeDunningSent` check on the mint side is cleaner).

**Duplicate check:** grepped all `.audit-pass{1..9}-*.md` for no-row/vacuous-mint/ordering double-dun discussion — zero hits. J5 §1c verified the fallback exists but did not file its consequence. **NEW** (pre-existing defect, not a pass#9-fix regression — stated as such).
