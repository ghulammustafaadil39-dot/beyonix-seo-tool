## NEW findings

### H2-L-1 — LOW — The G1-L-1 (pass#7) notification-dedupe fix only closes the *sequential* crash-retry case; the *concurrent duplicate delivery* case it was built for still double-sends

**Files:** `backend/src/services/billing.ts:83-120` (`send()` inside `registerDefaultBillingHooks`); `backend/migrations/049_wave4_pass7_billing_dedupe.sql`; `backend/src/providers/stripe.ts:466-480`.

**What's wrong:** The 049 fix made the billing-email hook do SELECT-check → `notify.sendEmail()` → INSERT-'sent'-row. That is a non-atomic TOCTOU:

1. Request A (ledger-insert winner) processes the handler, reaches `send()`: SELECT finds no `(event_id, type)` row → `await notify.sendEmail(to, ...)` (network I/O — wide window) → INSERTs the `'sent'` row.
2. Request B (ledger-insert loser) **deliberately reprocesses the full handler** per `stripe.ts:466-480` ("a concurrent duplicate … also lands here … Fall through to reprocess the crashed event") — money effects are guarded by event-id inserts, but the email path is not.
3. If B's SELECT lands before A's INSERT (very plausible — the window spans a real SMTP round trip), B also sends the email. The customer gets the same lifecycle email twice.

The partial unique index from 049 (`notification_log_event_dedupe_idx`) exists to support an atomic claim, but the code never uses it as one: the second INSERT fails with a unique violation *after the email already went out*, and the conflict is swallowed by `.catch(() => {})`. The migration's own comment — "The default hook now checks for an existing 'sent' row … so a reprocess skips" — is true only for *sequential* reprocesses, not concurrent ones. The fix comment in `stripe.ts:469-473` still claims "Reprocessing is safe because every non-idempotent handler below is guarded by an event-id idempotency key" — the notification path is still not guarded atomically.

**Concrete trigger:** Stripe redelivers `charge.refunded` / `invoice.payment_failed` / `customer.subscription.updated(past_due)` while the first attempt is still in flight (network-timeout retry — the exact F2-L-1 scenario 049 was written for). Both attempts run `applyPaymentEvent` concurrently (the webhook route, `routes/billing.ts:203-231`, has no per-event-id serialization) → both emit the billing event → both pass the SELECT → double dunning/refund email. Multi-instance deployments widen this (deliveries can land on different API replicas).

**Why LOW:** bounded (one extra email per concurrent-duplicate incident — itself rare), no money movement, no data loss, no privilege issue. Matches the original G1-L-1 severity.

**Fix:** claim-first atomic pattern — `INSERT INTO notification_log (…, status='claimed', event_id, …) … ON CONFLICT (event_id, notification_type) DO NOTHING` *before* `sendEmail`; only send when `rowCount = 1`; then update the claim row to `'sent'`/`'failed'`. The 049 partial unique index already exists to back exactly this. Keep the `'failed'`-doesn't-suppress behavior (retry should re-send), but a crash between send and the status update should be reclaimed with a short stale-claim window rather than sending unconditionally.

**Duplicate check:** grepped all `.audit-pass{1..7}-*.md` for `notification_log`, `emitBillingEvent`, G1-L-1. Pass#7 G1 *filed* the duplicate-email problem and 049 fixed it — but no pass reviewed the 049 *implementation*; the concurrent half of G1-L-1's own trigger list remains open because the implemented check is non-atomic. **NEW** (incomplete fix, not a re-file of the original).
