### 1a. I5-M#1 (MEDIUM): consumed-grace mirror in `customer.subscription.updated` — VERIFIED ✅
Code at `providers/stripe.ts:870-916`: `graceConsumed = storedStatus === 'past_due' && !storedGraceUntil` (`:880`); `graceUntil = graceConsumed ? null : ...` (`:882`); the upsert's `COALESCE(subscriptions.grace_until, EXCLUDED.grace_until)` writes NULL (`:894`); `justMinted` requires `!graceConsumed` (`:908-913`) so no dunning email. Regression tests `w4-pass9-fixes.test.ts:73` (consumed grace → no re-mint, no re-dun, stays `past_due`/NULL) and `:133` (genuine first failure on `active` → mints + duns) genuinely exercise both sides.

**Adversarial Q — does the `storedStatus` (by tenant) vs `existingGrace` (by incoming subId) split open any hole in adoption/supersede cases?** No. `storedStatus`/`storedGraceUntil` are read by tenant (`:800`); `existingGrace` by incoming `stripe_sub_id` (`:878`). In every non-supersede flow both queries hit the same row (one row per tenant). In the supersede flow the handler either returns early (E4-H-2 warn-and-ignore — tracked LIVE row, no mint possible) or falls through for F2-L-4 adoption, which requires the tracked row to be TERMINAL (`canceled`/`incomplete_expired`) — so `storedStatus` can never be `'past_due'` there and `graceConsumed` is false by construction. The admin-override row (`stripe_sub_id IS NULL`) skips the guard and adopts normally. No split-case hole.

**Adversarial Q — first-failure rows (`active`/`trialing`/`incomplete`) still mint?** Yes. `graceConsumed` is false for all three (only `'past_due'` + NULL grace triggers it); `existingGrace` is NULL on first failure → `graceDeadline()` minted, `justMinted` duns. The `:133` regression test covers `active`; the `incomplete` first-failure path mints via the same branch (`recordedStatus='incomplete'`, `:884`).

### 1c. I1-L-1/I1-L-2 (LOWs): atomic dunning mint + episode re-dun — VERIFIED ✅
- `invoice.payment_failed`: mint is now a single conditional `UPDATE … WHERE grace_until IS NULL` (`:1114-1118`); only `rowCount = 1` duns. Two concurrent `payment_failed` deliveries serialize on the row lock — exactly one wins. The no-row fallback (`:1119-1122`) preserves the old emit behavior only when no subscription row exists at all.
- `customer.subscription.updated`: the upsert's `COALESCE` keeps the race winner's grace; `justMinted` compares the winner's stored timestamp against *this* event's computed `graceUntil` (`:908-913`) — the loser stays silent. At-least-once per episode, exactly-once once successful. ✅

## 2. NEW findings (2 LOW)

### NEW LOW #1 — `invoice.paid` recovery has no amount guard: a $0 invoice revives a consumed-grace `past_due` row to paid `active`
**Files:** `backend/src/providers/stripe.ts:1033-1035` (`invMatchesTracked`), `:1035-1073` (recovery branch); amount computed at `:991-993` but never consulted.

**What's wrong:** The I5-L#1 fix gates recovery on the invoice belonging to the tracked subscription, but nothing checks that the invoice represents actual payment. Stripe emits `invoice.paid` for **$0 invoices** (auto-"paid" on finalization — e.g. a proration invoice netting to $0). A tenant sitting in consumed-grace `past_due` (downgraded to Starter, `grace_until` NULL) who makes a subscription change in the billing portal — the exact portal the dunning email drives them to — can generate a $0 proration invoice. Its `invoice.paid` (with `invSubId === stored`) flips the row to `'active'`, clears `grace_until`, re-resolves the plan from the invoice price, restores `tenants.plan_id`, and recomputes `read_only` — **full paid limits plus scheduler spend** (`scheduler.ts` status filter passes on `'active'` → real DataForSEO/LLM burn) while the original past-due balance is still unpaid and Stripe still considers the subscription `past_due`.

**Trigger / impact:** narrow but real — requires a portal subscription mutation netting a $0 invoice while `past_due`. Consequence is a transient paid-access window (until the next Smart-Retry `invoice.payment_failed`, which mints a fresh grace + duns — the state self-heals, but the free window lasts as long as the retry schedule). This is a "paid limits without paying" path squarely in the hunt brief. LOW because the trigger is unusual, customer-initiated, self-healing, and bounded by the retry cadence.

**Fix direction:** require `amount_paid > 0` for the `past_due`→`active` revival — but keep the `incomplete`+100%-off-coupon path intact (there a $0 first invoice IS the legitimate payment). Alternatively consult `billing_reason`. The `!invSubId → recover` fallback (deliberate per the I5-L#1 fix comment) is left as-is.

**Duplicate check:** grepped all `.audit-pass{1..9}-*.md` for amount-guard / `$0` / zero-amount invoice discussion — zero hits. The I5-L#1 fix added the sub-id match; no pass discusses the amount dimension. **NEW.**

### NEW LOW #2 — Keyless double POST `/billing/checkout` with a coupon leaks one `reserved_count` slot via the same-URL idempotent return
**Files:** `backend/src/routes/billing.ts:274` (`couponReserved = true`), `:350-357` (same-URL early return), `:417-425` (catch-path release).

**What's wrong:** The coupon slot is reserved (committed) *before* the claim check. When a second checkout request finds a live `'open'` claim with matching plan/interval, the handler does `ROLLBACK` + `return { url: claim.checkout_url }` (`:357`) — a normal return, not a throw — so the `catch` block's `releaseReservation()` (`:421`) never runs. The leaked reservation is never redeemed (only one session completes → one redeem) and never released (`checkout.session.expired` fires only for the one real session). Net: **one permanently-burned cap slot per occurrence** (`reserved_count` stays +1; the reserve predicate counts `redeemed + reserved < max_redemptions`, so capped promos silently erode — later legitimate customers get `COUPON_EXHAUSTED`).

**Trigger:** realistic — the frontend never sends `Idempotency-Key` (verified: zero hits in `frontend/`), so `withIdempotency('billing:checkout')` is pass-through; a user double-clicking "Subscribe" with a coupon, with the second POST landing after the first reached `'open'`, hits this path. (A second POST landing during `'creating'` correctly 409s and releases via catch.)

**Impact:** LOW — promo-accounting corruption / denial of discount to later customers; no money theft, no privilege issue; unlimited coupons (`max_redemptions IS NULL`) unaffected.

**Fix:** release the reservation on the same-URL early return, or (cleaner) run the claim check before `resolveStripeCoupon` so no slot is reserved when reusing an open session.

**Duplicate check:** E4-L-1 covers the *stale-dropped `checkout.session.completed`* leak (different path — the C-01 early return before redeem/release). No pass discusses the route's same-URL return leaking the reservation. Grepped `same session`, `same.url`, `CHECKOUT_IN_PROGRESS` across all passes — zero hits. **NEW.**
