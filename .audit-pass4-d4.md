## HIGH

### H-1 — Backup sidecar can never run: bash shebang on a bash-less image
**Files:** `backend/scripts/backup.sh:1`, `backend/scripts/restore.sh:1`,
`backend/scripts/_pg_env.sh:1`; triggered by `docker-compose.prod.yml`
(`backup` service)
**What's wrong:** All three scripts use `#!/usr/bin/env bash` and rely on
bash-only features (arrays `${EXTRA[@]}`, `[[ ]]`, `local`). The `backup`
service runs the stock `postgres:16-alpine` image, which is Alpine-based and
does not ship bash. The entrypoint (`["sh", "-c", "/usr/local/bin/backup.sh
..."]`) execs the script file, so the kernel resolves the shebang directly →
"bad interpreter" → the container crash-loops at every boot.
**Concrete trigger:** Follow DEPLOY.md §3 on a wiped machine:
`docker compose -f docker-compose.prod.yml up --build -d` → `backup`
restarts forever, **zero backups are ever produced**, while DEPLOY.md §6 and
RUNBOOK "Backups & restore" promise daily dumps into `pgbackups`. The
operator's off-site backup strategy silently has nothing to sync.
**Suggested fix:** Rewrite the three scripts to POSIX `sh` (replace arrays
with positional params, `[[` with `[`) and change shebangs to `#!/bin/sh`;
or mount them into a tiny custom image with bash installed. Add a CI lint
(`shellcheck -s sh`) so this can't regress.
**Note:** DEPLOY.md §9 item 5 already lists this as "UNVERIFIED" — it is
still unresolved in the deliverable, and Alpine images do not include bash,
so this is not hypothetical.

## MEDIUM

### M-1 — Prod `web` container runs Next.js in development mode
**File:** `docker-compose.prod.yml` (`web` service)
**What's wrong:** `api`, `worker`, and `migrate` all set `NODE_ENV:
production` explicitly, but `web` relies on `env_file: .env` only. The
frontend Dockerfile's `ENV NODE_ENV=production` (runner stage) is overridden
by compose `env_file` (compose precedence: `environment` > `env_file` >
image ENV). DEPLOY.md §3 instructs `cp .env.example .env`, and
`.env.example` sets `NODE_ENV=development`.
**Concrete trigger:** Operator follows DEPLOY.md verbatim → prod `web`
boots with `NODE_ENV=development` → Next.js standalone server serves in dev
mode (no prod optimizations, React dev warnings, verbose error surfaces in
production). Contradicts the "production" posture of the rest of the stack.
**Suggested fix:** Add `NODE_ENV: production` to the `web` service's
`environment:` in `docker-compose.prod.yml` (same as api/worker/migrate).

### M-2 — `.env.example` is missing 5 env knobs the code reads
**Files:** `.env.example` (absent); code: `backend/src/worker.ts:123-125`,
`backend/src/services/providerGuard.ts:53,74-75`; documented in
`docs/scale.md`
**What's wrong:** These are read by code but documented nowhere in
`.env.example`:
- `WORKER_HEAVY_CONCURRENCY` / `WORKER_LIGHT_CONCURRENCY` (worker queue-class
  concurrency; `worker.ts:124-125`, read via an `env: NodeJS.ProcessEnv`
  default param)
- `GLOBAL_PROVIDER_DAILY_CAP_CENTS` / `GLOBAL_PROVIDER_DAILY_CAP_UNITS`
  (the global provider spend circuit; `providerGuard.ts:74-75`)
- `PROVIDER_PRICE_<FEATURE>_CENTS` (dynamic per-feature cost calibration,
  e.g. `PROVIDER_PRICE_SERP_CENTS`; `providerGuard.ts:53`)

This directly contradicts two "proven complete" claims: README.md
("completeness was proven by grepping every `opt()`/`req()` call …
plus all live `process.env` reads … (Wave 3 audit, 2026-10-11)") and
RUNBOOK.md ("`.env.example` is complete and commented — every variable the
backend reads was proven by grepping …"). The Wave-3 grep missed them
because `worker.ts` reads through a function default parameter and
`providerGuard.ts` uses dynamic `process.env[envKey]` — both invisible to a
naive `process.env.X` pattern.
**Concrete trigger:** Operator wants to tune the provider spend circuit
(the dollar circuit that pass-3's M-3 showed never trips) or worker
concurrency → knobs are undiscoverable; `docs/scale.md` mentions them but
the file operators actually copy (`.env.example`) doesn't.
**Suggested fix:** Add a "scale / cost guardrails" section to
`.env.example` documenting all five (with defaults: heavy=6, light=3,
caps=0=disabled).

### M-3 — CI's Playwright E2E step can never fail
**File:** `.github/workflows/ci.yml:227`
**What's wrong:** The step is
`cd ../frontend && npx playwright test || echo "E2E_PLAYWRIGHT_PENDING"`.
Two compounding problems: (a) the `|| echo` swallows any failure, so the
job always passes; (b) there are **zero** Playwright specs under
`frontend/` and no playwright config — the real journeys live in
`backend/tests/e2e/journeys.mjs` (a `playwright-core` script, not a
Playwright Test spec) and are run from the wrong cwd. So the Playwright half
of `e2e-smoke` "passes" vacuously on every run.
**Concrete trigger:** A frontend regression breaks all five user journeys →
CI stays green; RUNBOOK.md's CI table ("e2e-smoke → … API journeys +
Playwright") and RELEASE_NOTES ("Playwright E2E (real Chromium, headless):
5/5 PASS") imply CI enforcement that does not exist. The 5/5 figure came
from a manual run, not CI.
**Suggested fix:** Replace the swallowed step with
`node backend/tests/e2e/journeys.mjs` (after the API+web start steps, per
the script's `BASE=http://localhost:3000` expectation) and delete the
`|| echo` so failures fail the job. (Related: `backend/tests/e2e/axe.mjs`
is also never executed in CI — RELEASE_NOTES lists axe as "not yet
verified", so this is documented, but worth wiring up now.)

### M-4 — README/RELEASE_NOTES mock-vs-real tables list env vars that don't exist
**Files:** `README.md` (CMS publish row), `RELEASE_NOTES.md` (CMS publish row)
**What's wrong:** Both tables' "Env config" column for CMS publish reads
"`CMS_PUBLISH_ENABLED`, `CMS_WP_*`, `CMS_WEBFLOW_*`". The code reads only
`CMS_PUBLISH_ENABLED` (`backend/src/config.ts:89`); WordPress/Webflow
credentials are per-request fields on `PublishInput` (`siteUrl`, `username`,
`appPassword`, `apiToken`, `collectionId` — `backend/src/services/publishConnector.ts:21-31`),
not environment variables. `.env.example` (F-04 section) agrees with the
code — only the two doc tables are stale.
**Concrete trigger:** Operator deploying with a WordPress site searches
docs/`.env.example` for `CMS_WP_*` to configure credentials → doesn't
exist; deploy-time confusion about how to make the real path work.
**Suggested fix:** Change the tables' Env config column to
"`CMS_PUBLISH_ENABLED` (credentials supplied per publish request, not via
env)".
