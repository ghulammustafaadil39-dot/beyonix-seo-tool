## HIGH

### H-1 · `backend/Dockerfile:10,14` — production image cannot be built (`tsc` missing)
**What's wrong:** `RUN npm ci --omit=dev` (line 10) skips devDependencies, but `typescript` is a devDependency (`package.json: devDependencies.typescript ^5.6.3`) and `npm run build` is `tsc -p tsconfig.json && cp -r src/prompts dist/prompts`. `tsc` is not in `node_modules/.bin` after an `--omit=dev` install, so the build step fails with `tsc: not found` and `docker build` of the backend image fails outright. The subsequent `npm prune --omit=dev` is a no-op (nothing to prune).
**Trigger:** `docker build -f backend/Dockerfile .` → fails at `RUN npm run build`. Any deploy depending on this image is blocked.
**Note:** this sits in the A2-H2 fix area — the prompts `COPY` + smoke test (lines 11–16) are correct, but the hardening pass kept `--omit=dev` before the build step, breaking the build the smoke test was meant to guard.
**Fix:** install everything for the build, prune after:
```dockerfile
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
COPY migrations ./migrations
RUN npm run build && npm prune --omit=dev
```

## MEDIUM

### M-1 · `backend/migrations/041_wave4_pass1.sql:11-23` — orphan-cleanup UPDATE runs AFTER the unique index it was meant to enable
**What's wrong:** the file first does `CREATE UNIQUE INDEX audits_one_active_per_site ON audits (site_id) WHERE status IN ('queued','running')` and only afterwards `UPDATE audits SET status='failed' ... WHERE status='queued' AND started_at < now() - interval '2 hours'`. On any database that actually contains the pre-A1-H1-fix duplicate `queued` orphans (the exact scenario this migration targets), the `CREATE UNIQUE INDEX` fails with a duplicate-key error, the whole migration file rolls back (each file is transactional per `db.ts`), and the cleanup never runs — so the migration can never be applied on exactly the databases that need it. Fresh databases are unaffected.
**Trigger:** deploy with ≥2 `queued` audits for one site (leftover from the old double-submit bug) → `runMigrations()` throws on 041 on every boot.
**Fix:** move the orphan-cleanup `UPDATE` above the `CREATE UNIQUE INDEX`. (Checked: `started_at` is set to `now()` on insert in `routes/audit.ts:115`, so the `started_at < now() - interval '2 hours'` predicate does match real orphans — the predicate is fine, only the ordering is wrong.)

### M-2 · `backend/src/metering.ts` `commitUsage` — reservation flip and `usage_events` write are not atomic
**What's wrong:** `commitUsage` runs `UPDATE usage_reservations SET status='committed' ...` and then `INSERT INTO usage_events ...` as two separate statements with no transaction. `getUsage()` sums `usage_events` + still-`reserved` holds. Between the two statements the spend is counted in NEITHER table, so a concurrent `reserveUsage` (which serializes only within its own short transaction) can grant up to `limit` more — collective committed spend can exceed the plan limit. A crash between the statements additionally loses the spend row while the reservation is already committed (silent under-billing of evidence).
**Trigger:** two concurrent `withUsageReservation` flows (e.g. parallel keyword refresh + SERP checks near the plan cap); or a worker crash mid-`commitUsage`.
**Fix:** one transaction, or a single statement: `WITH u AS (UPDATE usage_reservations ... RETURNING tenant_id, site_id, event_type, units, meta) INSERT INTO usage_events SELECT gen_random_uuid(), tenant_id, site_id, event_type, units, meta FROM u WHERE event_type NOT IN ('sites','keywords_tracked')`.

### M-3 · `backend/src/services/fairness.ts` — crashed worker's heavy slot leaks indefinitely under sustained traffic
**What's wrong:** the slot TTL is set on the whole Redis SET (`EXPIRE fair:heavy:<tenant> 900`), and `acquireHeavySlot` refreshes that TTL on *every* successful acquire. A worker that crashes mid-crawl never calls `releaseHeavySlot`; its dead slot member stays in the set, and as long as the tenant keeps submitting heavy jobs (each acquire re-arms the 900s TTL), the set never expires. `SCARD` keeps counting the dead member → the tenant's effective heavy concurrency silently drops from 2 to 1 until 15 minutes of *total* heavy-job inactivity. The A2-L7 heartbeat only extends the TTL while the job's process is alive — it does not help a dead process.
**Trigger:** worker OOM/crash during a crawl for a tenant with steady crawl traffic.
**Fix:** per-slot keys with individual TTLs (e.g. `SET fair:heavy:<tenant>:<slotId> 1 EX 900`), or a sorted set with per-member timestamps + `ZREMRANGEBYSCORE` reaping.

### M-4 · Outbound provider `fetch()` calls have no timeouts (`providers/llm.ts`, `providers/dataforseo.ts`, `providers/notify.ts`)
**What's wrong:** `GeminiProvider.generate` and `OpenAIProvider.generate` (`providers/llm.ts`), `DataForSEOProvider.post` (`providers/dataforseo.ts`), and `sendTelegram` (`providers/notify.ts`) all use bare `fetch()` with no `AbortSignal`. Only `captcha.ts` sets a timeout (`AbortSignal.timeout(8000)`). A stalled provider (hung TLS, black-holed host) hangs the caller: API routes hang until the server kills the socket (~5 min default) with no clean error, and worker jobs burn their full 10–20 min queue timeout before the timeout race fires.
**Trigger:** DataForSEO/LLM/Telegram endpoint stalls mid-request (not a clean failure — the circuit breaker only counts thrown errors, and a hung socket throws nothing until something times out).
**Fix:** `signal: AbortSignal.timeout(...)` (e.g. 30s DataForSEO, 120s LLM, 10s Telegram) on every outbound provider call.

### M-5 · `backend/scripts/rotate-encryption-keys.ts` — rotation bricks legacy `enc:` (kid-less) rows
**What's wrong:** the usage comment says old keys are retained "so existing ciphertext still decrypts" — true only for `enc2:<kid>:` rows. `decryptWithKeys` resolves kid-less `enc:` payloads with the PRIMARY key (`[...byKid.values()][0]`), i.e. the NEW key. Any row encrypted under the legacy single `ENCRYPTION_KEY` fails to decrypt after rotation to a new `ENCRYPTION_KEYS` primary (the script counts it `failed` and exits 1). Worse, an operator following the documented rotation procedure on a database that still holds legacy rows will discover the data loss only at rotate time.
**Trigger:** `ENCRYPTION_KEYS="knew:<new>,kold:<old>" npx tsx scripts/rotate-encryption-keys.ts` on a DB with legacy `enc:` rows.
**Fix:** document the required two-step (first rotate with the old key as primary to convert `enc:`→`enc2:`, then rotate to the new primary), or add an explicit legacy-key fallback parameter; at minimum correct the misleading comment.

## LOW

### L-1 · `backend/src/metering.ts` `reserveUsage`/`commitUsage` — zero units violate the `CHECK (units > 0)` constraint
`take = Math.max(0, Math.round(units))` in `reserveUsage` allows `0`; `011_metering.sql:13` has `units INT NOT NULL CHECK (units > 0)`. A direct `reserveUsage(..., 0)` (or `commitUsage(id, 0)` — reachable from `generateMetered` if an LLM returns 0 words) throws a raw PG check-violation 500 instead of a clean no-op/validation error.
**Fix:** floor at 1 or throw a 400 for `units < 1`.

### L-2 · `backend/src/providers/captcha.ts` `getCaptcha()` — `CAPTCHA_PROVIDER=test` honored in production
The `test` provider accepts the hardcoded token `captcha-test-pass` in ANY `NODE_ENV`. The comment says "Never enable in production" but nothing enforces it — one misconfigured env var disables signup CAPTCHA in prod.
**Fix:** refuse `'test'` unless `NODE_ENV` is `test`/`development` (same pattern as `isMockGoogleAllowed`).

### L-3 · `backend/scripts/backup.sh`, `restore.sh` — DB password visible in the process table
`pg_dump "$DATABASE_URL"` / `psql "$DATABASE_URL"` pass the credential-bearing URL as a command-line argument, visible to other local users via `ps`.
**Fix:** use `PGPASSWORD`/`.pgpass` or split `PG*` env vars instead of embedding credentials in the URL argument.

### L-4 · `backend/src/errors.ts` `errorEnvelope` — Fastify validation `details` leak schema internals in production
The validation branch returns `details: fErr.validation` (instancePath/schemaPath/params) even when `NODE_ENV=production`, while the generic-500 branch deliberately sanitizes. Minor information disclosure.
**Fix:** drop or sanitize `details` in production.

### L-5 · `backend/src/services/llmMetered.ts` `assertLlmCap` — W-03 tenant cap is check-then-act
The tenant self-imposed LLM word cap is read via `getUsage` and enforced outside the reservation; concurrent `generateMetered` calls can each pass the check and collectively exceed the cap (the plan-limit path is atomic via `withUsageReservation`; this one is not).
**Fix:** fold the cap check into the reservation transaction, or document the cap as advisory.

### L-6 · `backend/src/crypto.ts` — memoized `KEYS` means key rotation requires a restart (undocumented)
`keys()` caches the parsed key set in module state on first use; changing `ENCRYPTION_KEYS` at runtime has no effect until the process restarts. The rotation script's success output doesn't say this — an operator who rotates without restarting keeps encrypting with the old primary.
**Fix:** print "restart api/worker to pick up the new primary" in the rotate script's final output.

### L-7 · `backend/src/providers/stripe.ts` `applyPaymentEvent` — early returns skip the `processed_at` ledger update
The `!tenantId || !isPlanId(...)` / `!subId` early returns exit before the final `UPDATE stripe_webhook_events SET processed_at = now()`, so the webhook ledger permanently shows those events as unprocessed (observability wart; redeliveries still dedupe via the event-id insert).
**Fix:** set `processed_at` on all exit paths.

### L-8 · `backend/src/middleware/idempotency.ts` — `withIdempotency` wraps only `/billing/checkout`
The module docstring frames it as the C-07 mechanism "for POSTs that create paid work", but only the checkout route uses it; audit/content/report/keyword POSTs rely solely on BullMQ `jobId` dedupe (which only dedupes non-terminal jobs and is per-queue, not per-request).
**Fix:** extend to other paid-work POSTs or scope the docstring to checkout.

### L-9 · `backend/Dockerfile` — no `HEALTHCHECK`
The image defines no healthcheck; orchestrators can't distinguish a wedged API from a healthy one.
**Fix:** add `HEALTHCHECK CMD wget -qO- http://localhost:4000/healthz || exit 1` (or node-based).
