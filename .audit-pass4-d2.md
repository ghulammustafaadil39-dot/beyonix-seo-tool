## Findings

### HIGH-1 — GSC keyword seeding is dead: `seedFromGsc` double-decrypts the refresh token
- **File:** `backend/src/services/keywordService.ts:148-150` (provider contract: `backend/src/providers/google.ts:67-70`)
- **What's wrong:** `seedFromGsc` does `const token = decrypt(site.gsc_refresh_token_enc)` and passes the
  *plaintext* token to `getGoogle().searchQueries(token, …)`. But `RealGoogleProvider.authed()`
  (`google.ts:67-70`) calls `decrypt(refreshTokenEnc)` *again* on whatever it receives. Decrypting a
  plaintext Google refresh token (`1//0g…`) throws `Unknown encrypted format` — it starts with neither
  `enc:`, `enc2:` nor `plain:` — **on every call**.
- **Trigger:** POST `/sites/:id/keywords/research` on any site with GSC connected
  (`routes/keywords.ts:58-61` calls `seedFromGsc`). The route catches the throw and logs only a warning
  (`'GSC keyword seeding failed; continuing with research'`), so GSC-derived seed keywords are
  **silently never inserted** — the feature degrades invisibly and research runs without them.
  The other two call paths (`routes/gsc.ts:68`, `routes/ga4.ts:99-140`) pass the still-encrypted token
  and are correct, which is why this single call site stands out.
- **Fix:** pass the encrypted column through unchanged —
  `getGoogle().searchQueries(site.gsc_refresh_token_enc, siteUrl(site.domain))` and drop the `decrypt`
  call in `seedFromGsc`. Also add a regression test: no test covers `seedFromGsc` at all, which is why
  three passes missed it.

### MEDIUM-1 — tenant queue rate limiter hangs forever on Redis outage
- **File:** `backend/src/queues.ts:110-112` (`checkTenantRateLimit`) via `getConnection()`
  (`backend/src/queues.ts:17-25`)
- **What's wrong:** the per-tenant enqueue rate limiter (`incrWithTtl`, the Lua INCR-with-TTL) runs on
  the BullMQ connection, which is created with `maxRetriesPerRequest: null` (correct and required for
  BullMQ blocking commands). With that setting, an ioredis command never fails on a Redis outage —
  it retries indefinitely. So if Redis goes down, every user-initiated `enqueue()` (rateLimit defaults
  to `true`) **blocks the API request forever** instead of 429ing or 503ing; the middleware's
  `auth.ts` rate limit avoids this because it uses the separate `getRedis()` client
  (`maxRetriesPerRequest: 3`).
- **Trigger:** Redis unavailable (network partition, failover, restart) + any API route that enqueues
  work (audits, refresh routes). Requests pile up until timeouts/OOM instead of failing fast.
- **Fix:** route `checkTenantRateLimit` (and `enqueueDeduped`'s `SET NX` claim) through a dedicated
  ioredis client with bounded retries, or wrap the `incrWithTtl` call with a timeout and fail
  explicitly (open: allow enqueue when the limiter is unreachable; closed: 503) — document the choice.

### LOW-1 — idempotency middleware replays the handler's *return value*, not the wire payload
- **File:** `backend/src/middleware/idempotency.ts` (`completeClaim` call site)
- **What's wrong:** `completeClaim(tenantId, key, reply.statusCode, body)` stores `body` = the handler's
  return value. If a future wrapped handler calls `reply.send(payload)` itself (reply.sent === true),
  the stored body is the handler's return (often `undefined`) and replays would return an empty body
  with the original status. The single current consumer (`/billing/checkout`) returns its payload, so
  this is latent only.
- **Fix:** capture the payload from Fastify (`onSend` hook) or document in the header comment that
  wrapped handlers must `return` the response body and never `reply.send()` directly.

### LOW-2 — leader-election re-entry is non-atomic (GET then PEXPIRE)
- **File:** `backend/src/services/leaderElection.ts:39-48` (`tryAcquire` re-entry branch)
- **What's wrong:** when re-entering, the code does `GET` (compare to our token) then `PEXPIRE` as two
  commands. Between them the key can expire and be taken by another process, and we'd then extend
  *their* lock. Impact is bounded — the heartbeat uses Lua, and scheduler consumers also claim
  atomically (defense in depth, per the scheduler comment) — so the worst case is a rare duplicate
  tick, not double execution.
- **Fix:** fold into one Lua script (`if get==token then pexpire else 0 end`), same pattern as
  `heartbeat`.

### LOW-3 — exported `isShuttingDown` flag is never wired up (dead API)
- **File:** `backend/src/shutdown.ts:52-60`
- **What's wrong:** `installGracefulShutdown` tracks shutdown with a *local* `shuttingDown` variable;
  the module-level exported `isShuttingDown` object is never set, so any caller consulting it always
  sees `false`. Dead public API.
- **Fix:** set the exported flag inside `shutdown()`, or remove it.

## Checked and clean (spot-verified, no finding)

- `db.ts` migration runner: session-level advisory lock held on a dedicated client, released before
  `client.release()` (correct — pool release would otherwise hold it forever); per-file transactions
  with rollback-on-failure. Lexicographic migration ordering is chronological (001…030, 040–043).
- `crypto.ts`: kid-tagged `enc2:` resolution by kid; legacy `enc:` tries every known key primary-first
  (AES-GCM auth rejects wrong keys); `plain:` refused outside dev/test; module-level key memoization
  is a documented restart requirement (B2-L6 note).
- `config.ts` `validateSecrets`: fail-closed on weak/placeholder JWT and malformed
  `ENCRYPTION_KEYS` (kid regex matches `crypto.ts` `KID_RE`); Stripe keys without webhook secret fail
  at boot.
- `queues.ts`: `enqueueDeduped` (atomic Redis SET NX claim, released on enqueue failure so a failed
  enqueue never burns the window), jittered custom backoff, per-queue timeouts, DLQ capture only on
  terminal failure (`shouldDeadLetter`).
- `worker.ts` `withFairness`: `moveToDelayed` followed by `DelayedError` (never returns normally —
  no double-execution), slot heartbeat at 450s vs 900s slot TTL (A2-L7).
- `scheduler.ts`: UTC-only cron, one idempotency key per tick (C2-L6), leader-gated ticks, reaper only
  touches `queued` rows older than 2h.
- `middleware/auth.ts`: HS256-pinned JWT, token-version revocation, jti session check, `totp`-purpose
  tokens rejected for API use, API keys resolved by sha256 hash with atomic per-key rate limit.
- `middleware/csrf.ts`: double-submit with timing-safe compare, `x-api-key` treated as non-ambient
  credential (A1-M2).
- `middleware/idempotency.ts`: claim-before-execute, 422 on body mismatch, failed claims released,
  stale (5-min) pending claims conditionally reaped by same-hash taker only.
- `middleware/access.ts`: role hierarchy, `requireHumanSession` blocks key-management via API keys,
  platform-admin returns 404 (no existence leak), `humanUserId` defense-in-depth.
- Migrations 041 (cleanup UPDATE before partial unique index — correct order), 042
  (`claimed_at` wired in `webhookDelivery.ts:228`, retention entity wired in `retention.ts:46`),
  043 (`reserved_count` reserve/release/redeem wired in `routes/billing.ts` + `providers/stripe.ts`;
  reservation released on checkout failure path).
- `providers/stripe.ts`: mock webhook signature verified timing-safe with timestamp tolerance;
  real webhook uses Stripe's `constructEvent`; envelope unwrapping matches `data.object`.
- `providers/google.ts`: mock provider gated to test/development (`isMockGoogleAllowed`, fail-closed).
- `providers/captcha.ts`: `test` provider refused outside test/dev; network errors fail closed.
- `providers/notify.ts`: Telegram call has 10s abort timeout.
- `providers/dataforseo.ts`: 30s abort timeout counted by the circuit breaker.
- `Dockerfile`: digest-pinned base, full `npm ci` before build (tsc needs devDeps), non-root `node`
  user, build-smoke check for prompt templates.
- `scripts/rotate-encryption-keys.ts`: idempotent re-runnable, never logs plaintext, fails loudly on
  per-row failures.
