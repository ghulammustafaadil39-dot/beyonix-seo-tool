### F2-M-1 — MEDIUM — Scheduler still treats `incomplete` as spend-authorized; the E4-M-1 free-access loop survives via scheduled jobs

**Files:** `backend/src/scheduler.ts:60`, `:113` (E4-H-1 fix) vs `backend/src/middleware/requireSubscription.ts:32` (E4-M-1 fix)

**What's wrong:** The two pass#5 fixes contradict each other on `incomplete`, and they were committed 5 minutes apart (`23794db` 15:18, `bd6fbff` 15:23) without reconciliation:

- Trial gate (route layer, M-1): `BILLABLE_SUBSCRIPTION_STATUSES = ['active', 'trialing', 'past_due']` — `incomplete` deliberately removed, with the comment explaining that counting it as billable "enables rolling free access via never-funded checkouts".
- Scheduler filter (H-1): `OR sub.status IN ('active', 'trialing', 'past_due', 'incomplete')` — `incomplete` **still included**, in both the `enqueueForVerifiedSites` query and the rank-check query.

**Concrete trigger:** Trial expired → checkout with a never-funded async payment method (SEPA debit) → local status `incomplete`. Every spend *route* now 402s (M-1 works as intended) — but the daily `rank-checks` tick, `weekly-crawl`, `weekly-reports`, `daily-light-check`, `monthly-keyword-refresh`, `weekly-geo-checks`, and `weekly-backlink-sweep` all keep enqueueing for this tenant, spending real DataForSEO + LLM budget for ~23h until `incomplete_expired` downgrades them. Then the user starts another never-funded checkout and repeats — **zero successful payments, indefinite rolling scheduled spend**. The only thing that stops it early is the trial gate's lazy `read_only` flip, which fires only if the tenant touches a gated route; a tenant who never touches one (dashboard reads aren't gated) is never flipped.

This is the exact harm class E4-H-1 was filed for ("the route-layer gate can't cover system-initiated work") and the exact abuse loop E4-M-1 was filed to kill — the M-1 fix closed the route half while the H-1 fix's filter left the scheduler half open.

**Fix:** remove `'incomplete'` from both `IN (...)` lists in `scheduler.ts` so the scheduler's spend-authorization predicate matches the trial gate. (`incomplete` correctly *stays* in the dunning/grace logic — stripe.ts:689 — and the checkout block list — billing.ts:57; the scheduler enrollment is a spend decision, not dunning.)

**Duplicate check:** E4-M-1 filed the route half; E4-H-1's fix *introduced* the scheduler list when `incomplete` was still billable. No prior pass reports the post-fix inconsistency. **NEW.**

### F2-L-1 — LOW — E4-M-2 reprocess fix opens a concurrent-duplicate double-processing window

**File:** `backend/src/providers/stripe.ts:459-471`

**What's wrong:** The fix correctly recovers crashed attempts (row exists, `processed_at IS NULL` → reprocess). But it also fires when a *second concurrent delivery* of the same event id arrives while the first is still in flight: the loser of the insert race sees `processed_at IS NULL` and reprocesses instead of deduping. The old code was strictly safer here (conflict → unconditional swallow).

**Concrete trigger:** Stripe delivers the same event twice with overlapping processing windows (rare, but Stripe documents at-least-once delivery). Non-idempotent handlers then execute twice:
- `charge.refunded` → `INSERT INTO tenant_credits` has no idempotency guard → **double credit**;
- `checkout.session.completed` with coupon → `redeemed_count +1` twice, `reserved_count -1` twice (clamped), plus duplicate `checkout.completed` billing events;
- `customer.subscription.updated(canceled)` → duplicate `subscription.downgraded` events.

The at-least-once trade-off for *crashed* attempts is the intended fix; the *concurrent* case is the unintended regression. (Verified the ordering guard's strict `>` comparison correctly lets a crashed-then-retried event reprocess when `last_event_at == eventAt` — that part is right.)

**Fix (suggestion):** only reprocess when the unprocessed row is older than N minutes (crashed attempt); treat a *fresh* unprocessed row as an in-flight duplicate — return without marking so Stripe's sequential retry completes it.

**Duplicate check:** no prior pass discusses concurrent duplicate delivery vs the ledger. **NEW.**

### F2-L-4 — LOW — E4-H-2 superseded guard permanently ignores out-of-band new subscriptions (no self-heal)

**Advisory-lock reserve (focus #1) — the E2-M-1 fix is CORRECT:**
- Serialization holds: `pg_advisory_xact_lock(hashtext('global_provider_guard'))` is xact-scoped, deterministic per DB, and serializes all reserves — the E2 empirical overshoot (140¢ vs 100¢ cap) cannot recur: the second session blocks at the lock until the first commits, then reads committed totals.
- Safe under PgBouncer transaction pooling (xact-scoped, released at COMMIT — unlike session locks).
- No deadlock cycle: the reserve takes the advisory lock *before* any row lock; `commit`/`release` take row locks without the advisory lock; nested use inside metering's `withUsageReservation` takes the global lock on a *separate* pooled connection with a different key (`metering:{tenant}` vs `global_provider_guard`) — no lock-order inversion.
