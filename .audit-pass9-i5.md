## 3. NEW findings

### NEW MEDIUM #1 — `customer.subscription.updated` re-mints grace after it was consumed: dunning resurrection + recurring paid-access windows for non-payers

**Files:** `backend/src/providers/stripe.ts:823-849` (updated handler) vs `:1014-1043` (payment_failed handler); `backend/src/services/billing.ts:247-251` (`downgradeTenant`), `:283-293` (`processBillingGrace`)

**What's wrong:** The `invoice.payment_failed` handler was hardened for the consumed-grace case (D1-H-1): `curStatus === 'past_due' && !existingGrace` → record-only, no fresh grace, no re-dun (`:1018-1022`). The `customer.subscription.updated` handler was **not** — it keys only on the `grace_until` column (`:825-826`), which `downgradeTenant` deliberately clears to `NULL` after consumption (`billing.ts:250`; the NULL is load-bearing so the daily job doesn't re-pick the row). So the first `customer.subscription.updated(past_due|unpaid|incomplete)` after a grace-expiry downgrade sees `existingGrace = NULL` → mints a **fresh 3-day grace** (`graceDeadline()`) and re-sends the "Payment failed" dunning email (`:847-849`). The H1-L-2 `if (!existingGrace)` gate only suppresses *in-grace* duplicates; it cannot distinguish "never graced" from "grace consumed".

**Concrete loop:**
1. Payment fails → grace minted, dunning email #1.
2. Grace expires → `processBillingGrace` → `downgradeTenant(..., {subscriptionStatus:'past_due'})` → `tenants.plan_id='starter'`, subscription stays `'past_due'`, `grace_until=NULL`, "downgraded" email.
3. Stripe delivers `customer.subscription.updated` with status `past_due` — routine during dunning (portal payment-method update — the exact journey the dunning email drives — next-invoice finalization changing `latest_invoice`, any subscription mutation). Handler mints a fresh 3-day grace + dunning email #2.
4. During the resurrected grace the trial gate **passes** (`'past_due'` ∈ `BILLABLE_SUBSCRIPTION_STATUSES`, `requireSubscription.ts:38`) → paid endpoints accessible; the scheduler's status filter (`scheduler.ts:67,120`) resumes the tenant's rank-check/crawl/report jobs → **real DataForSEO/LLM spend on a non-payer** (quotas at starter level via `tenants.plan_id`, but the jobs run).
5. Three days later `processBillingGrace` downgrades again → another "downgraded" email → `grace_until=NULL` → next `subscription.updated` resurrects again. **Indefinite 3-day cycle**: grace → downgrade → grace, with a dunning + downgrade email every cycle.

**Why MEDIUM (not LOW like H1-L-2):** H1-L-2 was email-only duplication within one episode. This *re-opens paid access and scheduled provider spend* for non-payers in recurring windows and breaks the D1-H-1 "consumed grace never re-duns" invariant that the sibling handler honors. The fix is symmetric and small: in the `updated` handler, also select the stored status and treat `stored == 'past_due' && !existingGrace` as consumed (skip mint + skip emit), mirroring D1-H-1 — first-failure rows have stored status `active`/`trialing`, so they still mint correctly.

**Duplicate check:** grepped all `.audit-pass{1..8}-*.md` for `resurrect`, `consumed.grace`, `re-mint`, `fresh grace`. D1-H-1/E4-M-3 cover only the `invoice.payment_failed` side; H1-L-2 covers only in-grace duplicates; no pass discusses the `customer.subscription.updated` handler re-minting after consumption. The existing test (`w4-fix4-bea.test.ts:280`) covers consumed-grace only for `invoice.payment_failed`. **NEW.**

### NEW LOW #1 — G5-M#2 `invoice.paid` recovery doesn't verify the invoice belongs to the tracked subscription (the `canceled` branch does)

**File:** `backend/src/providers/stripe.ts:941-981`

**What's wrong:** The `canceled`-revival branch requires `invSubId === stored stripe_sub_id` (D1-H-1/D5-M-2, `:977-979`). The `past_due`/`incomplete` recovery branch directly above it (`:949-966`) never checks `invSubId` — and `resolveTenantForSubscription` falls back to the *customer* lookup when the invoice's subscription id isn't tracked (`stripe.ts:418-424`), so an `invoice.paid` for a *different* subscription (or a one-off non-subscription invoice, `subscription: null`) of the same customer reaches the branch.

**Trigger / impact:** narrow — requires a second/out-of-band subscription or a manually-issued one-off invoice for the customer (dashboard-level actions; the checkout 409 blocks tenants from creating a second subscription while `past_due`/`incomplete`). Consequence: the single per-tenant row is flipped to `'active'` with the *other* invoice's plan while `stripe_sub_id` still tracks the old subscription; the real subscription's later events then hit the E4-H-2 supersede warn-and-ignore (tracked id ≠ incoming id, tracked `'active'` not terminal), and a subsequent failure on the old subscription can downgrade a genuinely-paying tenant to Starter. Fix: apply the same `invSubId === stored` match (treating `invSubId == null` as no-match) before reviving.

**Duplicate check:** pass6-f2 mentions `invSubId` only for the *canceled* branch requiring the match (the inverse shape — out-of-band subs being ignored). No pass notes its absence in the `past_due`/`incomplete` branch. **NEW.**
