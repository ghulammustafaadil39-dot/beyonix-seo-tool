## 1. J3-M-1 fix verification — HOLDS (adversarial attempt log)

Fix location: `frontend/app/dashboard/billing/page.tsx`.

**The gating (the core fix).** The `?success=1` notice is now set only *after* `billingApi.subscription()` resolves, branched on the fetched status (`:230-255`):
- `active`/`trialing` (`:233`) → green "Payment successful — your plan is now active."
- `incomplete` (`:234-238`) → amber "Checkout completed, but your payment hasn't succeeded yet — your plan isn't active. Complete the payment in the billing portal below to activate it."
- `past_due` (`:239-243`) → amber "Your first payment failed — update your payment method in the billing portal below to keep your plan."
- else (`none`/`canceled`/`mock`/unknown) (`:244-254`) → neutral "Checkout completed — we're confirming your subscription now. If this page doesn't update within a minute, refresh it." Never claims active.

**Break attempts and results:**

1. *Fetch fails (network/401/500).* The notice-set lives inside the `try` after `Promise.all`; on rejection only `report(e)` runs — **no notice is shown at all**. Fail-closed. The pre-fetch code sets notices only for `?canceled=1` ("no charge was made" — accurate) and the `?plan=` pick (no success claim). ✅
2. *Stale `?success=1`.* Params are stripped via `window.history.replaceState` (`:213`) on mount, before the fetch completes. Reload/back-navigation cannot re-trigger the notice from the address bar. (Browser-history entries retain the query string — see observation O-3 — but re-loading from history re-runs the same status-gated logic, so no false success is possible; worst case is the neutral "confirming" copy on a terminal state.) ✅
3. *Other pages / pricing / emails promising an active plan.* Grep for `now active|Payment successful|success=1` across `app/ components/ lib/`: the success string exists **only** at `:233` (gated). No other `?success`/`?canceled` consumer exists. Pricing page CTAs go to `/signup?plan=` (trial flow, no activation claim); marketing copy ("14-day free trial — no credit card required", "cancel anytime") matches the server-side trial model. Emails are backend-rendered — no frontend email templates with billing copy exist. ✅
4. *The dead "Current plan" badge.* `hasSubscription` (`:318`) still counts `incomplete`, but the `PlanCards` `action` prop (`:466-478`) now renders **"Complete payment to activate"** (portal CTA) instead of the dead badge when `isCurrent && status === 'incomplete'`; the Current-plan card shows the `incomplete` explainer banner with its own portal CTA (`:406-419`). ✅
5. *`incomplete_expired` — the sibling state I tried hardest to break.* Backend models `incomplete_expired` as terminal (`TERMINAL_SUBSCRIPTION_STATUSES`, `backend/src/services/billing.ts:57`) and the J3 report cites the 23h→`incomplete_expired` transition — so I checked whether the local row can ever hold it (which would resurrect the dead-badge bug: `hasSubscription` is true for it, no banner covers it). **It cannot persist:** every `incomplete_expired` event is routed through `downgradeTenant`, which writes `status = 'canceled'` (`backend/src/providers/stripe.ts:974-976` → `services/billing.ts:244-254`); `unpaid` is normalized to `past_due` (`stripe.ts:923`). The only raw writer (`stripe.ts:658-659`) requires an expanded subscription object inside `checkout.session.completed`, which Stripe never sends on the real path (always a string id → fail-closed `'incomplete'`). So the frontend's reachable status set is exactly `{active, trialing, past_due, incomplete, canceled, mock, none}` — all covered. Hypothesis collapsed, not filed. ✅
6. *`trialing` + "Payment successful".* All plans have `trial_days: 0` (`backend/src/plans.ts:19,32,…`), so the real checkout path never produces `trialing` at `?success=1` landing (only the dev mock path). Branch is near-dead in production; harmless as-is. Noted as observation O-2. ✅
7. *`past_due` notice says "Your first payment failed".* Accurate in context: `?success=1` is only ever appended by a fresh checkout (`backend/src/routes/billing.ts:419,563`), so any `past_due` seen with the param is necessarily the first payment. Renewal-failure `past_due` never carries the param. ✅

**Conclusion:** no remaining path promises an active plan for a non-active subscription. J3-M-1 is fixed.

## 2. NEW findings

### K3-L-1 — LOW — `ErrorBanner` tells `incomplete`-status tenants "Plan limit reached."
**Files:** `frontend/components/ErrorBanner.tsx:63-90` (branch), `:76-78` (`hasLiveSub`)

**What's wrong.** On 403 `READ_ONLY_MODE`, the banner resolves the *actual* read-only cause from the subscription — but only for the trial-expired case (`trialEnded`). `hasLiveSub` (`:76-78`) treats `incomplete` as a live subscription (`status !== 'none' && status !== 'canceled'`). So a tenant whose subscription is `incomplete` — fail-closed, payment never succeeded, **no plan limits were ever hit** — gets the banner title **"Plan limit reached."** plus the backend message *"Your workspace is in read-only mode because usage exceeds your current plan limits…"* (`backend/src/middleware/auth.ts:277`). Both statements are factually wrong for this state; the J3-M-1 fix just taught the billing page to explain `incomplete` correctly, but this global banner (rendered on every dashboard page on any write attempt) still misattributes the cause.

**Trigger (reachable):** complete checkout → first payment fails → attempt any write action while `incomplete` → 403 `READ_ONLY_MODE` → banner.

**Impact:** confusion-only. The CTA ("Upgrade plan" → `/dashboard/billing`) lands on the page where the correct `incomplete` explainer now lives, so recovery is one click away; no action is blocked and no false success is claimed. Hence LOW.

**Fix:** extend the cause-resolution to `incomplete` — e.g. `const paymentIncomplete = sub?.status === 'incomplete'` → message *"Your payment hasn't completed yet — complete it in the billing portal to restore full access."*, title "Payment incomplete.", CTA "Complete payment" → `/dashboard/billing`. (Same treatment would apply to `past_due`-with-consumed-grace, which keeps `past_due` status post-downgrade — currently also labeled "Plan limit reached." although the cause is payment failure, not quota.)

**Duplicate check:** grepped all 35 `.audit-pass{1..10}-*.md` for `hasLiveSub`, `Plan limit reached` + `incomplete`. Prior F3-family work (pass6-f3, pass7-g3) fixed the *trial-expired* mislabeling only; the `incomplete` facet was never filed. **NEW.**

### K3-L-2 — LOW — password-reset `?token=` is never scrubbed from the URL
**File:** `frontend/app/reset-password/page.tsx:15`

**What's wrong.** The reset token is read via `useSearchParams().get('token')` on every render and **never removed from the address bar** — unlike the other two bearer-token-in-URL flows in this codebase, which both scrub immediately: the team-invite token (`app/dashboard/team/accept/page.tsx:38-44`, `history.replaceState`) and the OAuth/TOTP challenge token (`app/login/page.tsx:238-242`, `router.replace('/login?totp=1')`). A single-use, 24h-expiry (`backend/src/routes/auth.ts:445`, `issueVerificationToken(…, 'password_reset')`) credential therefore lingers in the address bar, browser history, and any shared/copied URL until the user navigates away — and stays *valid* for up to 24h if the user abandons the page without submitting.

**Impact:** requires access to the victim's browser/history — low severity; included because the codebase's own convention (scrub token-bearing URLs) is violated here, and the fix is one line (`router.replace('/reset-password')` after reading into state, mirroring the login flow).

**Duplicate check:** pass8-h3 reviewed this page ("token read once from `?token=` into a POST body (never logged/stored)") but never flagged URL persistence; no prior report mentions reset-token scrubbing. **NEW.**

### K3-L-3 — LOW — Cancel flow promises "end of your current billing period" for `incomplete` subscriptions
**Files:** `frontend/app/dashboard/billing/page.tsx:150` (copy), `:430-434` (button visibility)

**What's wrong.** The "Cancel subscription" button renders whenever `hasSubscription && !cancel_at_period_end` — and `hasSubscription` (`:318`) includes `incomplete`. The `CancelFlow` modal then tells the user *"Cancellation takes effect at the end of your current billing period."* (`:150`). An `incomplete` subscription has no paid period and no access; there is no "current billing period" to enjoy until the end of — canceling it ends it immediately (Stripe voids incomplete subscriptions; they cannot linger to period end). The retention copy ("you keep full access until…", "nothing is deleted immediately") is written for active subscribers and misdescribes the incomplete case.

**Impact:** edge-state copy inaccuracy; the handoff itself is honest (cancellation completes in the Stripe portal, which shows the true terms). LOW.

**Fix:** gate the timing sentence on status — e.g. hide the Cancel button (or adjust copy to "Cancels immediately — no active period exists") when `sub?.status === 'incomplete'`.

**Duplicate check:** grepped all 35 prior reports for `end of your current billing period` — zero hits. **NEW.**
