## NEW findings

### HIGH-1 — NEW — `next@14.2.35` (App Router) is in the affected range of GHSA-q4gf-8mx6-v5v3 / CVE-2026-23869 (High, CVSS 7.5), with no patch on the 14.x line

**Files:** `frontend/package.json:6` (`"next": "^14.2.0"`),
`frontend/package-lock.json` (`node_modules/next` → `14.2.35`).

**What:** GitHub reviewed advisory GHSA-q4gf-8mx6-v5v3 ("Next.js has a Denial
of Service with Server Components", published 2026-04-08, updated
2026-04-10; upstream CVE-2026-23869, CVSS 7.5 High): affected versions
`>= 13.0.0, < 15.5.15` and `>= 16.0.0-beta.0, < 16.2.3` — the advisory text
explicitly names **Next.js 14.x using the App Router** as affected. Patched
versions are **15.5.15** and **16.2.3** only — there is **no 14.x backport**.
This repo ships `next@14.2.35` with the App Router (`frontend/app/`,
`app/layout.tsx`, App Router route handlers). A specially crafted HTTP
request to an App Router Server Function endpoint can trigger excessive CPU
usage during deserialization → unauthenticated remote DoS of the web tier.

**Why not flagged before:** pass#5's E5 auditor reviewed deps *after* the
advisory was published and wrote "next 14.2.35, no known-bad versions" — they
missed it. Grep confirms no prior pass mentions `q4gf-8mx6-v5v3`,
`CVE-2026-23869`, or React2Shell follow-ons. (React2Shell RCE itself,
CVE-2025-55182, does **not** affect this app — Vercel carved out 14.x stable
and the React CVEs hit React 19; this app is on react 18.3.1.)

**Exposure in this app:** no `'use server'` functions exist (reduces the
classic attack surface), but two App Router route handlers are reachable
(`app/api/[...path]/route.ts`, `app/api/admin/impersonate/route.ts`); the
advisory's scope statement covers 14.x App Router broadly. There is **no**
edge mitigation: Caddy is a plain reverse proxy (no WAF rules — Vercel's WAF
rules for this CVE don't apply to self-hosted), and backend rate limiting
(S-03) does not cover direct-to-Next page/action routes. Blast radius is
bounded only by the web container's CPU cap (`cpus: '1.0'`,
`docker-compose.prod.yml:176`) — which is also the thing being DoSed: one
sustained crafted-request stream pins the single CPU and takes the
storefront + dashboard offline. Backend API (Fastify) is unaffected.

**Suggested fix:** plan the Next 15 upgrade (→ `>=15.5.15`) before or
immediately after go-live; this is a major-version migration, not a patch
bump, so it needs its own test cycle. Short-term: add request-rate limiting
for the Next tier at Caddy (or in front of it) and alerting on web-container
CPU saturation. Document the decision in `SECURITY.md` either way.
