## NEW findings

### M-1 — MEDIUM — Vulnerable nested `postcss@8.4.31` under `next@14.2.35` in the frontend lockfile; two published CVEs; no npm `overrides`

**Files:** `frontend/package-lock.json:962` (`"node_modules/next/node_modules/postcss": 8.4.31`); `next@14.2.35` pins `postcss: 8.4.31` exactly; neither `frontend/package.json` nor `backend/package.json` has an `overrides` section.

**What's wrong:** The frontend tree contains two postcss copies. The top-level is safe (8.5.29), but the nested copy pulled in by Next.js is **8.4.31**, which carries two published moderate CVEs:
- **CVE-2026-41305 / GHSA-qx2v-qp2m-jg93** (CVSS 6.1): postcss < 8.5.10 does not escape `</style>` when stringifying CSS ASTs → XSS when parsed CSS is re-embedded in `<style>` tags. Fixed in 8.5.10.
- **CVE-2026-69153** (CVSS 5.3): postcss < 8.5.19 — `PreviousMap.loadFile()` can be tricked into reading an unintended source-map file via absolute/traversal `sourceMappingURL` when `from` is unset. Fixed in 8.5.19.

Pass#4 D4's eyeball check explicitly signed this off ("postcss 8.5.29 (latest 8.x)… pins resolve healthy") — it only looked at the top-level copy and missed the nested one. The sibling beyonix-mailer project solved this exact class with an npm `overrides` entry forcing postcss to the fixed version; this repo has no overrides, so the vulnerable nested copy persists.

**Concrete trigger:** `npm ci` in the frontend (CI and the Docker `deps` stage) installs the vulnerable nested copy on every build. The exposure is honestly limited: the nested copy runs at `next build` time (postcss-loader) on the build machine against first-party source CSS, and it is **not** shipped in the standalone runtime image (runner stage copies only `.next/standalone` + `.next/static`). There is no user-submitted-CSS pipeline in this product, so neither CVE has a realistic attacker input here.

**Why MEDIUM anyway:** (a) two published CVEs in the shipped lockfile that a prior pass wrongly cleared; (b) the project's own safety net does not cover it — CI runs `npm audit --audit-level=high` (`.github/workflows/ci.yml:152-158`), and both CVEs are *moderate*, so CI stays green forever on this; (c) the fix is one line, already proven in the sibling project.

**Fix:** add to `frontend/package.json`:
```json
"overrides": { "postcss": ">=8.5.19" }
```
then regenerate `frontend/package-lock.json` and confirm the nested entry resolves ≥ 8.5.19. (8.5.29 already used at top level also satisfies this.)

### L-1 — LOW — `SIGNUP_TRIAL_DAYS` is read by code but documented nowhere; README's "proven complete" env claim is falsified again

**Files:** `backend/src/services/billing.ts:109` (`process.env.SIGNUP_TRIAL_DAYS`); `.env.example` (absent); `README.md:43-47`.

**What's wrong:** `signupTrialDays()` reads `process.env.SIGNUP_TRIAL_DAYS` (default 14) — the operator knob controlling the trial length introduced by the D5-H-1 fix. It appears in **no** `.env.example` entry and **no** markdown file in the repo. Meanwhile `README.md:43-47` still claims: "every variable is documented there, and completeness was proven by grepping every `opt()`/`req()` call in `backend/src/config.ts` plus all live `process.env` reads in services/providers/routes". The grep methodology missed a bare `process.env.X` read in `services/billing.ts` — the *exact* failure mode of pass#4 D4-M-2 (which fixed 5 knobs but left the method broken). The claim is now false for the second time.

**Concrete trigger:** Mustafa (or any operator) wants a 30-day launch trial; nothing in `.env.example`, DEPLOY.md, or README tells him the knob exists — he has to read source. The trial gate is the single most important billing behavior of Wave 4 and its only tuning knob is invisible.

**Fix:** add to `.env.example` (near the Stripe/billing section):
```
# Trial length (days) for new signups — server-side, never client-supplied.
# Unset = 14. Applies at signup; existing tenants unaffected.
SIGNUP_TRIAL_DAYS=14
```
and amend the README completeness claim to describe the actual grep used (include bare `process.env.` reads outside `config.ts`), or drop the "proven" wording.

### L-2 — LOW — DEPLOY.md covers none of the Wave-4 billing changes: migrations 044/045, the trial gate, or the `global_provider_guard` table

**Files:** `DEPLOY.md` (whole file — zero mentions of "trial", "044", "045", or "guard"); migrations `backend/migrations/044_trial_ends_at.sql`, `045_wave4_fix4_cleanup.sql`.

**What's wrong:** The upgrade path (`DEPLOY.md` §7) is generic ("migrations first"), which is fine for routine migrations — but 044/045 change *operator-visible billing behavior*:
- 044 adds `tenants.trial_ends_at` (NOT NULL, backfilled to +100y for existing tenants = grandfathered) and activates the trial gate: after the 14-day trial expires with no live subscription, spend routes 402 (`SUBSCRIPTION_REQUIRED`) and the tenant is flipped read-only (`middleware/requireSubscription.ts:36-61`).
- 045 replaces the sites unique constraint with a partial index (operationally relevant for support: re-adding deleted domains) and creates `global_provider_guard` backing the global daily provider-spend circuit.
- The Stripe row of the mock-vs-real tables ("Production without keys → 503 `BILLING_NOT_CONFIGURED`") is now incomplete: without Stripe keys, new signups still get **14 days of paid features** via the server-side trial — billing *ops* 503, but the product is not dead.

An operator following DEPLOY.md learns none of this: not that a deploy of 044 starts a 14-day clock on every *new* signup, not how to tune it (see L-1), not what a 402 after two weeks means for support tickets, and not that `GLOBAL_PROVIDER_DAILY_CAP_*` exists (it is in `.env.example` now, but absent from the DEPLOY.md §8 checklist).

**Concrete trigger:** deploy goes live, day 15: first support ticket "paid features stopped working, no error in Stripe" — the operator has no doc pointing at the trial gate.

**Fix:** add a short "Billing behavior after this release" note to DEPLOY.md §7/§8: trial length + knob, 402/read-only on expiry, grandfathering of pre-044 tenants, and the provider-spend circuit knobs. One paragraph + checklist line each.

### L-3 — LOW — DEPLOY.md §9 UNVERIFIED-5 is now stale: it directs the operator to chase a fixed problem

**File:** `DEPLOY.md:247` (UNVERIFIED item 5).

**What's wrong:** The item still says "`backend/scripts/backup.sh` has a `#!/usr/bin/env bash` shebang; it is unconfirmed whether `bash` exists in `postgres:16-alpine`. If not, every backup run fails with 'bad interpreter'. Verify on first deploy (`docker compose exec backup bash --version`)…". Since pass#4 D4-H-1 was fixed, all three scripts (`backup.sh`, `restore.sh`, `_pg_env.sh`) use `#!/bin/sh` and are written POSIX-clean (verified: no `[[ ]]`, no arrays; the scripts' own comments document the bash-less constraint). The doc now instructs the operator to verify something that is already resolved — and worse, the "if missing, the Backend/QA owner must fix" escalation path points at a non-issue, while the *actual* remaining backup risk (untested restore path, still never executed) gets no mention.

**Concrete trigger:** operator burns first-deploy time checking `bash --version` in the backup container per the doc, finds it missing (it is — alpine/busybox), and escalates a false alarm; meanwhile the genuinely unverified part (does `restore.sh` actually restore?) stays unverified.

**Fix:** rewrite UNVERIFIED-5 to reflect the POSIX-sh rewrite; replace the bash check with "run a real backup + restore cycle against a scratch database on first deploy".
