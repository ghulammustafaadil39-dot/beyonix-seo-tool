## MEDIUM

### B1-1 · API-key scope model not enforced on ~20 GET routes (least-privilege gap)
`backend/src/routes/competitors.ts`, `ga4.ts`, `gsc.ts`, `sites.ts`, `settings.ts`,
`billing.ts`, `account.ts` — various lines (see below).

`requireScope` is the documented F-13 gate for API-key callers ("fine-grained
access is otherwise gated by requireScope", `middleware/access.ts`), and the
scope catalog (`API_SCOPES`) defines `:read` scopes per resource. Mutations all
got gates in the A1-H2 fix, but these READS have no `requireScope`/`requireRoleOrScope`
at all — any valid API key, regardless of its granted scopes, can read them:
- `GET /sites`, `/sites/:id`, `/sites/:id/overview` (`sites.ts:143,150`, overview ~283) — no `sites:read` check
- `GET /sites/:id/competitors`, `/compare`, `/keyword-gaps`, `/content-gaps`, `/backlinks` (`competitors.ts:52,115,…`) — no `competitors:read` check
- `GET /sites/:id/gsc/queries` (`gsc.ts:50`), `GET /sites/:id/ga4/properties`, `/ga4/overview` (`ga4.ts:88,131`) — no scope check; exposes Search Console query data + GA4 traffic data
- `GET /settings`, `/usage`, `/settings/providers` (`settings.ts:52,~108,~114`) — no scope check; exposes `notify_email`, `telegram_chat_id`, plan/usage
- `GET /billing/subscription`, `/billing/invoices` (`billing.ts:256,272`) — no `billing:read` check
- `GET /account/members`, `/workspaces`, `/alert-rules`, `/digest`, `/notifications`, `/account/sites/:siteId/onboarding` (`account.ts`) — no scope check
Trigger: mint a key with only `webhooks:read`, then `curl -H "x-api-key: …" /api/v1/sites/:id/gsc/queries` → 200 with another resource's data. Still tenant-scoped (no cross-tenant leak), but it defeats the least-privilege scope model the product advertises.
Fix: add `requireScope('<resource>:read')` (session users pass through unaffected) to each read route, mirroring keywords/ranks/audits/geo/content/reports/backlinks which already do this.

### B1-2 · `POST /billing/portal` has no authorization gate beyond auth — any API key can mint a Stripe portal session
`backend/src/routes/billing.ts:295` — `authed.post('/billing/portal', async (req) => …)` with NO `preHandler`.
The portal URL grants full billing management (cancel subscription, change plans, view invoices, update payment method). Any valid API key — even one minted with only `sites:read` — can obtain it for the tenant. There is also no `billing:write` scope in `API_SCOPES` (only `billing:read`), so least-privilege billing actions are unexpressible.
Trigger: `curl -X POST -H "x-api-key: bseo_…" /api/v1/billing/portal` → `{url: "https://billing.stripe.com/…"}`.
Fix: gate with `requireRoleOrScope(['owner','admin'], 'billing:read')` at minimum (ideally add a `billing:write` scope and require it).

### B1-3 · Manual refresh routes lie: BullMQ jobId dedupe makes repeat clicks silent no-ops, API still returns `{ok:true, queued:true}`
- `backend/src/routes/ranks.ts:402` — `idempotencyKey: \`rank:${siteId}:${YYYY-MM-DD}\``
- `backend/src/routes/backlinks.ts:132` — `idempotencyKey: \`bl:${siteId}:${YYYY-MM-DD}\``
- `backend/src/routes/reports.ts:78` — `idempotencyKey: \`report:${site.id}:${weekStart()}\``

BullMQ `Queue.add` with a duplicate `jobId` returns the EXISTING job without error — including already-completed jobs, because `removeOnComplete: 100` (`queues.ts`) keeps them. So a user clicking "refresh rankings" twice in one day (or after the first run completed) gets `{ok:true, queued:true}` while nothing is queued. This is the same silent-dedupe class as the A1-H1 audit-race bug, but for these three routes the dedupe was never made per-request.
Trigger: POST `/sites/:id/ranks/refresh` twice within a day → second returns `queued:true`, no new job in BullMQ.
Fix: check for an existing live job first and return `{ok:true, queued:false, deduplicated:true}`, or use a per-click unique jobId (the spend is user-initiated and metered anyway).

## LOW

### B1-R1 · (fix-regression of A1-L5) `userId = "apikey:<uuid>"` still flows into UUID columns → 500 on ~15 user-scoped endpoints
`backend/src/middleware/auth.ts:153` still sets `userId: \`apikey:${row.id}\`` for API-key callers. The pass-1 commit claimed A1-L1..L6 fixed, but every direct `req.tenant.userId` / `u(req)` use against a UUID column still throws Postgres `22P02 invalid input syntax for type uuid` → 500:
- `routes/auth.ts:689` (`password/change`), `:727` (`email/change`), `:755` (`DELETE /auth/account`), `:787/:808/:832` (totp setup/enable/disable), `:844/:848` (`GET /auth/sessions` list query), `:867` (session revoke), `:875` (`logout-everywhere` → `revokeAllSessions` → `UPDATE users … WHERE id='apikey:…'`)
- `routes/account.ts:800,810` (`notification_rules.user_id` UUID, `016_notifications.sql:9`), `:820` (`notification_digests.user_id`), `:875` (onboarding has no user_id — safe), plus member/invite flows at `:499,:526,:552,:579,:597,:615` (reachable only by `admin`-scoped keys, which are unmintable — latent only)
`services/sessions.ts`, `services/totp.ts`, `services/emailVerification.ts` all take the raw string into `WHERE id = $1` / `user_id = $2`.
Trigger: `curl -X POST -H "x-api-key: bseo_…" /api/v1/auth/password/change` → 500 INTERNAL (and noisy error logs).
Fix (one place): set `userId: null` (or the raw key UUID) in the API-key ctx in `tenantFromApiKey`, and add `requireHumanSession` to all user-account routes; or make `authPlugin` reject API keys on routes that need a human user.

### B1-R2 · (fix-incomplete of S-09) prompt-injection delimiting missed `content-outline` / `content-draft` / seo-assets
`backend/src/services/prompt.ts:16` `renderPrompt` interpolates `{{var}}` raw — callers must pre-delimit. `contentEngine.ts:30-53` (`generateOutline`, `generateDraft`) pass `keyword`, `title`, `tone`, `siteDomain`, `outline` with NO `delimitUntrusted`, and the templates (`src/prompts/content-outline.txt`, `content-draft.txt`) carry no "treat as data" instruction. Same gap in `contentWorkflow.ts:257-264` (`generateSeoAssets` interpolates `"${input.title}"` / `"${input.keyword}"` raw; only `topics` is delimited). S-09's fix covered onpage + geo + brief but not these.
Impact is self-injection only (a tenant injecting into their own content generation; output lands in their own draft), hence LOW — but it breaks the codebase's own `delimitUntrusted` convention.
Fix: wrap all user-controlled template vars in `delimitUntrusted(...)` at the three call sites.

### B1-4 · `getSerpSnapshot` cache-hit path hardcodes `providerIsMock: false`
`backend/src/services/serpSnapshots.ts:~138` (and the flight-lock-winner path): on a cache hit the code returns `providerIsMock: false` without reading the row's `source_provider` (`readFreshSnapshot` doesn't even select it). A snapshot fetched by the mock provider and then served from cache is labeled as real data — the same honesty-label class as A3-M1/A3-M2.
Fix: select `source_provider` in `readFreshSnapshot` and set `providerIsMock: source_provider === 'mock'`.

### B1-5 · No ongoing reaper for stuck `audits.status='queued'` rows — route check has no age bound
`backend/src/routes/audit.ts:100-106` — the active-audit SELECT has no age filter, while the worker's dup check (`crawlJobs.ts:306-311`) only looks back 24h. Migration 041 cleaned pre-existing orphans, but if a future row ever sticks in `queued` (crash between `enqueue()` throwing and the failed-marking UPDATE at `audit.ts:170-174`), every future audit for that site 409s forever and the partial unique index blocks worker recovery inserts. Narrow window, permanent effect.
Fix: add a scheduler sweep marking `queued` rows older than ~2h as `failed` (same predicate as the migration), or add an age bound to the route's SELECT.

### B1-6 · `planIdFromStripePrice` reverse map omits annual prices
`backend/src/providers/stripe.ts:14-27` — only `STRIPE_PRICE_STARTER/GROWTH/PRO` are consulted, not `STRIPE_PRICE_*_ANNUAL` (which `priceIdForPlan` supports). For annual subscribers, `customer.subscription.updated` plan resolution depends entirely on the `subscription_data.metadata.planId` fallback; if metadata is ever absent (dashboard-created subscription), the plan falls back to the stale stored value. The "single source of truth = price id" claim is incomplete.
Fix: include the `_ANNUAL` env vars in the reverse map.

### B1-7 · `importKeywords` does up to 1000 sequential single-row INSERTs (A1-L1 pattern, unbatched)
`backend/src/services/keywordService.ts:481-492` — one round trip per keyword (cap 1000 via `parseKeywordBulkImport`). Same N+1 class as A1-L1 (which was batched for backlinks). Also `skipped: kws.length - imported` is wrong when `getKeywordMetrics` drops keywords with no data.
Fix: batch the upsert like the backlinks upload (500/statement); compute skipped from actual processed count.

### B1-8 · `routes/audit.ts` `isoWeekKey()` still has the N-A2-2 local/UTC mix
`backend/src/routes/audit.ts:19` — `new Date(Date.UTC(d.getFullYear(), d.getMonth(), d.getDate()))` mixes local getters into `Date.UTC`, the exact bug fixed in `scheduler.ts` `isoWeek()`. Harmless today (jobId is unique per audit row, so the week key is cosmetic), but it will produce the wrong week label near midnight in non-UTC timezones; also duplicates `isoWeek` logic instead of sharing it.
Fix: delete the local copy and import `isoWeek` from `scheduler.ts` (or `weekStart` semantics).

### B1-9 · `getKeywordMetrics` commits full reservation on partial provider results
`backend/src/services/keywordCache.ts:52` — `actualUnits: missing.length` is committed even when `provider.keywordMetrics(missing)` returns fewer rows (failures are silently dropped at line 55). Over-records `keyword_metrics` spend vs actual.
Fix: `actualUnits: fresh.length`.

### B1-10 · Checkout holds the tenant row lock across a Stripe network call
`backend/src/routes/billing.ts:196-236` — `SELECT … FOR UPDATE` → `getPayments().createCustomer(...)` (network I/O) → `UPDATE` → `COMMIT`. The N-A1-5 fix (FOR UPDATE) is correct for the double-create race, but holding the lock across the Stripe call serializes all concurrent billing mutations for the tenant on Stripe latency; and if `UPDATE` fails after `createCustomer` succeeded, the Stripe customer is still orphaned (narrower than before, but not closed).
Fix: create the Stripe customer BEFORE `BEGIN`, then do lock+check+update in the transaction (re-check `stripe_customer_id` inside, reuse-or-adopt on conflict).
