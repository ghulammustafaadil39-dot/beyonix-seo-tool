## HIGH

### H-1 — D5-H-1 trial-gate fix is route-middleware only: all 7 scheduled spend jobs bypass it, so trial-expired AND suspended tenants keep burning provider money indefinitely
- **Files:** `backend/src/scheduler.ts:40-57` (`enqueueForVerifiedSites`), `:73-165` (schedules), `backend/src/middleware/requireSubscription.ts` (gate), `backend/src/services/*.ts` processors
- **What's wrong:** The D5-H-1 fix ("every signup got paid Starter free forever") added `requireActiveSubscriptionOrTrial` as a Fastify **preHandler**. I verified it is wired on the spend routes of all 8 route files (keywords, ranks, content, geo, audit, reports, competitors, backlinks — including the single-spend-route files audit.ts:67 and ranks.ts:396). But the 7 recurring spend schedules — `weekly-crawl` (:73), `rank-checks` daily (:83), `weekly-reports` (:111), `daily-light-check` (:119), `monthly-keyword-refresh` (:132), `weekly-geo-checks` (:145), `weekly-backlink-sweep` (:153) — all funnel through `enqueueForVerifiedSites`, whose query is `SELECT id, tenant_id FROM sites WHERE verified = TRUE AND deleted_at IS NULL`: **no join to tenants, no trial/subscription/suspended/read_only filter**. The comment even says "Scheduler bulk-enqueues are system-initiated". I grepped every job processor (`keywordJobs`, `rankJobs`, `crawlJobs`, `geoJobs`, `backlinkJobs`, `contentJobs`, `reportJobs`) for `read_only` / `trial_ends_at` / `suspended_at`: **zero hits**. `requireSite` checks only site existence. Metering only enforces plan quotas — and a trial-expired tenant keeps `plan_id='starter'`, so the jobs spend happily against Starter quotas. The gate's `read_only=TRUE` flip (requireSubscription.ts) doesn't help: the scheduler never reads it, and it's only flipped lazily on the next gated-route hit anyway.
- **Concrete trigger:** User signs up, verifies a site, uses the 14-day trial, never pays. Day 15+: every API spend route 402s — but the daily rank-check tick keeps enqueueing `rank:<site>:<day>` jobs and the weekly crawl/report/geo/backlink sweeps keep running, spending real DataForSEO + LLM budget against Starter quotas **forever**. Same for a platform-suspended abuser: the D5-L-2 fix paused their *Stripe billing* (they stop paying) but their scheduled jobs keep spending *our* money — suspend is "fully blocked" at the API choke point (`enforceTenantState`) but wide open in the background.
- **Fix:** Filter scheduler enrollment by billing liveness: join `tenants` (+ `subscriptions`) in `enqueueForVerifiedSites` / the rank-check query and skip tenants where `suspended_at IS NOT NULL` or (trial expired AND no subscription in `active/trialing/past_due/incomplete`). Belt-and-braces: check the same predicate at the top of each spend processor (jobs can sit queued across the expiry boundary).
- **Overlap:** NEW. D5-H-1 filed the free-Starter hole and its fix was verified at the route layer in pass #4; nobody checked the scheduler/worker path.

### H-2 — `incomplete` subscriptions bypass the ALREADY_SUBSCRIBED block, then the first subscription's webhooks clobber the second subscription's row — paying customer downgraded while billed
- **Files:** `backend/src/routes/billing.ts:57` (`ACTIVE_SUBSCRIPTION_STATUSES = ['active','trialing','past_due']` — no `'incomplete'`), `backend/src/providers/stripe.ts:484-733` (subscription event branches key `ON CONFLICT (tenant_id)` / `downgradeTenant(tenantId, …)` without checking `stripe_sub_id`)
- **What's wrong:** Two compounding defects. (a) A tenant whose first payment fails lands in local status `'incomplete'` (stripe.ts sets it from `checkout.session.completed` with `subObj.status='incomplete'` and from `subscription.updated(incomplete)`). `'incomplete'` is **not** in the checkout block list, so `POST /billing/checkout` happily creates a **second** Stripe subscription — the D1-H-1 fix deliberately kept `past_due` in the block list for exactly this reason but `incomplete` was missed, even though an `incomplete` Stripe subscription is equally alive (it auto-retries / expires after 23h). (b) Every subscription webhook handler assumes ≤1 subscription per tenant: `customer.subscription.created/updated` upserts `ON CONFLICT (tenant_id)` with whatever `subId` the event carries, and the `canceled`/`incomplete_expired`/`deleted` branches call `downgradeTenant(tenantId, …)` unconditionally — never verifying the event's subscription id matches the row's `stripe_sub_id`.
- **Concrete trigger:** Checkout #1 with a card that fails 3DS → subscription A `incomplete`. User retries via a fresh checkout (natural behavior; nothing blocks it) → subscription B `active`, row now tracks B. 23h later Stripe auto-expires A → `customer.subscription.updated(incomplete_expired)` for **A** → `resolveTenantForSubscription` misses on sub id (row tracks B), falls through to `stripe_customer_id` → resolves the tenant → `downgradeTenant(tenantId, 'subscription_incomplete_expired')` → tenant on Starter, local status `canceled`, **while subscription B is active and billing Pro**. The ordering guard doesn't save us: the expiry event is newer than B's events. Variant: A's `past_due` retry events flip-flop the row between the two subscriptions.
- **Fix:** Add `'incomplete'` to `ACTIVE_SUBSCRIPTION_STATUSES` (the correct recovery for a failed first payment is the billing portal's open-invoice payment, not a second subscription — mirrors the D1-H-1 reasoning). Independently, make the subscription event branches verify `data.id === stored stripe_sub_id` and ignore/mismatch-log events for non-current subscriptions instead of clobbering.
- **Overlap:** NEW. D4-d1 H-1 covered the `past_due`→`canceled` variant of the double-subscription hole; the `incomplete` variant and the cross-subscription clobbering were never reported.

## MEDIUM

### M-1 — `incomplete` counts as billable in the trial gate: rolling free access via async-payment checkouts, no payment ever succeeding
- **Files:** `backend/src/middleware/requireSubscription.ts:29,31` (`BILLABLE_SUBSCRIPTION_STATUSES` includes `'incomplete'`), `backend/src/routes/billing.ts:57`
- **What's wrong:** Treating `incomplete` like `past_due` (grace) is defensible for a dunning flow, but in the **trial gate** it creates a free-access loop. A Stripe Checkout session can complete while the subscription is `incomplete` (async payment methods — SEPA debit, bank transfer — where settlement takes days; `checkout.session.async_payment_failed` isn't handled, so nothing flips the local row early). Local status `incomplete` ∈ billable → paid features unlocked. Stripe auto-expires the incomplete subscription after ~23h → `incomplete_expired` → downgrade → status `canceled` → and since `incomplete`/`canceled` are not checkout-blocked, the user just starts another checkout. Idempotency doesn't stop it (`withIdempotency` is a pass-through without the client header, and a new header mints a new session).
- **Concrete trigger:** Trial expires → checkout with SEPA debit (never funded) → ~23h+ of paid features per cycle → expiry → repeat. Zero successful payments, indefinite rolling access. Each cycle is manual, so this is abuse-effort-gated, not a drive-by.
- **Fix:** Drop `'incomplete'` from `BILLABLE_SUBSCRIPTION_STATUSES` (keep it in the dunning/grace logic where it belongs), or require the trial gate to see a *paid* invoice / non-`incomplete` status. Handle `checkout.session.async_payment_failed` → flip to `past_due` immediately.
- **Overlap:** NEW. C5-L-2 (pass #3) made `incomplete` not *activate* the paid plan at webhook time, but the gate's inclusion of `incomplete` as billable was never examined.

### M-2 — Any transient failure between webhook ledger insert and completion permanently loses the event (D5-M-1 fixed only the 502 path)
- **Files:** `backend/src/providers/stripe.ts:459` (insert-before-process), `:495` (ordering guard), end-of-function `markProcessed`
- **What's wrong:** D5-M-1 correctly identified that the 502 `PRICE_NOT_CONFIGURED` throw left its ledger row behind and turned retries into permanent no-ops — and that path now deletes the row (`:650`). But the **general** case is unchanged: the event id is inserted *before* any processing, and *any* exception after that point (DB failover mid-upsert, deploy restart during the ~10 sequential queries, pool exhaustion) makes the route return 500 → Stripe retries → `ON CONFLICT DO NOTHING` → `rowCount===0` → `markProcessed()` (stamps `processed_at=now()`) → `{deduplicated:true}`. The retry is swallowed **and the row is marked processed**, so there is no record that the event was never applied. I confirmed there is no reader/reaper of `stripe_webhook_events ... WHERE processed_at IS NULL` anywhere (only `routes/account.ts:161` lists the table for the erase enumeration).
- **Concrete trigger:** `invoice.paid` for a Pro renewal is being processed when Postgres fails over → 500 → Stripe retries for 3 days, every retry deduped → tenant stays `past_due` → `processBillingGrace` downgrades a customer who paid. The reverse direction loses money: a swallowed `customer.subscription.deleted` leaves a canceled payer on the paid plan.
- **Fix:** Mark the ledger row failed-but-retryable on exception (catch around processing → `UPDATE stripe_webhook_events SET processed_at=NULL, attempts=attempts+1 ...`), and make the conflict branch re-attempt rows whose `processed_at IS NULL` instead of blindly deduping. Or move the insert to after successful processing and accept at-least-once semantics with the existing idempotent upserts (they already are).
- **Overlap:** NEW as a general finding; D5-M-1 (pass #4) covered only the deliberate-502 path and is marked fixed.

### M-3 — A late `invoice.payment_failed` resurrects a genuinely canceled subscription to `past_due` + fresh grace + dunning email
- **Files:** `backend/src/providers/stripe.ts:824` (`} else if (!existingGrace) {`), in the `invoice.payment_failed` branch
- **What's wrong:** The D1-H-1 logic handles the post-downgrade case (`curStatus==='past_due' && !existingGrace` → don't mint fresh grace). But when the local status is `'canceled'` — i.e. the subscription genuinely ended via `customer.subscription.deleted` → `downgradeTenant` (status `canceled`, `grace_until=NULL`) — a *later-created* `invoice.payment_failed` falls into `else if (!existingGrace)` and flips the row back to `past_due` with a **new 3-day grace** and emits the `invoice.payment_failed` dunning email ("Your plan stays fully active for a 3-day grace period"). The ordering guard doesn't stop it: this failure event is *newer* than the delete event (Stripe keeps retrying an open final invoice after the subscription is deleted).
- **Concrete trigger:** User cancels via portal (subscription deleted immediately) → Stripe Smart Retries keep hammering the open final invoice → next `invoice.payment_failed` (created after the delete) → tenant row resurrected to `past_due`, user gets a "payment failed — update your method" email for a subscription they canceled, and `POST /billing/checkout` 409-blocks them for 3 days ("already subscribed — use the portal") while the portal shows no active subscription.
- **Fix:** In the `payment_failed` branch, treat `curStatus==='canceled'` like the grace-consumed case: record the invoice, emit nothing, never mint grace or flip status. Only `past_due`/`incomplete`/`active`/`trialing` rows should enter dunning.
- **Overlap:** NEW.

### M-4 — Admin plan override writes a fake `active` subscription row that permanently dead-ends self-serve checkout
- **Files:** `backend/src/routes/admin.ts:187-208` (override upsert: `status='active', stripe_sub_id=NULL`), `backend/src/routes/billing.ts:275` (ALREADY_SUBSCRIBED block), `backend/src/routes/billing.ts:portal` (`NO_CUSTOMER` when `stripe_customer_id` null)
- **What's wrong:** The A1-M5 fix made the override sync the subscriptions row (`status='active'`, `stripe_sub_id=NULL`) so the trial gate and `getBillingWindow` see the comp. But that row now trips the checkout guard: `SELECT status ... → 'active'` ∈ `ACTIVE_SUBSCRIPTION_STATUSES` → 409 `ALREADY_SUBSCRIBED` "use the billing portal". The portal then 400s with `NO_CUSTOMER` (no `stripe_customer_id` — comps never touch Stripe). There is no admin endpoint to clear the override row. So a comped tenant who later wants to pay is stuck: checkout says "already subscribed", portal says "no customer", and only a manual DB edit unblocks them. Missed revenue + guaranteed support ticket, and the 409 message actively misdirects.
- **Concrete trigger:** Support comps a trial-expired user to Growth via `POST /admin/tenants/:id/plan` → user loves it, clicks "Upgrade to paid" → 409 → clicks through to portal → 400 NO_CUSTOMER → churn or ticket.
- **Fix:** Make the checkout block ignore override rows (`stripe_sub_id IS NULL`), or have the override write a distinguishable status (e.g. `'comped'`, added to the trial gate's billable list but not the checkout block list).
- **Overlap:** NEW. Pass #4 verified the A1-M5 read_only/subscription-sync aspects; the checkout dead-end wasn't examined.

### M-5 — Suspend's Stripe pause is best-effort with no retry or reconciliation: a failed pause leaves a suspended tenant billed indefinitely, reported as `ok:true`
- **Files:** `backend/src/routes/admin.ts:138-150` (suspend handler), `backend/src/providers/stripe.ts:252-264` (`pauseSubscription`)
- **What's wrong:** The D5-L-2 fix (suspend now pauses Stripe billing via `pause_collection`) is real, but the pause is explicitly best-effort: on `pauseSubscription` throw, the handler logs, records `billingPaused: []` in the audit meta, and returns `{ ok: true, billingPaused: [] }` — **indistinguishable from "there was nothing to pause"** unless someone reads the audit log. There is no retry, no scheduled reconciliation of suspended tenants' Stripe state, no alert. A Stripe blip at suspend time → tenant fully blocked from the product, charged every month until a human notices.
- **Concrete trigger:** Admin suspends an abusive paying tenant during a Stripe API degradation → `pauseSubscription` throws → suspend "succeeds" → next month the suspended tenant is invoiced for a product they cannot access → chargeback.
- **Fix:** On pause failure, return a non-ok signal (e.g. `ok:true, billingPaused:[], billingPauseFailed:true`) and add a daily reconciliation job: for tenants with `suspended_at NOT NULL`, verify `pause_collection` is set on their Stripe subscriptions (or re-attempt the pause). At minimum surface the failure in the admin tenants list.
- **Overlap:** NEW aspect. D5-L-2 (pass #4) filed "suspend doesn't touch Stripe billing" — the pause itself is now implemented and verified; this is about its failure handling.

## LOW

### L-1 — Out-of-order `checkout.session.completed` is dropped as stale → coupon reserved slot leaks forever
- **Files:** `backend/src/providers/stripe.ts:489-510` (ordering guard; `checkout.session.completed` is subject to it, only `charge.refunded` is exempt), `:518-620` (checkout branch redeems the coupon)
- **What's wrong:** If `customer.subscription.updated` is *delivered* before `checkout.session.completed` (Stripe does not guarantee order), the subscription event advances `last_event_at`, and the later-arriving (earlier-created) session event is dropped as `stale:true` — correctly for state, but the coupon path only runs inside the dropped branch. The slot reserved at checkout (`reserved_count+1`) is then never redeemed **and never released**: `checkout.session.expired` won't fire for a completed session, and the D5-L-1 release only runs when the redeem predicate executes. Each occurrence permanently burns one redemption slot; with `max_redemptions=10` a few out-of-order deliveries silently exhaust the coupon. Side effects: the `checkout.completed`/`trial.started` billing event never emits and `subscriptions.coupon_code` is never recorded.
- **Concrete trigger:** Coupon `LAUNCH50` (cap 10) + a burst of checkouts where Stripe delivers subscription events first a few times → 3 slots leak → effective cap becomes 7.
- **Fix:** Exempt `checkout.session.completed`'s coupon-redemption from the stale drop (redeem the coupon even when the state upsert is skipped as stale), or release the reservation when dropping a completed session as stale.
- **Overlap:** NEW trigger. D5-L-1 (pass #4, fixed) covered the deactivation-mid-flight leak; this is the out-of-order-delivery leak.

### L-2 — Invite-accept dissolve swallows `cancelTenantBilling` failure and deletes anyway (erase aborts; dissolve doesn't)
- **Files:** `backend/src/routes/account.ts:596-601` (dissolve branch: try/catch logs and continues to `DELETE FROM tenants`)
- **What's wrong:** The D1-L-13 fix calls `cancelTenantBilling(oldTenantId)` before dissolving the shell — good. But on failure it `console.error`s and **proceeds with the dissolve**, while the erase flow (`:1067`) treats the same failure as 502 and aborts with no rows deleted. The dissolve failure mode is exactly the C1-H-1 hole the fix was meant to close: Stripe keeps charging a customer whose tenant row is gone, and unlike erase there's no tombstone and the user (now on another tenant) can't even see it. Secondary: the cancel runs inside the invite-accept transaction's try block but against the pool (not the tx client); if a *later* step (DELETE, logActivity) throws and the tx rolls back, the shell survives with its Stripe subscription already canceled — annoying but recoverable via re-checkout.
- **Concrete trigger:** Stripe API 500 during invite-accept by a sole user of a paying shell → shell dissolved, subscription still active → monthly charges with no account and no local record.
- **Fix:** Mirror erase: on cancel failure, throw 502 and abort the accept (user retries the invite); or on failure, skip the dissolve and leave the shell intact with an explicit error.
- **Overlap:** NEW aspect. D1-L-13 (pass #4) filed "dissolve doesn't cancel" — the cancel call is now present and verified; this is about its failure semantics.

### L-3 — Mock `pauseSubscription`/`resumeSubscription` loses the pre-pause status (dead `mockPausedStatus` map)
- **Files:** `backend/src/providers/stripe.ts:286` (map), `:344-376` (mock pause/resume)
- **What's wrong:** The comment says the map "remembers pre-pause statuses", but `pauseSubscription` hardcodes `mockPausedStatus.set(key, 'active')` regardless of the actual status (`trialing`/`past_due`/`incomplete` all become `'active'` on resume), and `resumeSubscription` never reads the map at all — it just `SET status='active'` in SQL and deletes the entry. So the map is write-only dead code and the status is always flattened to `active`.
- **Concrete trigger:** Dev/test only. Suspend a `past_due` (in-grace) tenant in mock mode → unsuspend → grace/dunning state silently becomes `active`.
- **Fix:** Store the real pre-pause status from the `RETURNING` row and restore it on resume (the real provider doesn't need this — Stripe keeps the status server-side).
- **Overlap:** NEW.

### L-4 — Orphaned-Stripe-customer race: `stripe_customer_id` written after the Stripe call, so a crash leaves an un-cancelable subscription
- **Files:** `backend/src/routes/billing.ts` (checkout: `createCustomer` before the DB transaction writes `stripe_customer_id`), `backend/src/providers/stripe.ts:889-920` (`cancelTenantBilling` no-ops when `stripe_customer_id` is null)
- **What's wrong:** The checkout flow creates the Stripe customer (and then the subscription via the session) *before* the transaction that persists `tenants.stripe_customer_id`. A process crash in that window leaves a live Stripe customer + subscription with no local link. Every cancel path (`cancelTenantBilling` for erase, last-user delete, and dissolve) looks up the customer id from the tenant row → null → silent no-op → the ghost subscription bills forever with no local record and no tenant for webhooks to resolve to.
- **Concrete trigger:** Deploy restart / OOM between `createCustomer` and the transaction commit, user completes the Stripe session → monthly charges, `stripe_customer_id` NULL locally, invisible to all cancel flows.
- **Fix:** On checkout, reconcile by email/metadata as a fallback in `cancelTenantBilling` (Stripe customer `metadata.tenantId` is set at creation), or record the Stripe customer id in a pending-checkout row *before* the Stripe call.
- **Overlap:** NEW as a filed finding. D4-d5 noted this exact residual as "noted only" without filing it.

## Verified as holding (not findings)

- **Suspend/unsuspend pause mechanics:** real provider pauses `active/trialing/past_due/incomplete` subs via `pause_collection: {behavior:'mark_uncollectible'}` and resume clears it; `DisabledPaymentsProvider` no-ops honestly; suspended tenants are fully blocked at the auth choke point (`enforceTenantState`, middleware/auth.ts:259) — no portal/checkout access while suspended. The suspend-during-grace → unsuspend plan mismatch self-heals: the `past_due`→`active` transition emits `customer.subscription.updated`, which re-resolves the plan from the Stripe price id.
- **Dissolve-cancel happy path:** `cancelTenantBilling` runs before the shell `DELETE`; a shell *cannot* hold credits ( `tenant_credits` is in `SHELL_TENANT_TABLES`, so any credit balance forces 409 `INVITE_WOULD_ORPHAN_DATA` instead of dissolving) — the erase-flow tombstone gap does not apply here.
- **Webhook idempotency/ordering:** ledger insert-before-process, synthetic `mock-payload:` ids for id-less mock events, `mock-confirm:<session_id>` dedupe, per-tenant `last_event_at` guard with the `charge.refunded` exemption (NEW-4), and the D5-M-1 fix verified (ledger row deleted before the 502 `PRICE_NOT_CONFIGURED` throw so retries reprocess).
- **Trial gate wiring:** `requireActiveSubscriptionOrTrial` present on the spend routes of all 8 paid route files (verified per-route; the single-use files audit.ts:67 and ranks.ts:396 each have exactly one spend route). Trial length is server-side (`signupTrialDays()`), never client-supplied; disposable-email block exists (defaults off — `config.ts`, `DISPOSABLE_EMAIL_BLOCK=false`).
- **Coupon lifecycle:** atomic reserve under row lock, no lock held across the Stripe call (D5-L-5 fix holds), single release guarded by `couponReserved` (D5-M-3 fix holds), release-on-failed-redeem (D5-L-1 fix holds), `checkout.session.expired` releases abandoned holds (real mode).
