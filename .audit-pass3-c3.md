## Findings

### L-1 — LOW — `billingApi.checkout` still offers/forwards `trialDays`, which the backend rejects
- **File:** `frontend/lib/api.ts:545-570` (`CheckoutOptions`, doc comment, body spread).
- **What:** The interface offers `trialDays?: number`, the comment claims the "real
  checkout schema is { planId, interval?, couponCode?, trialDays? }", and the body
  spread forwards it. The backend `checkoutSchema` (`backend/src/routes/billing.ts`,
  `additionalProperties: false`) has NO `trialDays` — A1-M6 moved trial length to
  server-side plan config and the client must not send it.
- **Trigger:** Any caller passing `trialDays` (the type invites it) gets a 400
  validation error. Today the only caller (`billing/page.tsx:234`) doesn't pass it,
  so this is a live wire waiting to be tripped, plus a false contract statement in
  the comment.
- **Fix:** Remove `trialDays` from `CheckoutOptions`, the doc comment, and the body
  spread. (Same class as the research-`limit` issue below.)

### L-2 — LOW — `keywordsApi.research` advertises a `limit` param the backend ignores
- **File:** `frontend/lib/api.ts` (`keywordsApi.research(siteId, seeds, limit?)`).
- **What:** The helper takes `limit?: number` and includes it in the POST body. The
  backend `/sites/:id/keywords/research` schema accepts only `{ seeds }` (no
  `limit`, no `additionalProperties: false`), so a supplied limit is silently
  ignored. The one caller (`KeywordsTab.tsx:110`) doesn't pass it, and
  `JSON.stringify` drops the undefined — so no live breakage, but the signature
  promises a server capability that doesn't exist.
- **Fix:** Drop the `limit` param from the helper signature and body.

### L-3 — LOW — Impersonation handoff only works through the same-origin proxy; breaks under `NEXT_PUBLIC_API_URL` direct-API deploys
- **Files:** `frontend/app/api/admin/impersonate/route.ts`, `frontend/app/admin/page.tsx:132`,
  `frontend/lib/api.ts` (header comment documents the direct-API mode).
- **What:** The handoff sets `bseo_token` as a **host-only** cookie on the web origin
  and `api('/api/admin/impersonate')` is same-origin-routed. With `NEXT_PUBLIC_API_URL`
  set (the documented non-proxied deploy), the browser resolves that path against
  the API origin — the API has no `/api/admin/impersonate` (only `/api/v1/admin/impersonate`),
  so the call 404s; even a manual call to the handoff route would set the cookie on
  the wrong host, where direct-API calls never send it. The result is a loud failure,
  not a silent session mix-up — but the admin action advertises itself as available
  in a deploy mode where it cannot work.
- **Fix:** In the admin page, detect `NEXT_PUBLIC_API_URL` (build-time env, available to
  the client) and disable the "Start impersonation" action with an honest note
  ("requires the same-origin proxy deploy"), or document in RUNBOOK that direct-API
  deploys cannot impersonate.

### L-4 — LOW — Slack webhook URL persists in alert-rule config after the slack channel is removed
- **File:** `frontend/app/dashboard/notifications/page.tsx:169-180` (`toggleChannel`).
- **What:** Deselecting the `slack` channel patches `channels` but leaves
  `config.slack_webhook_url` untouched; `saveRule` re-sends the full config, so the
  unused Slack webhook URL (a credential) stays stored server-side indefinitely. If
  slack is re-enabled later, the old URL reappears pre-filled — arguably convenient,
  but its persistence after removal is undisclosed, and a rotated/deleted Slack
  webhook keeps a stale secret in the DB.
- **Trigger:** Enable slack on any alert rule, save a webhook URL, then deselect
  slack — `GET /api/v1/account/alert-rules` still returns `slack_webhook_url` in config.
- **Fix:** In `toggleChannel`, when removing `slack`, also delete
  `config.slack_webhook_url` (e.g. `const { slack_webhook_url, ...rest } = draft.config`).

### L-5 — LOW — v1 GEO tab platform checklist omits `claude`, contradicting its own comment
- **File:** `frontend/components/tabs/GeoTab.tsx:17` (`PLATFORMS`).
- **What:** The comment says the list "Must match the backend allowlist
  (`GEO_PLATFORMS_ALLOWED`)" but it is a strict subset: it omits `claude`, which the
  backend allowlist includes (`backend/src/services/geoService.ts:18`), and which
  `GEO_ENGINES` (`lib/api.ts`) and the embedded `GeoV2Panel` run-set both include.
  No contract violation (backend accepts subsets), just a missing engine option on a
  user-facing checklist.
- **Fix:** Add `'claude'` to `PLATFORMS`/`PLATFORM_LABELS`, or correct the comment if
  the omission is deliberate.
