## 2. NEW findings (3 LOW)

### NEW LOW-1 — H1-L-2's grace-minting branch races with itself across event types: concurrent `invoice.payment_failed` + `subscription.updated(past_due)` double-dun

**Files:** `backend/src/providers/stripe.ts:824-848` (subscription.updated branch), `:1014-1028` (invoice.payment_failed branch); `backend/src/services/billing.ts:137-144` (identical template for both types).

**What's wrong:** H1-L-2 made dunning fire only when the handler *reads* `existingGrace = NULL` — but both branches decide on a **stale pre-read**, and the mint is not atomic:
- subscription.updated: `SELECT grace_until … WHERE stripe_sub_id=$1` (`:824-825`) → upsert → `if (!existingGrace) emit` (`:847-848`).
- invoice.payment_failed: `SELECT status, grace_until … WHERE tenant_id=$1` (`:1014`) → `else if (!existingGrace)` mint + emit (`:1023-1028`).

A single failed payment produces *both* events within seconds, and the webhook route processes deliveries concurrently (no per-tenant serialization). If both handlers' SELECTs land before either's write commits, **both mint a grace and both emit** — two identical "Payment failed — please update your payment method" emails for one failure. The G1-L-1 `(event_id, type)` dedupe cannot fire: distinct event ids *and* distinct types. The money state is harmless (last-writer-wins on `grace_until`, seconds apart), but the exact duplicate-email class H1-L-2 was filed to kill survives through concurrency.

**Impact:** LOW — one extra identical email per incident; narrow race window; no money/data/privilege impact.

**Fix:** make the mint atomic and emit only on the atomic win, e.g. `UPDATE subscriptions SET status='past_due', grace_until=$2 WHERE tenant_id=$1 AND grace_until IS NULL` and emit only when `rowCount = 1` (payment_failed branch); for the updated branch, derive the emit decision from whether the upsert actually installed the grace rather than the pre-read.

**Duplicate check:** grepped all `.audit-pass{1..8}-*.md` for `grace.*concurrent`, `concurrent.*grace`, `mint.*race`. H1-L-1/H2-L-1 cover *same-event* concurrent duplication; H1-L-2 covers *sequential* cross-event duplication. The *concurrent cross-event* mint race is unreported. **NEW.**

### NEW LOW-2 — H1-L-2 regression: a transient failure of the single grace-minting send leaves the whole episode with ZERO dunning email

**Files:** `backend/src/services/billing.ts:83-150` (`send` closure); `backend/src/providers/stripe.ts:1023-1028`, `:847-848` (minting branches).

**What's wrong:** After H1-L-2, exactly one send attempt exists per failure episode — the grace-minting event. If that attempt's `notify.sendEmail()` throws (transient SMTP/provider failure), the `send` closure **catches it, marks the row `'failed'`, and returns normally** — the webhook is marked processed (`:1152-1157`), so Stripe never redelivers. Every subsequent event in the episode (`invoice.payment_failed` Smart Retries, `subscription.updated(past_due)`) now sees `existingGrace` set and stays silent *by design*. Nothing retries `notification_log` `'failed'` rows (verified: no sweeper, no scheduler, no reaper references billing dunning; the H2-L-1 takeover only helps if the *same* event_id is reprocessed, which can't happen for a 200'd webhook). Net: the customer gets **no "payment failed" warning at all**, then is downgraded 3 days later. Pre-H1-L-2, retry emails accidentally healed a failed first send; the fix removed that resilience without replacing it.

**Impact:** LOW — requires a transient email failure at the exact minting moment; no money/data/privilege impact; the `subscription.downgraded` email still fires at grace expiry, so the customer is not left entirely uninformed.

**Fix:** a small sweeper that re-drives `notification_log` rows with `status='failed'` and `notification_type IN ('invoice.payment_failed','subscription.past_due')` while the tenant's `grace_until` is still active — or, in the silent branches, re-emit when the minting attempt is recorded as `'failed'` rather than staying silent unconditionally.

**Duplicate check:** grepped for `transient.*email`, `send.*fail.*dun`, `'failed'.*retry`, `zero.*email`. The `notifications.ts:236` digest-count finding is a different defect. **NEW.**

### NEW LOW-3 — Two completed checkout sessions → two live Stripe subscriptions; the second is billed but locally invisible

**Files:** `backend/src/routes/billing.ts:306-347` (409 check inside row-lock txn; `createCheckoutSession` **after** COMMIT at `:347`); `backend/src/providers/stripe.ts:719-730` (E4-H-2 supersede guard).

**What's wrong:** The `ALREADY_SUBSCRIBED` 409 check runs inside the tenant-row-lock transaction, but `createCheckoutSession` happens after `COMMIT`. Two sessions created before either completes (concurrent double-click, or sequential: session A abandoned-but-valid-24h, session B started and completed, then session A completed from the old tab) both pass the 409 — no subscription row exists yet at check time. If the customer completes **both** payments, Stripe creates two live subscriptions. Locally, `ON CONFLICT (tenant_id)` keeps one row; the second subscription's `stripe_sub_id` either overwrites the first's (checkout upsert writes it unconditionally) or its `created`/`updated` events hit the E4-H-2 supersede guard ("tracked LIVE row + different sub id → warn-and-ignore"). Either way **one subscription is billed by Stripe every cycle while locally invisible** — no product signal, no admin signal beyond a `console.warn`.

**Impact:** LOW — requires the customer to complete two checkout payments (self-inflicted, visible on their card statement, admin can cancel the dupe via existing tooling); no cross-tenant or attacker angle. Same shape as F1-L-3 (rated LOW).

**Fix:** record the open checkout session id on the tenant/subscription row at creation and 409 (or warn) when a second session is created while one is open; and/or on `checkout.session.completed`, when adopting a sub id while a *different* live sub id is tracked, cancel the superseded Stripe subscription (or at minimum surface it — admin alert, not just `console.warn`).

**Duplicate check:** grepped for `double.checkout`, `two checkout`, `second checkout`, `double-billing`. D1 (pass#4) covered the *sequential post-downgrade* variant — fixed by D1-H-1 (status stays `past_due` → 409 blocks). F1-L-3 covered the *admin-override* variant. The *two-sessions-both-completed* variant is unreported. **NEW.**
