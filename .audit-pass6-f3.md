## NEW findings

### F3-L-1 — LOW — The pass#5 trial banner fix mislabels the trial-expired case: "Plan limit reached." + "Upgrade plan" shown to users who have no plan

**Files:** `frontend/components/ErrorBanner.tsx:36-61` (introduced by `58bee77`).

**What's wrong:** The fix widens `upgrade` to cover `SUBSCRIPTION_REQUIRED`, but
the rendered chrome is shared: the `<strong>` prefix always reads
"Plan limit reached." and the CTA always reads "Upgrade plan". For a
trial-expired, never-subscribed tenant the banner now reads:

> **Plan limit reached.** Your free trial has ended. Subscribe to continue using
> paid features. [Upgrade plan]

The label contradicts the message (no plan exists to have hit a limit), and the
button says "Upgrade plan" while the message says "Subscribe". This is
fix-introduced copy confusion on the primary monetization surface.

**Fix:** branch the strong label and CTA on the code, e.g.
`needsBilling ? 'Free trial ended.' : 'Plan limit reached.'` and
`needsBilling ? 'Subscribe' : 'Upgrade plan'`.

**Duplicate check:** grepped all `.audit-pass{1,2,3,4,5}-*.md` for "Plan limit
reached" — zero hits. **NEW** (introduced by the pass#5 fix).

### F3-L-2 — LOW — `ErrorBanner` ignores the plumbed `ApiError.upgrade` flag, so 403 `READ_ONLY_MODE` still dead-ends with a generic red banner

**Files:** `frontend/components/ErrorBanner.tsx:36` (checks codes only);
`frontend/lib/api.ts:22,88` (`upgrade` parsed from the body into `ApiError`);
`backend/src/errors.ts:21` + `backend/src/middleware/auth.ts:276-280`
(`READ_ONLY_MODE` sent with `{ upgrade: true }`).

**What's wrong:** The wire is complete end-to-end — backend serializes
`upgrade: true` into the error body, the frontend parses it into
`ApiError.upgrade` — but `report()` only tests
`e.code === 'LIMIT_EXCEEDED' || e.code === 'SUBSCRIPTION_REQUIRED'`. A
trial-expired tenant flipped read-only who then attempts any non-spend mutation
(e.g. site settings, which carry no trial gate per E1's verified-clean list)
gets 403 `READ_ONLY_MODE` → generic red banner, **no subscribe path**, even
though the backend explicitly flagged the error as upgrade-worthy. E3-MED-1's
own fix suggestion said "(or treat 402 + `upgrade` flag generically)"; the fix
took the code-list path instead and left the flag dead.

**Fix:** `const needsBilling = e.upgrade === true || e.code === 'SUBSCRIPTION_REQUIRED';`
(or treat `upgrade` as the generic condition and keep the code list as fallback).

**Duplicate check:** no prior audit filed the ignored `upgrade` flag (E3-MED-1
mentioned it only as an alternative fix implementation, never as a defect).
**NEW.**

### F3-L-3 — LOW — Trial-expired tenants flipped read-only see a factually wrong
reason: "usage exceeds your current plan limits"

**Files:** `backend/src/middleware/auth.ts:276-280` (message);
`frontend/components/ErrorBanner.tsx` (renders it verbatim);
`backend/src/middleware/requireSubscription.ts:53-61` (the flip that causes it).

**What's wrong:** When the trial lapses, `requireActiveSubscriptionOrTrial`
flips the tenant `read_only=TRUE`. Every subsequent non-spend mutation fails
with 403 `READ_ONLY_MODE` whose message says "Your workspace is in read-only
mode **because usage exceeds your current plan limits**." For a trial-expired
tenant that reason is false — their usage didn't exceed anything; they have no
subscription. The frontend renders the copy verbatim, so the user is told to
"remove excess resources" when the actual remedy is subscribing. Fix is backend
copy (differentiate the read-only reason, or have the frontend show its own
trial-specific message for `READ_ONLY_MODE` when `tenant_trial_ends_at` is past),
flagged here because it surfaces directly in the just-fixed trial UX.

**Duplicate check:** no prior audit mentions this message. **NEW.**
