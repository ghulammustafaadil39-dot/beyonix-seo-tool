## Findings (all NEW — none reported in passes #1–#3; searched all `.audit-pass*.md`)

### M-1 — MEDIUM — Invite-accept returns the session JWT in the JSON body, contradicting the project's cookie-only token policy
- **Files:** `frontend/lib/api.ts:657-664` (`InviteAccepted`); `backend/src/routes/account.ts:632`
  (verified read-only for the contract).
- **What:** `POST /api/v1/account/invitations/accept` returns
  `{ ok: true, tenantId, role, token: fresh }` where `fresh` is the newly-minted,
  tenant-bound session JWT. The frontend codifies this in its types with the comment
  *"the body token is the new tenant-bound session JWT per the frozen contract addendum."*
  The contract addendum is real (`CONTRACTS.md:422` records it), so this is a
  **documented, deliberate exception** — but it contradicts the project's own A3-H1
  "JWT-in-body" policy (session JWT delivered ONLY via httpOnly cookie, never in a
  JSON body), which was enforced by fixing the equivalent impersonation case.
  Any XSS on the accept page at accept time (or a malicious extension, devtools
  shoulder-surf) captures a live tenant session JWT from the response body.
- **Trigger:** Accept any team invitation in a browser with script access to the page;
  the accept response body contains a usable session token.
- **Mitigating facts:** the accept page itself never reads `res.token` (it relies on
  the httpOnly cookie + `authApi.me()` verification, `app/dashboard/team/accept/page.tsx:54-66`),
  so no frontend code path consumes the token today.
- **Fix:** Re-confirm the exception with the security owner; the safer resolution is
  to stop returning `token` in the body (API clients can use the cookie flow, as the
  browser does). At minimum, remove it from the browser-facing typed contract
  (`token?: never` on `InviteAccepted`) so no future caller can adopt the insecure pattern.

### M-2 — MEDIUM — False "free trial" claim on the public pricing page, landing page, and billing notice
- **Files:** `frontend/app/pricing/page.tsx` ("Every plan starts with a free trial —
  no credit card required."); `frontend/app/page.tsx:82-83` (FAQ: "Every plan starts
  with a free trial — no credit card required. You only pay when you decide to keep
  it."); `frontend/app/dashboard/billing/page.tsx` (~line 202, plan-preselect notice:
  "subscribe below to start your free trial"); CTAs read "Start free with {plan}".
- **What:** The backend plan config (`backend/src/plans.ts`) sets `trial_days: 0` for
  **all three plans** (starter/growth/pro), with the comment "Default 0 (no trial);
  raise per plan when the business wants trials." Checkout only applies a trial when
  `trial_days` is truthy (`backend/src/routes/billing.ts:316`). There is no free trial
  in the shipped product — the marketing claim is false advertising on public pages.
- **Trigger:** Any visitor reads /pricing or the landing-page FAQ; any new signup
  arriving with `?plan=` sees the billing-page trial notice.
- **Fix:** Remove or qualify the trial claim on all three pages (and the "Start free"
  CTA copy) until `trial_days` is actually enabled per plan. (The 14-day refund FAQ
  is consistent with `app/legal/terms` and is fine.)

### L-1 — LOW — Pricing table advertises "Audits / month: 4/12/30" with no backend enforcement
- **Files:** `frontend/app/pricing/page.tsx` (`LIMIT_ROWS`: `['Audits / month', '4', '12', '30']`);
  `frontend/app/dashboard/billing/page.tsx:26` (`audits_month: { label: 'Audits per month' }`).
- **What:** `usageSummary` (`backend/src/metering.ts:186-199`) reports only
  `sites, keywords_tracked, ai_words, geo_checks, serp_checks, keyword_metrics, crawl_pages`
  — there is no `audits_month` limit key anywhere in the backend, so the advertised
  per-plan audit caps are unenforced and the dashboard meter for them can never render.
  (Audits are presumably bounded indirectly by `crawl_pages`.)
- **Trigger:** Customer on Starter runs a 5th audit in a month — nothing stops them,
  contradicting the pricing table.
- **Fix:** Remove the row from the pricing table or implement a real `audits_month`
  limit in `plans.ts` + metering.

### L-2 — LOW — `/docs/api` rate-limit statement contradicts the implementation
- **File:** `frontend/app/docs/api/page.tsx` ("Limits are per tenant per minute.").
- **What:** The global limiter is per-IP (`backend/src/index.ts:84-89`), and API-key
  limits are per-KEY (`apikey:${keyId}`, `backend/src/middleware/auth.ts:138-148`).
  Nothing is "per tenant per minute." The sibling api-keys page ("Each key has its own
  per-minute rate limit") states it correctly.
- **Fix:** Reword to "per API key per minute (plus a per-IP global limit)."

### L-3 — LOW — BYOK LLM key has no UI despite backend support, docs, and a provider dropdown
